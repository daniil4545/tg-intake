# intake - контекст AI-агентов

Канонический файл проекта. Держим коротким; детали живут в `docs/`.

Общие конвенции всех проектов Galera (язык, ветки, релизы, CHANGELOG,
безопасность) живут во внутренней базе знаний; здесь только специфика проекта.

Репозиторий: `github.com/daniil4545/tg-intake`, публичный. Всё, что попадает в
коммит, читается посторонними: ни секретов, ни персональных данных, ни
внутренних имён сотрудников и клиентов.

## Проект

Сервис `intake` (репозиторий `tg-intake`, продуктовое имя «Galera Предложка») -
внутренний Telegram-бот, единая точка входа бизнеса в разработку. Релиз 0.1.0
принимает обращения сотрудников по работающим сервисам, доводит их интервью до
пригодного к работе описания, заводит тикет в GitHub Issues нужного проекта и
показывает его статус по меткам. Следом идут заведение проекта через интервью и
вопросы по документации. Границы, порядок функций и деление -
[docs/prd.md](docs/prd.md).

Цель - убрать владельца из роли переводчика между сырым фидбеком и агентом.
Это внутренний инструмент: минимальная рабочая модель важнее продуктового polish.

## Принципы

1. **Core против Изменяемого.** Каркас (поток, схема БД, контракты интеграций,
   инварианты) меняется дорого и защищается. Правила поведения (контракт
   готовности, тексты, предел вопросов) живут данными и меняются свободно.
   Разделение по функциям - раздел 4 PRD. Правка правил не должна требовать
   миграции.
2. Минимум кода. Никаких функций, интерфейсов и файлов «на будущее».
3. Плоская Go-структура, имя файла равно ответственности.
4. Сначала модель состояния, потом код.
5. Побочные эффекты выполняет детерминированный Go. LLM возвращает недоверенный
   структурированный вывод; Go валидирует его до БД, outbox и внешних API.
6. Комментарии объясняют только неочевидное «почему».
7. Логирование - часть каждого среза: действие автора и решение сервиса
   наблюдаемы, новый side effect сопровождается логом.
8. Не коммитить секреты, `.env`, токены.

## Стек

Модуль `github.com/daniil4545/tg-intake`. Прямых зависимостей три, остальное -
стандартная библиотека. Обоснование выбора - раздел 1
[docs/architecture.md](docs/architecture.md).

- Go 1.25, PostgreSQL 16 (данные и очередь через `FOR UPDATE SKIP LOCKED`)
- `gopkg.in/telebot.v4` - Bot API, кнопки, long polling
- `github.com/jackc/pgx/v5` - драйвер и пул
- `github.com/pressly/goose/v3` - миграции, бинарь в образе
- `log/slog` (stdlib) - JSON-логи; OpenRouter и GitHub - свои клиенты на
  `net/http`, SDK не тянем; ffmpeg не нужен - модель принимает ogg/opus
- Модели: `OPENROUTER_MODEL_MEDIA` (голос и скриншоты,
  `google/gemini-3.1-flash-lite`), `OPENROUTER_MODEL_DIALOG` (интервью и
  саммари, `deepseek/deepseek-v4-flash-0731`)

## Команды

Всё из `src`: `docker compose up -d postgres`, `make migrate-up`, `make run`,
`make test`, `make vet`, `make ci-check`, `make migrate-reset`.
`migrate-*` отказываются работать с не-localhost базой без `ALLOW_REMOTE=1`.

Диагностика контура - только через `deploy/safe-ssh.sh` из корня; без
аргументов печатает список действий. Все действия read-only, произвольный ssh
к серверу не используем.

Проверка выката: зелёный workflow означает «Coolify принял запрос», а не
«версия выкачена» - сверять `app_revision` из `health` с кандидатом, старый
контейнер остаётся healthy и при несостоявшемся деплое. Заведённые в контуре
переменные показывает `deploy-config`; `app-env` - лишь окружение, с которым
стартовал текущий контейнер.

## Workflow

Пайплайн задачи и инженерные дефолты платформы - внутренняя база знаний вне
репозитория. Технические решения - `docs/architecture.md`; нетривиальный срез
получает спеку `docs/plans/plan-*.md` до реализации.

Ветки: единственная - `prod`; срез в `feature/<slug>`, PR в `prod`, после
мерджа ветка удаляется. Деплой контура только по тегу `v*` и команде владельца
(workflow `Deploy`); автодеплоя по push нет. Отдельного dev-контура нет:
понадобится - заводится заново по runbook базы знаний.

Метод интервью взят из промта брифовщика (внутренняя база знаний): разбор
конкретного случая, детектор выдумки, замок пересказа «где я ошибся», признак
тянет вопрос. Промт бота - самостоятельный файл, а не копия: другой жанр и
бюджет вопросов. При правках сверяться с оригиналом, не тащить его целиком.

## Критические инварианты

- **Медиа не переживает обращение.** Файл нужен только до подтверждения саммари
  автором. После публикации тикета файлы удаляются; в БД и в issue остаётся
  текст и `file_id` Telegram. Изображение никогда не попадает в git и в логи.
- **Обезличивание до публикации.** Экстрактор возвращает описание без
  персональных данных клиентов: идентификаторы карточек и статусы остаются,
  ФИО, телефоны и переписка - нет. Транскрипт чистится теми же правилами.
- **Единственный источник истины по статусу - метка issue.** Сервис только
  читает метки и уведомляет об изменении. Кто метку поставил, человек или CI,
  сервису неизвестно и неважно.
- **Экстрактор обязан признаваться в непрочитанном.** Схема извлечения содержит
  поле «не разобрано». Правдоподобная выдумка хуже явного пробела: её примут
  за факт.
- **Тикет не публикуется без подтверждения автора.** Саммари с вопросом «где я
  ошибся» - последняя точка, где ловится неверно прочитанный скриншот, пока
  файл ещё существует.
- **Нормализация до диалога, изображение последним.** Аудио и текст
  нормализуются первыми, скриншоты разбираются после них и с протоколом сырья в
  контексте. Медиа входит в модель один раз, в историю диалога попадает только
  текст.
- **Авторство не теряется.** ФИО из Telegram уходит в шапку тела issue и в
  метку `author:<slug>`. GitHub не даёт создать тикет от чужого имени, поэтому
  автор фиксируется телом, а не полем API. Обезличивание касается данных
  клиентов, не автора.
- **Доступ по белому списку Telegram ID.** Список в конфиге; чужому бот
  отвечает отказом и обращение не заводит.
- **Егресс наружу может быть закрыт.** С хоста контура прямой путь к
  OpenRouter отвечает `403` от фильтра по дороге. Прокси задаётся каждому
  клиенту отдельно (`OPENROUTER_PROXY`, `TELEGRAM_PROXY`), пустое значение -
  прямой путь: общий прокси процесса увёл бы в туннель и GitHub, доступный
  напрямую.
- **Порядок промта фиксирован:** стабильный префикс (инструкция плюс контекст
  проекта) впереди и кэшируется, волатильное (протокол сырья, история) сзади.
  Ни одной изменяющейся строки в префиксе, иначе кэш молча перестаёт работать.
- **Ни одна идея не выбрасывается.** Отклонение всегда с причиной и всегда
  доступно автору в боте; доставка уведомлением - M8. Недобранный контракт даёт
  тикет с меткой `incomplete` и явным списком пробелов, а не отказ.
- **Мультипроектность с первого дня.** Проект - строка в таблице (`owner/repo`
  и контекст для промта). Токен GitHub один на сервис, в таблице ключей нет.
  Добавление проекта не требует деплоя.
- **Внешние вызовы идут через таблицу `jobs`**, идемпотентны по полю `key` и
  оставляют аудит в `case_events`. Синхронно из обработчика апдейта уходят
  только ответы автору внутри диалога.
- **Нормализация не знает, чем кончится разговор.** Сырьё превращается в текст
  одинаково для любого режима: в шаге нормализации нет ни типа тикета, ни
  issue. Это то, что делает вторую функцию бота наслаиванием, а не переписью.
