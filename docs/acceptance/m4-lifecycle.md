# Приёмка M4: просмотр тикетов, отмена и подключение проектов

Дата: 2026-08-08. Спеки: [plan-m4-lifecycle.md](../plans/plan-m4-lifecycle.md),
[plan-m4-projects.md](../plans/plan-m4-projects.md). PR: `feature/m4-lifecycle`.

## Что меняется для людей

**Было.** Автор отправлял обращение, получал номер тикета и ссылку - и на этом
связь обрывалась. Узнать, взяли ли задачу в работу, он мог только написав
владельцу в личку. Ссылка помогала не всем: доступ к репозиториям есть у части
сотрудников.

**Стало.** Автор в любой момент открывает `/tickets`, выбирает проект и видит
последние десять тикетов со статусами по-русски. В карточке - текст тикета
целиком, последний комментарий и ссылка. Свой тикет он может отменить, пока тот
не доигран; бот закрывает issue и подтверждает отмену сообщением.

**Плюс.** Бот больше не показывает сотрудникам один себя: список проектов
задаётся переменной контура, добавление проекта не требует выката кода.

## Тех-сводка

Список строится из своей базы, статусы читаются у GitHub одним запросом в
момент открытия. Отмена идёт через очередь: ставит свою метку, точечно снимает
прочие метки статуса и закрывает issue как `not planned` - чужие метки при этом
целы. Статусы и их названия живут файлом правил, а не кодом, поэтому набор
правится без миграции. Просмотр ходит в GitHub отдельным клиентом с коротким
бюджетом: бот обрабатывает сообщения последовательно, и медленный ответ иначе
заморозил бы его для всех авторов.

## Как проверено

- Сборка, `go vet`, `gofmt` - чисто.
- `go test ./... -race` - зелёный, 9 новых тестов из 15.
- Миграция `0004` применяется и откатывается на живой базе, в том числе когда в
  очереди уже лежит работа отмены.
- Два ключевых теста проверены мутацией: со сломанным кодом они падают.
- Независимое ревью реализации: один блокирующий дефект найден, исправлен и
  покрыт тестом.
- Живого прогона в dev не было ни разу.

## Самопроверка на пять минут

Перед прогоном нужны два действия владельца: заполнить `PROJECTS` в конфигурации
контура и расширить `GITHUB_TOKEN` на репозитории добавленных проектов.

1. Напишите боту `/tickets` - он спросит, тикеты какого проекта показать. В
   списке проектов должны быть все, что вы завели в `PROJECTS`.
2. Выберите проект. Ожидается список последних тикетов вида
   `#9 - Заведён - Заголовок`. Если тикетов нет, бот так и скажет.
3. Нажмите кнопку тикета. Ожидается карточка: номер, статус, автор, текст
   тикета, ссылка. Служебной строки вида `<!-- intake:case:... -->` в тексте
   быть не должно.
4. Поставьте в GitHub на этот issue метку `status:in-progress`, снимите
   `status:new` и переоткройте список. Статус должен стать «В работе».
5. Откройте карточку своего тикета и нажмите «Отменить тикет». Через несколько
   секунд придёт «Тикет #N отменён и закрыт». В GitHub issue закрыт как
   `not planned`, стоит `status:cancelled`, метки `type:` и `author:` целы.
6. Откройте карточку чужого тикета - кнопки «Отменить» быть не должно.

## Известные ограничения

- Уведомлений о смене статуса нет: автор узнаёт новости, только заглянув в
  бота. Отклонение может пролежать незамеченным - это срез M8.
- Комментарии автора к тикету не входят в срез, дополнить тикет можно только
  через GitHub - срез M9.
- Тикеты, заведённые в репозитории руками, боту не видны.
- Статус в списке ищется среди последней сотни issue репозитория; точный статус
  всегда даёт карточка.
- Список ограничен десятью последними тикетами проекта, поиска и фильтров нет.
- Добавление проекта требует правки переменной и рестарта контейнера.

## Как откатить

Выкатить предыдущий образ в Coolify и откатить миграцию: `goose down` до версии
`0003`. Откат снимает уникальный индекс и возвращает прежний список видов работ;
данные обращений и тикеты в GitHub он не трогает. Метки статусов, заведённые в
репозиториях, остаются - они безвредны и пригодятся при следующем выкате.
