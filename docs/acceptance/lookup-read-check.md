# Приёмка: право на чтение документации

Дата: 2026-08-17. Спеки нет - срез мельче её. Ветка:
`feature/lookup-read-check`. Продолжает [ask](ask.md).

## Что меняется для людей

**Было.** Режим «Спросить» не работал ни разу с самого релиза, и об этом никто
не знал: токену GitHub не хватало права читать содержимое репозитория. Первым
на это наступил живой человек - обращение дошло до похода в документацию,
упало шесть раз подряд, а бот предложил «спросить ещё раз своими словами».
Совет не мог сработать: повтор упирался в тот же отказ.

**Стало.** Право проверяется на старте по каждому проекту, и его отсутствие
видно в логе, а не в разговоре. Если доступа всё-таки нет, бот говорит об этом
прямо - доступа нет, повтор не поможет, нужен владелец сервиса, - и оставляет
переход в тикет: обращение автора не теряется.

## Тех-сводка

- `GitHub.CheckRead` - листинг корня репозитория. README для проверки не
  годится: его 404 не отличить от отказа в правах. Клиент рабочий, с повторами:
  сетевой сбой старта иначе записался бы в лог отказом в правах, а настоящий
  403 возвращается сразу и повторов не стоит.
- Старт зовёт её следом за проверкой записи: `github_read_ok` либо
  `github_read_denied` с проектом, репозиторием и ошибкой. Отказ проект не
  выключает - без `Contents` тикеты работают полностью.
- `lookupFailedText` разводит отказ в правах и временный сбой тем же приёмом,
  что уже стоял на публикации; общий признак вынесен в `isDenied`.
- Сообщение об отказе называет недостающее право: ответ GitHub несёт заголовок
  `X-Accepted-GitHub-Permissions`, и он уже попадал в текст ошибки.

Миграций нет. Переменная не менялась, но право у токена расширяется:
`Issues: read and write` плюс `Contents: read`.

## Как проверено

- `make ci-check` в `src` (база на 5433, 5432 занят соседним сервисом):
  миграции, тесты, `go vet`, сборка - зелёные.
- Новые тесты: `TestCheckReadNamesMissingPermission` - отказ несёт статус и имя
  права, а запрос уходит по адресу контента; `TestLookupFailedTextSeparatesDenial`
  - 403 отправляет к владельцу, сетевой сбой оставляет прежнее «спросите ещё
  раз».
- Живой отказ на контуре отдельно не проверяется: для этого пришлось бы отнять
  право у рабочего токена.

## Самопроверка на 5 минут

1. Владелец добавляет `Contents: Read` в fine-grained PAT на репозитории
   проектов, при пересоздании токена обновляет `GITHUB_TOKEN` в Coolify.
2. `deploy/safe-ssh.sh health` - `app_revision` совпадает с выкаченным тегом.
   Зелёный workflow этого не доказывает: старый контейнер остаётся healthy.
3. `deploy/safe-ssh.sh app-logs 100` - на каждый активный проект пара
   `github_write_ok` и `github_read_ok`, ни одного `github_read_denied`.
4. В боте: проект qualifier, «Спросить», любой вопрос про сервис. Ответ
   приходит со ссылкой на md-файл.
5. `deploy/safe-ssh.sh case <id>` - работа `lookup` в `done`, статус обращения
   `collecting`: ответ разговор не закрывает, `answered` ставит только
   «Закончить разговор».

## Известные ограничения

- Проект, заведённый командой `/project` после старта, проверку чтения получит
  только при следующем перезапуске: `/project` проверяет лишь право писать.
  Заведение проекта - действие владельца, и лог старта он видит.
- Проверка стоит на корне репозитория: право, выданное точечно и не
  покрывающее каталог `docs/`, она пропустит. GitHub такой нарезки не даёт,
  случай теоретический.

## Как откатить

Откат коммитов среза. Миграций нет, состояние в базе не затрагивается;
расширенное право у токена откатывать не требуется - оно ничему не мешает.
