- Воркер - `RunWorker` с картой работ из `main.go`, стоп по `t.Cleanup`.

## 3. Ведение диалога

Модель недетерминирована. По итогам двух живых прогонов (первый - S1, S5 pass, остальные fail
без поломки продукта кроме `checkTurn`; второй - все пять упёрлись в жёсткие проверки
конкретного выбора модели или в провайдера) тест разделяет три рода исхода:
- **Инвариант продукта** - жёсткая проверка (`Errorf`/`Fatalf`), обязана держаться при любом
  выборе модели: не больше одного сообщения с `inline_keyboard` (`assertScreenStripped` - у
  прошлого живого экрана есть `editMessageReplyMarkup` раньше, чем новый стал живым); ровно
  один `answerCallbackQuery` на нажатие, ноль тоже провал (`pressButton` считает вызовы до и
  после конкретного нажатия, а не последний тост всего прогона); устаревшая кнопка - toast
  «Этот экран устарел» без побочного действия; пропуск ведёт к саммари без нового раунда
  (Р-15); метка `incomplete` и строка «Не уточнено:» есть тогда и только тогда, когда
  `rules.Unclear(kind, filled)` не пусто - тот же расчёт, что делает `Publisher`, а не
  самоотчёт модели (`cs.Gaps`); типовые метки issue отражают фактический `cs.Kind` (`mixed` -
  обе, иначе - только своя); каждая заготовленная тестом мысль автора - её ключевая фраза -
  встречается в теле issue (`assertIdeasKept`, «Ни одна идея не выбрасывается»); заголовков
  модели от 1 до 6, без повторов (`assertHeadings`).
- **Выбор модели** - был ли раунд, какие ключи спросила, закрыла ли пункт ядра - идёт в
  `t.Logf` (`driveToSummary`, `logCoreGaps`), сценарий идёт дальше по фактическому пути: если
  раунд случился, отвечаем подготовленными фактами (`answerWithFacts` - все факты разом, не
  только по ключу конкретного вопроса: модель может спросить не под тем ключом, под которым
  заготовлен факт) и ждём следующего шага.
- **Провайдер** - шаг не дождался ответа за `liveStepDeadline` (не меньше двух подряд попыток
  работы воркера, `2*jobTimeout` с запасом): если в журнале этого обращения есть `llm_retry`
  или `job_failed` с «deadline exceeded», сценарий `t.Skipf` с числом таймаутов, а не `FAIL` -
  провайдер не отвечал, продукт ни при чём; зависание без этих следов - `Fatalf`, продукт
  виноват. Итоговая строка `TestLiveRun`: сколько сценариев дошли до конца, сколько пропущено
  провайдером, сколько упало; если ни один из S1-S5 не дошёл - `FAIL`.

Раунд отвечается одним текстом автора (§3 плана - как и полагается по формату диалога).
Саммари подтверждается кнопкой «Публикую» только после того, как статус действительно стал
`summary` - до этого момента кнопка не нажимается (после первого прогона S2 жал её раньше).

## 4. Сценарии

Вход каждого: `/start`, проект, «Создать тикет», материал текстом, «Готово». Проверка -
инварианты §3, а не конкретный выбор модели (`kind`, число раундов, какие ключи) - тот идёт в
`t.Logf`, а факты ниже отвечают раунд, если он случился, а не гарантируют его.

| # | Материал | Факты на случай раунда |
|---|---|---|
| S1 `R2` баг | ссылка на сделку 59767187, затем расшифровка (закрылась «Дублем», ждали «Встреча назначена») | `case`, `wrong` - те же детали ещё раз |
| S2 `R2` пожелание | «Руками отказываю лидам не под портрет ..., ставлю сделке "нерелевантен лид"» | `need`, `why`, `detail` (признак - деятельность вне агентств и студий) |
| S3 `R1` смесь | текст `R1` из §10 (склонение имени + напоминание за час вместо дня) | `case`, `wrong`, `why` (`mixedR1Facts`) |
| S4 смесь для гейта B | тот же случай, продиктованный другими словами, плюс отдельная идея без пункта ядра (комментарий при закрытии сделки - проверяет, что идея не потерялась) | те же `mixedR1Facts` |
| S5 `R5` пропуск | «Напоминания опять приходят неправильно» | нет - раунд не отвечается, а пропускается кнопкой |

S3/S4 issue остаётся открытым для гейта B (`closeAfter=false` в `mixedScenario`); S1/S2/S5
закрывают тикет в песочнице сами после публикации (§8).

Сценарий - подтест `t.Run`; итог - строка `t.Logf`: issue, метки, `kind`, `gaps`, события,
pass/fail. `TestLiveRun` в конце печатает «итог: пройдено/пропущено провайдером/упало» (§3).

## 5. Запуск

```
make -C src live GITHUB_TOKEN=$(gh auth token) LIVE_DATABASE_URL='postgres://intake:intake@localhost:5434/intake_live?sslmode=disable'
```

`GITHUB_TOKEN` - make-переменной командной строки, не префиксом окружения (`VAR=... make`):
`.env` дерева тоже может держать `GITHUB_TOKEN`, а make отдаёт файлу приоритет над окружением
процесса - префикс молча перекрылся бы. `check-live-db` (Makefile) отказывает, если токен
пришёл из `.env` (`$(origin GITHUB_TOKEN)` = `file`). Токен нигде не печатается. `make -C src
vet lint` зелёный с тегом.

## 7. Критерий приёмки

- Команда: строка §5 зелёная. Сценарий, пропущенный по вине провайдера (§3), приёмке не
  мешает; упавший по инварианту продукта - мешает. Если ни один из S1-S5 не дошёл до конца -
  команда красная (`TestLiveRun` сам это ловит, §3).
- Не автоматизируется: чтение двух issue смеси (S3, S4) - владелец на гейте B. Вид экранов в
  клиенте не проверяем: разметку покрывает журнал фейка, клиент покажет первое обращение на
  проде после релиза; скрин не нужен.
- Не проверяем: прод, голос и скриншоты; конкретный выбор модели (был ли раунд, число
  раундов, какие ключи спросила) - его статистически измеряет `eval`, не живой прогон.
