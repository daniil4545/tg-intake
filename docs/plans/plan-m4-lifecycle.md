# Спека M4: просмотр тикетов и отмена

Дата: 2026-08-08. Даёт автору обратную дорогу: посмотреть, что стало с его
тикетом, и отменить ненужный. Версия 2, после двух независимых ревью.

Основание: [prd.md](../prd.md) разделы 3 и 4Б, [architecture.md](../architecture.md)
разделы 3, 4, 6, 11. Предыдущий срез - [plan-m2-interview.md](plan-m2-interview.md).

## 1. Что делаем и зачем

После M2 обращение доходит до issue и на этом обрывается. Автор получил номер и
ссылку - и всё: узнать, взяли ли тикет в работу, отклонили ли, он может только
спросив владельца в личку. Ровно то, ради устранения чего сервис и писался.

M4 достраивает просмотр: список тикетов проекта со статусами, карточка с телом
тикета и последним комментарием, кнопка отмены своего тикета. Статус читается у
GitHub в момент, когда автор открыл список.

Критерий смысла: за неделю работы ни один автор не написал владельцу «что там с
моим тикетом».

## 2. Границы среза

**Входит.** Метки статусов правилами и в bootstrap, вход в просмотр командой и
из меню, список тикетов проекта, карточка с телом и последним комментарием,
отмена тикета автором через очередь.

**Не входит.** Уведомления о смене статуса и фоновый опрос GitHub - срез M8.
Комментарии автора к тикету - срез M9. Проверка дублей - M5. Брифинг - M6.

**Конфиг не меняется.** Ни одной новой переменной.

## 3. Решения среза

**Уведомления и фоновый опрос вынесены из среза.** Решение владельца. Три
рабочих статуса на десяток тикетов - это до тридцати сообщений автору за цикл,
и они обесценивают друг друга; статус нужен в тот момент, когда человек о нём
вспомнил. Отказ убирает из среза фоновую горутину, работу опроса и обе колонки
состояния: хранить «о чём автору уже сказали» незачем, если ему не говорят.

Цена названа прямо: инвариант «отклонение всегда доходит до автора» ослаблен до
«доступно автору в боте», и это записано в [AGENTS.md](../../AGENTS.md).

**Комментарии автора вынесены тем же решением.** Комментарий по PRD - это
полноценный сбор пачки с голосом и скриншотами, то есть второй активный
разговор у автора, а `cases_one_active_per_user` держит ровно одно. Снять
индекс мало: нужен способ, которым автор показывает, к какому разговору
относится очередное голосовое. [architecture.md:474-484](../architecture.md#L474-L484)
уже назвал это решением продукта и отложил до M6.

**Список строится из своей базы, статусы добираются одним запросом.** В `cases`
уже лежат `issue_number`, `issue_url`, `title` и `summary` - заголовки и номера
оттуда. Метки живут только в GitHub, поэтому на открытие списка идёт один
запрос за последними issue репозитория. Issue, заведённые руками, в списке не
появятся: бот показывает то, что завёл сам.

**Чтение GitHub идёт синхронно, но с отдельным бюджетом.** Инвариант требует
пускать внешние вызовы через `jobs`; защищает он побочные эффекты и доставку, а
у просмотра нет ни того, ни другого - это чтение без следа, автор ждёт ответа
на экране. Но телебот поднят с `Synchronous: true` ([bot.go:80](../../src/internal/app/bot.go#L80)),
апдейты всех авторов идут одной очередью, а рабочий клиент GitHub держит
таймаут 20 секунд и три повтора с отсрочкой - один отказ заморозил бы бота для
всех почти на полминуты. Поэтому просмотр ходит через отдельный клиент:
таймаут 5 секунд, ноль повторов, отказ сразу превращается в «статус
недоступен». Мутации (отмена) остаются работой в очереди с полным бюджетом.

**Право отмены - только у автора.** PRD различает «просмотр - все видят все» и
«отмена автором» как отдельные правила. Кнопка «Отменить» рисуется, только если
нажавший равен `cases.user_id`, и работа отмены перепроверяет это же условие:
кнопка живёт в чужом сообщении ровно до перезапуска клиента.

**Набор статусов - один источник, файл правил.** Метки статусов заводятся из
`rules/statuses.json`, а не перечисляются вторично в Go. Иначе добавленный в
файл статус бот умел бы читать, но никогда не завёл бы в GitHub - молчаливый
рассинхрон между «Изменяемым» и Core. В `baseLabels` остаются только `type:*` и
`incomplete`.

**Метка статуса опознаётся по префиксу `status:`.** Без этого правила
`author:<slug>`, `type:bug` и `incomplete` попадали бы в «неизвестный статус» на
каждом тикете и залили бы лог. Неизвестной считается только метка с префиксом
`status:`, которой нет в правилах.

**Отмена меняет метки точечно.** `PUT .../labels` затирает все метки issue
разом, включая проставленные владельцем. Поэтому отмена добавляет
`status:cancelled` через `POST` и снимает через `DELETE` все прочие метки с
префиксом `status:` - именно все, а не одну: после падения между вызовами на
issue может висеть две.

## 4. Правила данными: `rules/statuses.json`

Статусы по PRD - блок «Изменяемое». Порядок в файле задаёт приоритет: если на
issue висит несколько меток статуса, побеждает первая по файлу. Порядок меток в
ответе GitHub произволен и осмысленным приоритетом быть не может.

```json
{
  "statuses": [
    {"label": "status:rejected",    "title": "Отклонён", "color": "b60205", "final": true},
    {"label": "status:cancelled",   "title": "Отменён",  "color": "cfd3d7", "final": true},
    {"label": "status:prod",        "title": "В проде",  "color": "0e8a16", "final": true},
    {"label": "status:dev",         "title": "В dev",    "color": "1d76db", "final": false},
    {"label": "status:in-progress", "title": "В работе", "color": "fbca04", "final": false},
    {"label": "status:new",         "title": "Заведён",  "color": "ededed", "final": false}
  ]
}
```

| Поле | Назначение |
| --- | --- |
| `label` | имя метки в GitHub, ключ сопоставления и то, что заводит bootstrap |
| `title` | что видит автор в списке и карточке |
| `color` | цвет метки при заведении. Живёт здесь, а не в Go: иначе набор статусов снова раздвоится |
| `final` | тикет доигран, кнопка отмены не рисуется |

Валидация при старте по образцу `LoadContract`: пустой список, пустая метка,
пустой `title`, дубль метки, метка без префикса `status:` или отсутствие хотя бы
одного нефинального статуса - ошибка старта. Файл из одних финальных статусов
тихо убрал бы отмену навсегда.

`Statuses.Pick(labels []string) (Status, bool)` - первый по файлу статус из
набора меток issue. Метки без префикса `status:` игнорируются молча, метка с
префиксом и без записи в файле пишется в лог как `status_unknown`.

## 5. Схема: миграция `0004_lifecycle.sql`

```sql
-- +goose Up

-- Пять меток статусов заводятся впервые: bootstrap уже отработал в M2 и поднял
-- флаг, иначе новые метки не доехали бы до существующих проектов.
UPDATE projects SET labels_ready = false;

-- Карточка ищет обращение по паре проект-номер, единственность обязана быть
-- гарантией схемы, а не удачей.
CREATE UNIQUE INDEX cases_project_issue ON cases (project_id, issue_number)
    WHERE issue_number IS NOT NULL;

ALTER TABLE jobs DROP CONSTRAINT jobs_kind_check,
                 ADD  CONSTRAINT jobs_kind_check CHECK (kind IN (
                     'normalize_voice', 'normalize_images', 'interview',
                     'summarize', 'publish', 'notify', 'remind', 'cancel_issue'));

-- +goose Down

-- Удаление строго до пересоздания CHECK: ADD CONSTRAINT валидирует таблицу
-- немедленно, и одна строка cancel_issue уронила бы откат.
DELETE FROM jobs WHERE kind = 'cancel_issue';
ALTER TABLE jobs DROP CONSTRAINT jobs_kind_check,
                 ADD  CONSTRAINT jobs_kind_check CHECK (kind IN (
                     'normalize_voice', 'normalize_images', 'interview',
                     'summarize', 'publish', 'notify', 'remind'));
DROP INDEX cases_project_issue;
```

Колонки статуса тикета нет и не появляется: инвариант «единственный источник
истины - метка issue» остаётся буквальным. `cases.status` не трогаем - отмена
это состояние issue, а не обращения; обращение остаётся `published`.

## 6. Правки существующего кода

M4 наслаивается, но четыре правки в коде M2 обязательны, и каждая нужна не
ради удобства.

| Файл | Правка | Почему обязательна |
| --- | --- | --- |
| `github.go` | `NewGitHub(token, api string, log)` - базовый URL параметром вместо константы, плюс второй `http.Client` для чтения с таймаутом 5с и без повторов | без первого нечем подменить GitHub в тестах, без второго отказ GitHub морозит бота для всех авторов |
| `github.go` | `baseLabels` теряет `status:new`, статусы приходят из правил; появляется `listIssues` - один низкоуровневый запрос списка, из которого растут `FindIssue` и просмотр | иначе набор статусов задан в двух местах, а запрос списка написан дважды |
| `bot.go` | `sendLong` вешает `opts` только на последний кусок | сейчас длинная карточка продублирует кнопки под каждым куском |
| `bot.go` | вход в просмотр командой `/tickets`, а не только кнопкой меню | меню действий рисуется только при `cs == nil` ([bot.go:339](../../src/internal/app/bot.go#L339)); во время интервью до кнопки не добраться, а именно тогда автор и вспоминает про старый тикет |
| `case.go` | ветка `cancel_issue` в `HandleFailedJob` | без неё исчерпавшая повторы отмена молча умирает, а автору уже сказали «отменяю» |
| `main.go` | `checkGitHub` заводит метки при `labels_ready = false` и зовёт `MarkLabelsReady` | иначе новые метки статусов доедут до проекта только со следующей публикацией |

## 7. Поток

```
   /tickets  либо  меню проекта -> «Посмотреть тикеты»
          |
          v
   номера и заголовки из cases  +  GET issues?state=all  ->  метки по номерам
          |
      список: #12 В работе - Заголовок
          |
      кнопка тикета
          v

          |

```

## 8. Функции

Всё новое живёт в `tickets.go`. Владелец - тип `Tickets{pool, gh, statuses, log}`:
у `Cases` нет и не должно быть GitHub-клиента, он владеет состоянием обращения,
а не внешним трекером.

```go
type Ticket struct {
    CaseID  string
    Number  int
    URL     string
    Title   string
    UserID  int64          // автор: решает, рисовать ли «Отменить»
    Status  Status         // пустая, если метку не удалось прочитать
    Author  string         // ФИО из users, только для карточки
    Body    string         // cases.summary, только для карточки
    Comment string         // последний комментарий issue, только для карточки
}
```

Один тип на список и карточку: три поля карточки в списке остаются пустыми, а
второй тип с пересечением в шести полях дороже, чем три пустые строки.

### `LoadStatuses() (Statuses, error)`

Читает `rules/statuses.json` из `embed` (директива расширяется до
`//go:embed rules/*.json`), разбирает и валидирует по разделу 4. Зовётся в
`main.go` рядом с `LoadContract`.

### `(t *Tickets) List(ctx, projectID) ([]Ticket, error)`

1. `SELECT id, issue_number, issue_url, title, user_id FROM cases
   WHERE project_id = $1 AND issue_number IS NOT NULL
   ORDER BY issue_number DESC LIMIT 10`.
2. `listIssues` быстрым клиентом: `state=all&per_page=100&sort=created&direction=desc`.
   Записи с ключом `pull_request` отбрасываются - REST GitHub считает issue
   каждый pull request, и в активном репозитории они вытесняют тикеты из окна.
3. Метки разложить по номерам, статус взять через `Pick`.

Ошибка GitHub не прячет список: заголовки и номера уже прочитаны из базы, автор
видит их со строкой «статус недоступен». Номер, не попавший в окно ста записей,
показывается так же - без статуса. Это осознанный предел: точный статус даёт
карточка.

### `(t *Tickets) Load(ctx, projectID, number) (*Ticket, error)`

1. Обращение по паре проект-номер плюс `LoadUser` за ФИО автора.
2. `GET /repos/{o}/{r}/issues/{n}` быстрым клиентом - актуальные метки. Отказ не
   роняет карточку: статус остаётся пустым. 404 означает «тикет больше не
   существует» и показывается автору прямым текстом.
3. Статус `final` - дочитать последний комментарий через `LastComment`.

Тело берётся из `cases.summary`, а не из `issue.body` ответа GitHub, и это
обязательное условие, а не оптимизация: в теле issue живут шапка авторства и
служебный маркер `<!-- intake:case:<uuid> -->`, которым незачем уезжать в чат.
Перед отправкой тело проходит ту же чистку разметки, что и саммари в диалоге:
`ParseMode` бот не включает, и решётки заголовков ушли бы автору буквально.

### `(t *Tickets) LastComment(ctx, project, number) (string, error)`

`GET /repos/{o}/{r}/issues/{n}/comments?per_page=100`; комментарии приходят по
возрастанию идентификатора, нужен последний. Пришло ровно 100 - берётся
следующая страница, не больше пяти.

Комментарий показывается в карточке как «последний комментарий», а не как
«причина отклонения». Связать их нечем: протокола, которым владелец фиксирует
причину, нет ни в PRD, ни в процессе, и подписать «переоткрыл, беру» причиной
отказа значит соврать автору. Пустой список даёт пустую строку и лог
`comment_missing`: инвариант требует причины, и её отсутствие должно быть
видно.

### `(t *Tickets) Cancel(ctx, cs *Case, userID int64) error`

Постановка работы из хендлера. Перед `PutJob` удаляет прежнюю работу отмены
этого обращения - точно как `FinishCollect` гасит работы прошлого захода:
ключ `cancel:<case_id>` в `jobs` живёт вечно, и без удаления вторая попытка
отмены после провала первой молча не создала бы ничего.

### `(t *Tickets) RunCancel(ctx, job) error`

Вход: `{"case_id": "...", "user_id": N}`.

1. Загрузить обращение. Нет `issue_number` - выход без действия. `user_id` из
   payload не равен `cases.user_id` - выход и лог: отменять чужое нельзя.
2. `GET issues/{n}` полным клиентом. 404 - выход без действия, тикет уже не
   существует. Статус `final` - выход и `notify` автору «тикет уже закрыт»:
   между нажатием и обработкой владелец мог увести его в прод, и молчать здесь
   нельзя, автору уже ответили «отменяю».
3. `POST issues/{n}/labels` с `["status:cancelled"]`.
4. `DELETE issues/{n}/labels/<метка>` для каждой прочей метки с префиксом
   `status:`, 404 игнорируется. Все, а не одна: падение между шагами 3 и 4
   оставляет на issue две метки статуса.
5. `PATCH issues/{n}` с `{"state": "closed", "state_reason": "not_planned"}`.
6. Транзакцией: событие `cancelled_by_author` с `INSERT ... WHERE NOT EXISTS`
   по этому виду события и работа `notify` автору. Без условия повтор работы
   после падения между `PATCH` и `FinishJob` записал бы второе событие в
   журнал.

Проверка `final` делается один раз, на шаге 2, и после собственных мутаций не
повторяется: иначе только что поставленная `status:cancelled` (она финальная)
оборвала бы работу до снятия старой метки.

Порядок вызовов важен: метка ставится до закрытия. Обратный оставил бы закрытый
issue без объяснения при падении между вызовами.

### `HandleFailedJob`: ветка `cancel_issue`

Работа исчерпала повторы - автору уходит «Отменить тикет не получилось,
попробуйте позже», в журнал пишется `cancel_failed`. Молчание оставило бы
человека в уверенности, что тикет отменён, при том что метка могла успеть
поставиться, а закрытие - нет.

### Бот: что добавляется

| Хендлер | Что делает |
| --- | --- |
| `/tickets` | показывает меню проектов теми же кнопками, что `askProject`, со своим `Unique` |
| `onTickets` | список: строки `#12 В работе - Заголовок`, под ними по кнопке на тикет. Пусто - «По этому проекту тикетов ещё нет» |
| `onCard` | карточка: заголовок, статус, автор, тело, последний комментарий, ссылка. Кнопки «Отменить» (только автору и только если не `final`) и «К списку» |
| `onKill` | зовёт `Cancel`, отвечает «отменяю» |

Кнопка «Посмотреть тикеты» добавляется и в меню проекта - короткий путь для
автора без активного обращения.

`callback_data` несёт `<project_slug>:<issue_number>` - в 64 байта укладывается
с запасом. Slug резолвится через `ListProjects` с фильтром `active`, как это
делает `onProject`: проект, выключенный между открытием списка и нажатием,
отвечает «Проект недоступен».

Ссылка на issue остаётся в карточке: у части сотрудников доступ к репозиторию
есть. Содержимое пересказывается всем одинаково - два режима отображения дороже
одного полного.

### `EnsureLabels` и старт

`checkGitHub` уже обходит активные проекты и проверяет доступ. Туда же
добавляется заведение меток при `labels_ready = false` и вызов
`MarkLabelsReady` после успеха. Отказ по проекту остаётся предупреждением, а не
падением старта - как и проверка доступа: один недоступный проект не должен
мешать остальным. Флаг при частичном провале не поднимается, следующий старт
повторит; резервный путь в `Publisher.Run` остаётся и покрывает проекты,
добавленные между рестартами.

Стоимость: при недоступном GitHub старт удлиняется на таймаут по каждому
проекту. Это тот же клиент и тот же бюджет, что уже тратит `CheckAccess`
сегодня, новой цены срез не вносит.

## 9. Контракты GitHub

Проверено по документации, версия API `2022-11-28`.

| Шаг | Запрос | Что берём |
| --- | --- | --- |
| Список | `GET /repos/{o}/{r}/issues` с `state=all`, `sort=created`, `direction=desc`, `per_page` | `number`, `labels[].name`, ключ `pull_request` для отсева |
| Карточка | `GET /repos/{o}/{r}/issues/{n}` | `labels[].name` |
| Комментарий | `GET /repos/{o}/{r}/issues/{n}/comments` с `per_page`, `page` | `body` последнего |
| Отмена, метка | `POST /repos/{o}/{r}/issues/{n}/labels`, тело `{"labels": [...]}` | - |
| Отмена, снятие | `DELETE /repos/{o}/{r}/issues/{n}/labels/{name}`, 404 если метки нет | - |
| Отмена, закрытие | `PATCH /repos/{o}/{r}/issues/{n}`, `state: closed`, `state_reason: not_planned` | - |

Документация предупреждает прямо: «Issues» endpoints may return both issues and
pull requests», отличать по ключу `pull_request`.

Право fine-grained PAT на закрытие issue документация точными словами не
называет («push access or Triage role»), поэтому проверяется живым запросом в
dev, как в M2 проверялось право на метки. Тем же прогоном проверяется двоеточие
в пути `DELETE .../labels/status:new`: по RFC 3986 оно в сегменте пути
допустимо без экранирования, но это первое место в проекте, где имя метки
уезжает в URL, а не в тело.

Расход лимита: один запрос на список, один-два на карточку, до пяти на отмену.
Против 5000 в час незаметно.

## 10. Логи

Добавляются: `tickets_listed` (user_id, project, count), `ticket_opened`
(user_id, case_id, issue), `status_unknown` (project, issue, label),
`comment_missing` (issue), `issue_cancelled` (user_id, case_id, issue),
`cancel_denied` (user_id, case_id), `cancel_failed` (case_id, issue).
`user_id` обязателен там, где действие совершает человек. Тексты комментариев в
лог не идут - они могут содержать что угодно, включая данные клиента.

## 11. Критерий приёмки

1. Автор шлёт `/tickets`, выбирает проект и видит до десяти последних тикетов
   со статусами по-русски.
2. Владелец меняет метку в GitHub, автор переоткрывает список - статус новый.
3. Карточка показывает тело тикета без служебного маркера, без шапки авторства
   и без решёток разметки.
4. У тикета с `status:rejected` в карточке виден последний комментарий.
5. Автор нажимает «Отменить» - issue закрыт с `not planned`, стоит
   `status:cancelled`, все прочие метки статуса сняты, метки `type:*` и
   `author:*` целы.
6. У чужого тикета кнопки «Отменить» нет; работа отмены с чужим `user_id`
   ничего не делает и пишет `cancel_denied`.
7. У тикета в `status:prod` кнопки нет, а если статус сменился после открытия
   карточки - автор получает «тикет уже закрыт», а не молчание.
8. GitHub недоступен - список открывается с заголовками и пометкой «статус
   недоступен» не дольше пяти секунд, бот отвечает другим авторам всё это
   время.
9. `/tickets` работает во время активного интервью и не ломает диалог.
10. Метка `status:` вне правил не роняет просмотр и попадает в лог; метки
    `type:*` и `author:*` в лог не попадают.

## 12. Тестовый сценарий

Клиент GitHub подменяется базовым URL на `httptest.Server` - для этого
`NewGitHub` и получает `api` параметром. Решение M2 «мок проверял бы сам себя»
отменяется в одном месте и по причине: здесь проверяется не ответ GitHub, а то,
какие запросы уходят и в каком порядке.

| Тест | Что проверяет |
| --- | --- |
| `TestListByProject` | список отдаёт только тикеты своего проекта и только с `issue_number` |
| `TestListSkipsPullRequests` | записи с ключом `pull_request` не попадают в сопоставление |
| `TestListSurvivesGitHubError` | отказ оставляет список с пустыми статусами, а не ошибкой |
| `TestPickPriority` | две метки статуса разрешаются по порядку файла правил |
| `TestCancelRemovesAllStatusLabels` | уходят `POST` и `DELETE` на каждую прочую `status:*`, `PUT` не уходит |
| `TestCancelDeniedForStranger` | чужой `user_id` не порождает ни одного запроса |
| `TestCancelTwiceOneEvent` | повтор работы не пишет второе событие в журнал |
| `TestLoadStatuses` | пустой файл, дубль метки, метка без префикса и набор из одних финальных роняют старт |

Живой прогон в dev по всем десяти пунктам приёмки - до гейта B.

## 13. Долги и что останется незакрытым

Закрывается здесь: `PUT` против точечных меток, приоритет статусов, отсев
pull request'ов, право отмены, идемпотентность отмены, точка внедрения для
тестов GitHub.

Открывается и записывается в backlog:

- **Терминальные состояния разошлись с документами.** «Тикет отменён при
  `cases.status = published`» не значится ни в таблице терминальных состояний
  PRD раздела 3, ни в машине состояний architecture раздела 3. Свести после
  приёмки среза.
- **Уведомления о смене статуса** - M8. До него автор узнаёт новости, только
  заглянув в бота, и отклонение может пролежать незамеченным неделю.
- **Комментарии автора к тикету** - M9.
- **Протокола причины отклонения нет.** Карточка честно показывает последний
  комментарий; связать его с отказом можно будет, только когда у владельца
  появится соглашение, как эту причину писать.
- Тикеты, заведённые в репозитории руками, боту не видны.
- Статус в списке ограничен окном в сто последних записей репозитория; точный
  статус даёт карточка.
- Список ограничен десятью последними тикетами проекта, поиска и фильтров нет.
