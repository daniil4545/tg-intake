# Спека M4: просмотр тикетов и отмена

Дата: 2026-08-08. Даёт автору обратную дорогу: посмотреть, что стало с его
тикетом, и отменить ненужный.

Основание: [prd.md](../prd.md) разделы 3 и 4Б, [architecture.md](../architecture.md)
разделы 3, 6 и 11. Предыдущий срез - [plan-m2-interview.md](plan-m2-interview.md).

## 1. Что делаем и зачем

После M2 обращение доходит до issue и на этом обрывается. Автор получил номер и
ссылку - и всё: узнать, взяли ли тикет в работу, отклонили ли, он может только
спросив владельца в личку. Ровно то, ради устранения чего сервис и писался.

M4 достраивает просмотр: список тикетов проекта со статусами, карточка с телом
тикета и причиной отклонения, кнопка отмены своего тикета. Статус читается у
GitHub в момент, когда автор открыл список.

Критерий смысла: за неделю работы ни один автор не написал владельцу «что там с
моим тикетом».

## 2. Границы среза

**Входит.** Метки статусов в bootstrap, список тикетов проекта, карточка тикета
с телом и причиной отклонения, отмена тикета автором, правила статусов данными.

**Не входит.** Уведомления о смене статуса и фоновый опрос GitHub - вынесены
отдельным срезом, решение раздела 3. Комментарии автора к тикету - тоже
отдельный срез. Проверка дублей - M5. Брифинг - M6.

**Конфиг не меняется.** Ни одной новой переменной: период опроса был нужен
только уведомлениям.

**Трогаем существующий код в трёх местах.** Меню действий проекта в `bot.go`
получает вторую кнопку. `baseLabels` в `github.go` дополняется пятью метками
статусов. `checkGitHub` в `main.go` начинает не только проверять доступ, но и
заводить метки. Поток обращения, интервью и публикация не меняются вовсе.

## 3. Решения среза

**Уведомления и фоновый опрос вынесены из среза.** Решение владельца на гейте.
Три рабочих статуса на десяток тикетов - это до тридцати сообщений автору за
цикл, и они обесценивают друг друга; статус нужен в тот момент, когда человек о
нём вспомнил, а не когда он сменился. Отказ от уведомлений убирает из среза
фоновую горутину, работу опроса, обе колонки состояния и почти всю миграцию:
хранить «о чём автору уже сказали» незачем, если ему не говорят.

Цена названа прямо: инвариант «отклонение всегда доходит до автора»
ослабляется до «отклонение всегда с причиной и доступно автору в боте».
Человек может неделю не знать, что его идею не взяли. Это осознанный размен, и
он снимается тем же срезом, который вернёт уведомления.

**Комментарии автора вынесены тем же решением.** Комментарий по PRD - это
полноценный сбор пачки с голосом и скриншотами, то есть второй активный
разговор у автора. Сейчас `cases_one_active_per_user` держит ровно одно
активное обращение, и на этом инварианте стоит разбор каждого входящего
сообщения. Снять индекс мало - нужен способ, которым автор показывает, к какому
разговору относится очередное голосовое; [architecture.md:474-484](../architecture.md#L474-L484)
уже назвал это решением продукта и отложил до M6.

**Список строится из своей базы, статусы добираются одним запросом.** В `cases`
уже лежат `issue_number`, `issue_url`, `title` и `summary` всех опубликованных
ботом тикетов - заголовки и номера берутся оттуда. Метки живут только в GitHub,
поэтому на открытие списка идёт один запрос за последними issue репозитория, и
метки раскладываются по номерам. Issue, заведённые в репозитории руками, в
списке не появятся: бот показывает то, что завёл сам.

**Чтение GitHub идёт синхронно, мимо очереди, и это осознанное отклонение.**
Инвариант требует пускать внешние вызовы через `jobs`, но защищает он побочные
эффекты и доставку: работа не должна потеряться при рестарте. У просмотра нет
ни того, ни другого - это чтение без следа, автор ждёт ответа на экране, а при
ошибке нажимает кнопку ещё раз. Через очередь список превратился бы в переписку
с задержкой, ровно как ответы диалога, которые M2 по той же причине шлёт
синхронно. Отмена - мутация, и она остаётся работой в очереди.

**Отмена меняет метки точечно, а не заменяет набор.** `PUT .../labels` затирает
все метки issue разом, включая проставленные владельцем вручную. Поэтому отмена
идёт двумя вызовами: `POST .../labels` добавляет `status:cancelled`,
`DELETE .../labels/{name}` снимает прежнюю метку статуса, и 404 на удалении
означает «метки и не было» - это не ошибка.

## 4. Правила данными: `rules/statuses.json`

Статусы по PRD - блок «Изменяемое». Набор и тексты живут файлом рядом с
`contract.json`, читаются при старте и валидируются: пустой список, пустая
метка или дубль роняют старт, а не первый просмотр.

```json
{
  "statuses": [
    {"label": "status:new",         "title": "Заведён",  "final": false},
    {"label": "status:in-progress", "title": "В работе", "final": false},
    {"label": "status:dev",         "title": "В dev",    "final": false},
    {"label": "status:prod",        "title": "В проде",  "final": true},
    {"label": "status:rejected",    "title": "Отклонён", "final": true},
    {"label": "status:cancelled",   "title": "Отменён",  "final": true}
  ]
}
```

| Поле | Назначение |
| --- | --- |
| `label` | имя метки в GitHub, оно же ключ сопоставления при чтении issue |
| `title` | что видит автор в списке и карточке |
| `final` | тикет доигран. Кнопка отмены на нём не рисуется |

Метка, которой нет в файле, показывается автору как «статус неизвестен» и
пишется в лог: владелец завёл свою метку, и выдумывать её смысл сервис не
станет.

## 5. Схема: миграция `0004_lifecycle.sql`

```sql
-- +goose Up

-- Пять меток статусов заводятся впервые: bootstrap уже отработал в M2 и поднял
-- флаг, иначе новые метки не доехали бы до существующих проектов.
UPDATE projects SET labels_ready = false;

ALTER TABLE jobs DROP CONSTRAINT jobs_kind_check,
                 ADD  CONSTRAINT jobs_kind_check CHECK (kind IN (
                     'normalize_voice', 'normalize_images', 'interview',
                     'summarize', 'publish', 'notify', 'remind', 'cancel_issue'));

-- +goose Down
ALTER TABLE jobs DROP CONSTRAINT jobs_kind_check,
                 ADD  CONSTRAINT jobs_kind_check CHECK (kind IN (
                     'normalize_voice', 'normalize_images', 'interview',
                     'summarize', 'publish', 'notify', 'remind'));
DELETE FROM jobs WHERE kind = 'cancel_issue';
```

Ни одной новой колонки. Статус тикета в базе не хранится вовсе - инвариант
«единственный источник истины по статусу - метка issue» остаётся буквальным, и
проверка на ревью прежняя: колонки статуса тикета в схеме нет.

`cases.status` не трогаем: отмена тикета - это состояние issue, а не обращения.
Обращение остаётся `published`, оно своё дело сделало.

## 6. Поток

```
   меню проекта -> «Посмотреть тикеты»
          |
          v
   номера и заголовки из cases  +  GET issues?state=all  ->  метки по номерам
          |
      список: #12 В работе - Заголовок
          |
      кнопка тикета
          v
   карточка: GET issues/{n}  (+ GET comments, если метка status:rejected)
          |
      «Отменить» (только если статус не final)
          v
   job cancel_issue --> POST labels, DELETE labels/{прежняя}, PATCH state=closed
          |
          v
   notify автору: «Тикет #12 отменён»
```

## 7. Функции

### `LoadStatuses() (Statuses, error)`

Читает `rules/statuses.json` из `embed`, разбирает и валидирует. Пустой список,
пустая метка или дубль метки - ошибка старта. Возвращает тип с двумя методами:
`ByLabel(label string) (Status, bool)` и `Pick(labels []string) (Status, bool)` -
первая известная метка статуса из набора issue.

### `ListTickets(ctx, projectID) ([]Ticket, error)`

1. `SELECT issue_number, issue_url, title, user_id FROM cases WHERE project_id = $1
   AND issue_number IS NOT NULL ORDER BY issue_number DESC LIMIT 10`. Десять
   последних: список в Telegram листать неудобно, а тикет старше десятого ищется
   в GitHub тем, у кого есть доступ.
2. `GET /repos/{o}/{r}/issues?state=all&per_page=100&sort=created&direction=desc` -
   один запрос на весь список.
3. Разложить метки по номерам, для каждого тикета взять `Pick`. Номера, которых
   в ответе не оказалось, получают пустой статус: показываем тикет без него, а
   не прячем.

Ошибка GitHub не прячет список: заголовки и номера уже прочитаны из базы, автор
видит их со строкой «статус недоступен». Просмотр не должен умирать вместе с
чужим сервисом.

### `LoadTicket(ctx, projectID, number) (*Ticket, error)`

1. Обращение по проекту и номеру issue из базы: заголовок, тело `summary`,
   автор, ссылка.
2. `GET /repos/{o}/{r}/issues/{n}` - актуальные метки, точечно и свежо.
3. Метка `status:rejected` - дочитать причину через `ReadReason`.

### `ReadReason(ctx, project, number) (string, error)`

`GET /repos/{o}/{r}/issues/{n}/comments?per_page=100`; комментарии приходят по
возрастанию идентификатора, нужен последний. Пришло ровно 100 - берём следующую
страницу, не больше пяти: пятьсот комментариев у внутреннего тикета означают,
что что-то пошло не так, и это видно в логе.

Комментариев нет - возвращает пустую строку, карточка пишет «причина не
указана», а лог получает предупреждение. Инвариант требует, чтобы отклонение
всегда шло с причиной, и его нарушение должно быть заметно.

### `RunCancelIssue(ctx, job) error`

Вход: `{"case_id": "..."}`. Ключ работы `cancel:<case_id>` - повторная постановка
невозможна.

1. Загрузить обращение. Нет `issue_number` - выход без действия.
2. `GET /repos/{o}/{r}/issues/{n}` - текущие метки. Статус `final` - выход:
   между нажатием кнопки и обработкой работы тикет мог уехать в прод.
3. `POST /repos/{o}/{r}/issues/{n}/labels` с `["status:cancelled"]`.
4. `DELETE /repos/{o}/{r}/issues/{n}/labels/<прежняя метка>`, 404 игнорируем.
5. `PATCH /repos/{o}/{r}/issues/{n}` с `{"state": "closed", "state_reason":
   "not_planned"}`.
6. Транзакцией: событие `cancelled_by_author` в `case_events` и работа `notify`
   автору с подтверждением.

Порядок важен: метка ставится до закрытия. Обратный порядок оставил бы закрытый
issue без объяснения, если сервис упадёт между вызовами. Повтор безопасен:
добавление метки идемпотентно, удаление отсутствующей даёт игнорируемый 404,
закрытие закрытого - не ошибка.

### Бот: что добавляется

| Хендлер | Что делает |
| --- | --- |
| `onTickets` | кнопка «Посмотреть тикеты» в меню проекта. Строки вида `#12 В работе - Заголовок`, под ними по кнопке на тикет |
| `onCard` | карточка: заголовок, статус, автор, тело из `summary`, причина отклонения, ссылка. Кнопки «Отменить» (если статус не `final`) и «К списку» |
| `onKill` | ставит работу `cancel_issue`, отвечает «отменяю» |

`callback_data` несёт `<project_slug>:<issue_number>` - в 64 байта укладывается
с запасом.

Ссылка на issue остаётся в карточке: у части сотрудников доступ к репозиторию
есть. Но содержимое пересказывается всем одинаково, потому что у части его нет,
и два режима отображения дороже одного полного.

Просмотр не создаёт обращение и не мешает активному диалогу: он работает только
кнопками, а текст в состоянии `interview` по-прежнему уходит ответом на вопрос.

### `EnsureLabels`: что меняется

`baseLabels` дополняется пятью метками статусов: `status:in-progress`,
`status:dev`, `status:prod`, `status:rejected`, `status:cancelled`. Вызов
переезжает в старт сервиса - `checkGitHub` уже обходит активные проекты и
проверяет доступ, там же заводит недостающие метки при `labels_ready = false`.
Иначе после выката M4 владелец не смог бы поставить `status:in-progress` до
первой новой публикации.

## 8. Контракты GitHub

Проверено по документации, версия API `2022-11-28`.

| Шаг | Запрос | Что берём |
| --- | --- | --- |
| Список | `GET /repos/{o}/{r}/issues` с `state=all`, `sort=created`, `direction=desc`, `per_page` | `number`, `labels[].name` |
| Карточка | `GET /repos/{o}/{r}/issues/{n}` | `labels[].name`, `state` |
| Причина | `GET /repos/{o}/{r}/issues/{n}/comments` с `per_page`, `page` | `body` последнего комментария |
| Отмена, метка | `POST /repos/{o}/{r}/issues/{n}/labels`, тело `{"labels": [...]}` | - |
| Отмена, снятие | `DELETE /repos/{o}/{r}/issues/{n}/labels/{name}`, 404 если метки нет | - |
| Отмена, закрытие | `PATCH /repos/{o}/{r}/issues/{n}`, `state: closed`, `state_reason: not_planned` | - |

Клиент `GitHub` из M2 переиспользуется целиком: повторы, разбор `Retry-After` и
различение 4xx и 5xx уже написаны, добавляются только методы.

Право fine-grained PAT на закрытие issue документация точными словами не
называет (сказано «push access or Triage role»), поэтому проверяется живым
запросом в dev, как в M2 проверялось право на метки.

Расход лимита: один запрос на открытие списка, один-два на карточку, три на
отмену. Против 5000 запросов в час это незаметно даже при десятке
пользователей.

## 9. Логи

Добавляются: `tickets_listed` (project, count), `ticket_opened` (case_id,
issue), `status_unknown` (project, issue, label), `reason_missing` (issue),
`issue_cancelled` (case_id, issue). Текст причины отклонения в лог не идёт - он
может содержать что угодно, включая данные клиента.

## 10. Критерий приёмки

1. Автор открывает «Посмотреть тикеты» и видит до десяти последних тикетов
   проекта с человеческими названиями статусов.
2. Владелец меняет метку в GitHub, автор переоткрывает список - статус новый.
3. Карточка показывает тело тикета целиком: автор читает его, не выходя в
   GitHub.
4. У тикета с меткой `status:rejected` в карточке виден текст причины из
   последнего комментария.
5. Автор нажимает «Отменить» - issue закрыт с `not planned`, метка
   `status:cancelled` стоит, прежняя метка статуса снята, чужие метки целы.
6. У тикета в статусе `status:prod` кнопки «Отменить» нет.
7. GitHub недоступен - список открывается с заголовками и пометкой «статус
   недоступен», а не ошибкой.
8. Метка, которой нет в правилах, не роняет просмотр и попадает в лог.

## 11. Тестовый сценарий

Без сети, на подменённом HTTP-клиенте GitHub и на живой базе из compose.

| `TestListTicketsByProject` | список отдаёт только тикеты своего проекта и только с `issue_number` |
| `TestListSurvivesGitHubError` | отказ GitHub оставляет список с пустыми статусами, а не ошибкой |
| `TestUnknownLabel` | метка вне правил не роняет просмотр |

Живой прогон в dev-контуре по всем восьми пунктам приёмки - до гейта B.

## 12. Что останется незакрытым

- **Уведомления о смене статуса и фоновый опрос GitHub** - отдельный срез.
  До него автор узнаёт новости, только заглянув в бота, и отклонение может
  пролежать незамеченным неделю.
- **Комментарии автора к тикету** - отдельный срез вместе с решением о двух
  активных разговорах. До него дополнить тикет можно только через GitHub.
- Тикеты, заведённые в репозитории руками, боту не видны.
- Причина отклонения ищется не глубже пятисот комментариев.
- Список ограничен десятью последними тикетами проекта, поиска и фильтров нет -
  отложено осознанно.
- Статус в списке верен на момент открытия: между просмотром и нажатием
  «Отменить» он мог смениться. Поэтому работа отмены перечитывает метки и
  отступает, если тикет уже `final`.
