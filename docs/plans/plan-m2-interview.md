# Спека M2: интервью и публикация

Дата: 2026-08-08. Замыкает Core: обращение доходит от протокола сырья до issue
в GitHub. После M2 сервис решает исходную задачу целиком.

Основание: [prd.md](../prd.md) разделы 3 и 4, [architecture.md](../architecture.md)
разделы 3, 6-9. Предыдущий срез - [plan-m1-intake.md](plan-m1-intake.md).

## 1. Что делаем и зачем

M1 доводит пачку сырья до `cases.protocol` и останавливается. Дальше сегодня
никто не идёт: обращение висит в `normalizing`, автор не получает ни вопросов,
ни тикета.

M2 достраивает три шага: диалоговая модель добивает недостающие пункты
контракта готовности раундами по 2-3 вопроса, автор подтверждает саммари, Go
публикует issue через очередь и отдаёт автору номер и ссылку.

Критерий смысла: владелец берёт созданный issue и начинает по нему спеку, не
задав автору ни одного уточняющего вопроса.

## 2. Границы среза

**Входит.** Контракт готовности данными, интервью раундами, ответ текстом,
голосом и кнопкой «Всё так», саммари с вопросом «где я ошибся», правка саммари,
публикация issue через outbox с авторством и метками, bootstrap меток проекта,
напоминание о брошенном черновике, `GITHUB_TOKEN` и модель диалога в конфиге.

**Не входит.** Просмотр тикетов, статусы, уведомления о смене метки,
комментарии, отмена после публикации - это M4. Проверка дублей - M5. Брифинг -
M6.

**Трогаем в M1 ровно три места, и только их.** Конец нормализации
(`normalize.go`) сейчас шлёт автору «следующий шаг появится позже» и ничего не
ставит в очередь - вместо текста-заглушки ставится работа `interview`.
`DropFiles` уезжает из нормализации в `PublishIssue`. Разбор входящего
сообщения в `bot.go` учится различать сырьё и ответ на вопрос. Всё остальное в
M1 закрыто; иная правка - только если тест M2 вскроет дефект, отдельным
коммитом с причиной.

## 3. Решения среза

**История интервью хранится в `case_events`, новых таблиц и колонок нет.**
Диалог по природе append-only, а журнал с `payload jsonb` уже есть и уже
пишется в тех же транзакциях, что и смена статуса. Отдельная колонка `history`
дала бы вторую копию тех же данных и миграцию; отдельная таблица - третью
сущность ради последовательности из шести записей. История собирается запросом
по видам `round_asked` и `answer_given` в порядке `created_at`. Для M6 модель
не меняется: у длинного брифинга те же события, только их больше.

**Контракт готовности живёт в `internal/app/rules/contract.json`.** Правка
состава пунктов не должна требовать ни миграции, ни деплоя кода - это блок
«Изменяемое» из PRD. Файл читается при старте, разбирается в структуру и
валидируется: пустой контракт или тип обращения без обязательных пунктов
роняют старт, а не первый живой диалог.

JSON, а не YAML: разбор есть в стандартной библиотеке, а пятая зависимость ради
одного файла правил не окупается. Читаемость файла от этого не страдает, а
список типов обращения всё равно ограничен CHECK в `cases.kind` - новый тип
требует миграции, и загрузка правил проверяет это явным сообщением.

**Предел раундов - конфиг `INTERVIEW_ROUNDS`, дефолт 3.** Значение шаткое по
PRD и будет меняться после первых обращений. Конфиг, а не файл правил: это одно
число, а не набор.

**Обезличивание делят промт и Go, и это признанная граница.** Структурные
данные (телефон, email, номер карты) Go вырезает регулярным выражением до
записи в тело issue. Всё остальное - ФИО клиентов, куски переписки - забота
промтов интервью и саммари. Надёжный детектор персональных данных это отдельный
проект, а последняя защита от промаха у нас уже есть: автор видит саммари
целиком до публикации и правит его.

**Публикация идёт одной работой `publish` без параллельности.** Объём на три
порядка ниже лимитов GitHub, а последовательная публикация снимает вопрос
гонки за bootstrap меток проекта.

**Работа обращения существует в единственном экземпляре, и новая заменяет
прежнюю.** Одно правило вместо трёх частных: второе «Готово» перезапускает
нормализацию, дописанный ответ отменяет ещё не начатый ход и модель отвечает
один раз на всё сразу, повторное «Публикую» после исчерпанных повторов снова
уходит в очередь, а не упирается в ключ погашенной работы. Ключ остаётся
детерминированным (`<вид>:<case_id>`), потому что дубли исключены заменой, а не
уникальностью ключа.

Исключение - расшифровка голосового: она привязана к элементу, и её ключ несёт
`item_id`. Такие работы снимает сбор при повторном «Готово».

От дубля наружу защищает не очередь, а состояние: `issue_number` обращения и
скрытый маркер в теле тикета.

**Ход разговора несёт версию и проверяет её при записи.** Замена работы снимает
запланированный ход, но не тот, что уже выполняется: пока модель думает, автор
может дописать. Ход читает число ответов автора перед вызовом модели и требует
его неизменности в транзакции записи; разошлось - результат отбрасывается
целиком, потому что свежий ход уже поставлен ответом. Без этого автор получал
два раунда вопросов на один свой ответ, и заметить это в логах было нечем.

**Создание issue - единственный запрос без повторов на уровне клиента.**
Оборванный ответ на успешный `POST` означает, что тикет уже создан, и слепой
повтор дал бы второй. Повторяет очередь, а она перед этим ищет маркер. У
остальных запросов повторы клиента остаются: они идемпотентны.

## 4. Правила данными: `rules/contract.yaml`

```json
{
  "bug": [
    { "key": "case", "title": "Конкретный случай", "required": true },
    { "key": "expected", "title": "Что должно было произойти", "required": true },
    { "key": "actual", "title": "Что произошло на самом деле", "required": true },
    { "key": "where", "title": "Где это видно", "required": false }
  ],
  "feature": [
    { "key": "problem", "title": "Какую задачу это решает", "required": true },
    { "key": "today", "title": "Как справляются сейчас", "required": true },
    { "key": "result", "title": "Каким должен быть результат", "required": true }
  ],
  "question": [
    { "key": "question", "title": "Вопрос", "required": true },
    { "key": "context", "title": "Что уже пробовали", "required": false }
  ]
}
```

Состав пунктов - предмет правки после первых живых обращений, и менять его
можно без единой строки кода. Заголовки становятся заголовками разделов в теле
issue: одно место задаёт и что спрашиваем, и как это выглядит в тикете.

**Загрузка.** `LoadContract` читает файл через `embed` при старте. Ошибки
разбора и пустой список пунктов у любого типа - падение старта с понятным
сообщением.

## 5. Конфиг: что добавляется

| Переменная | Назначение | Дефолт |
| --- | --- | --- |
| `OPENROUTER_MODEL_DIALOG` | модель интервью и саммари | `deepseek/deepseek-v4-flash-0731` |
| `GITHUB_TOKEN` | fine-grained PAT, `Issues: read and write` | обязательна |
| `INTERVIEW_ROUNDS` | предел раундов вопросов | `3` |

`GITHUB_TOKEN` проверяется при старте по каждому активному проекту: fine-grained
PAT выдаётся на конкретные репозитории, и права на второй проект не следуют из
прав на первый. Право на метки должно обнаружиться до того, как первый тикет
уедет без них. Отсутствие токена роняет старт, как и токен бота; отсутствие
прав на отдельный проект - предупреждение в лог, остальные проекты работают.

## 6. Поток и состояния

Машина состояний не меняется, достраиваются переходы после `normalizing`:

```
[normalizing] --протокол готов--> [interview]
      [interview] --вопросы есть--> ждём ответ автора --> [interview]
      [interview] --contract закрыт или предел раундов--> [summary]
      [summary] --«поправить»--> [interview]
      [summary] --«Публикую»--> [publishing] --issue создан--> [published]
      [interview], [summary] --«Отмена»--> [cancelled]
```

Ожидание ответа автора отдельным статусом не является: обращение стоит в
`interview`, и признак «ждём ответ» - непустой последний `round_asked` без
`answer_given` после него. Так машина остаётся на семи состояниях.

«Отмена» из `publishing` запрещена: работа уже в очереди, и отменять надо было
до неё. Кнопка в этом статусе не показывается, а `CancelCase` перестаёт
отменять обращения в `publishing` - иначе issue создаётся по отменённому
обращению.

**Разбор входящего сообщения.** Сейчас `bot.go` шлёт любой текст и голос в
`CollectItem`, а тот при статусе не `collecting` отвечает «сбор закрыт». В M2
развилка по статусу обращения:

| Статус | Куда идёт сообщение автора |
| --- | --- |
| `collecting` | `CollectItem`, как сейчас |
| `interview`, `summary` | `ApplyAnswers` |
| `normalizing`, `publishing` | «разбираю, минуту» - работа уже идёт |

Без этой развилки ни один ответ на вопрос интервью не доходит до обработчика, и
диалог не работает вовсе.

## 7. Функции

### `LoadContract() (Contract, error)`

Вход: файл `rules/contract.yaml` из `embed`. Выход: контракт по типам
обращения. Алгоритм: разобрать yaml, проверить непустоту каждого типа и
уникальность ключей внутри типа, вернуть структуру. Ошибка роняет старт.

### `RunInterview(ctx, job) error`

Вход: работа `interview` с `case_id`.

1. Загрузить обращение; если статус не `interview` и не `normalizing` - выйти,
   работа устарела.
2. Собрать запрос: system с методом интервью, контрактом нужного типа и
   контекстом проекта; user с протоколом сырья; следом история раундов из
   `case_events`.
3. Запрос к модели диалога по схеме `InterviewTurn`.
4. Валидировать по разделу 8. Нарушение - один повтор запроса, второе - работа
   в `failed`, автору «не смог разобрать, попробуем ещё раз».
5. В одной транзакции: записать `kind`, `contract`, `gaps`, инкремент `round`,
   событие `round_asked` с вопросами, перевод в `interview`.
6. Если `ready` истинно или `round` достиг предела - поставить работу
   `summarize`. Иначе отправить автору раунд вопросов с кнопкой «Всё так».

Работа несёт признак `fix`: при нём предел раундов не проверяется, и правка
саммари даёт дополнительный ход. Иначе автор, заметивший ошибку на последнем
раунде, не может её исправить - счётчик уже на пределе, и следующий проход молча
уходит в саммари. Номер раунда при этом растёт как обычно: одинаковые номера в
журнале сделали бы сверку кнопки «Всё так» неоднозначной.

Предел считается по уже заданным раундам: исчерпав их, ход не спрашивает ничего,
а собирает саммари с тем, что есть. Так `INTERVIEW_ROUNDS=3` означает ровно три
раунда вопросов, а не два.

Выход: либо вопрос автору, либо переход к саммари.

### `ApplyAnswers(ctx, cs, answer) error`

Вход: ответ автора - текст, голосовое или нажатие «Всё так».

1. Голосовое уходит на транскрибацию работой в очередь, тем же шагом, что и
   сырьё M1. Синхронно вызывать модель из обработчика нельзя: апдейты Telegram
   обрабатываются последовательно, и минута ожидания OpenRouter останавливает
   бота для всех авторов.
2. «Всё так» подставляет `suggested` всех вопросов последнего раунда. Номер
   раунда приходит в `callback_data` и сверяется с `cases.round`: кнопка от
   прошлого раунда осталась в чате и не должна закрывать чужие вопросы.
3. Записать событие `answer_given`, снять ещё не начатую работу `interview` и
   поставить новую.

Разбор «на какой вопрос это ответ» делает модель на следующем ходу: Go
свободный текст не парсит. Незакрытые ключи остаются в `gaps` и
переспрашиваются, закрытые не трогаются.

Снятие непочатой работы обязательно: человек дописывает вторым сообщением, а
кнопку «Всё так» нажимает дважды. Без него каждый такой случай давал бы
отдельный ход модели и два раунда вопросов подряд на один ответ.

### `RunSummarize(ctx, job) error`

1. Запрос к модели диалога по схеме `Summary` с контрактом и историей.
2. Валидировать: заголовок непустой и не длиннее 80 символов, ключи разделов
   принадлежат контракту.
3. Вырезать структурные персональные данные регулярным выражением.
4. Записать `title`, `summary`, `incomplete` (истинно при непустых `gaps`),
   перевод в `summary`.
5. Отправить автору саммари по разделам, список пробелов и вопрос «где я
   ошибся» с кнопками «Публикую», «Поправить», «Отмена».

### `ConfirmSummary(ctx, cs) error`

Кнопка «Публикую»: перевод в `publishing` и постановка работы `publish` с
ключом `publish:<case_id>` в одной транзакции. Повторное нажатие ничего не
делает: статус уже не `summary`.

Кнопка «Поправить» состояние не меняет: она только просит написать замечание.
Правкой становится следующее сообщение автора, и обрабатывает его тот же
`AddAnswer` - ответ при статусе `summary` возвращает обращение в `interview` и
идёт признаком `fix`. Отдельное состояние «ждём замечание» дало бы восьмой
статус ради одной подсказки, а голосовая правка работает тем же путём.

### `PublishIssue(ctx, job) error`

1. Если `issue_number` не пуст или статус не `publishing` - выйти. Проверка
   статуса обязательна: без неё отменённое обращение всё равно уедет в GitHub.
2. `EnsureLabels`, если у проекта `labels_ready` ложно.
3. Собрать тело: шапка с ФИО автора и его ником, разделы контракта по
   заголовкам из правил, список пробелов при неполноте, маркер
   `<!-- intake:case:<uuid> -->` последней строкой.
4. `POST /repos/{owner}/{repo}/issues` с метками `type:<kind>`, `status:new`,
   `author:<slug>` и `incomplete` при неполноте.
5. При неизвестном исходе (таймаут, 5xx) перед повтором искать маркер поиском
   по репозиторию: защита от дубля при потерянном ответе на успешный запрос.
6. Записать `issue_number`, `issue_url`, статус `published`, событие
   `published`; поставить работу `notify`.
7. Удалить файлы обращения и обнулить `file_path`.

Шаг 7 переносит удаление медиа из M1 сюда: инвариант требует, чтобы файл жил до
подтверждения саммари. В M1 файлы стираются сразу после нормализации, потому
что интервью в срезе нет; здесь удаление переезжает в конец.

### `CancelCase`: что меняется

Функция из M1 гасит только работы нормализации. Добавляются `interview` и
`summarize`: отменённое обращение не должно получить вопрос следующего раунда.
Работа `publish` не гасится, потому что отмена из `publishing` запрещена
вовсе - к этому моменту автор уже подтвердил публикацию.

### `EnsureLabels(ctx, project) error`

Создаёт недостающие метки проекта через `POST /repos/{owner}/{repo}/labels`,
ставит `labels_ready`. Существующая метка возвращает 422 и это не ошибка.
Автосоздание меток при создании issue документацией не обещано, поэтому шаг
явный.

### `RemindDrafts(ctx) error`

Идёт тем же часовым тикером, что и `SweepDrafts`, и перед ней: обращение в
`collecting`, `interview` или `summary`, к которому не прикасались сутки и у
которого `reminded_at` пуст, получает одно напоминание и отметку времени.
Повторных напоминаний нет. Отдельная работа `remind` в очереди не нужна - тикер
уже есть, а само сообщение всё равно уходит работой `notify`.

Уборка файлов расширяется теми же тремя статусами. В M1 она смотрит только на
`collecting`, потому что дальше файлов не было; с переносом удаления в
`PublishIssue` брошенное обращение в `summary` держало бы медиа на диске
бессрочно. Заодно срок считается от `updated_at`, а не от `created_at`: разговор
идёт часами, и время создания перестало быть признаком заброшенности.

## 8. Контракты LLM и промты

Схемы `InterviewTurn` и `Summary` - раздел 7 архитектуры, здесь только проверки
Go, потому что вывод модели недоверенный:

| Проверка | При нарушении |
| --- | --- |
| вопросов не больше трёх | повтор запроса |
| каждый `key` вопроса есть в `gaps` | повтор запроса |
| все ключи принадлежат контракту типа | повтор запроса |
| `ready` истинно только при пустом `gaps` | повтор запроса |
| обязательные пункты закрыты либо перечислены в `gaps` | повтор запроса |
| заголовок саммари непустой и не длиннее 80 символов | повтор запроса |

Второе нарушение подряд возвращает ошибку работы, и дальше решает очередь: повод
может быть и временным (сбой провайдера), а её повторы это уже умеют. Исчерпав
попытки, работа уходит в `failed`, автор получает понятный ответ, обращение
остаётся живым - следующий ответ автора ставит новый ход, и разговор
продолжается с того же места.

**Промты.** `prompts/interview.md` и `prompts/summary.md`. Порядок сообщений
фиксирован и обязателен: system с методом, контрактом и контекстом проекта -
кэшируемый префикс без единой изменяющейся строки; user с протоколом сырья;
следом история раундов.

Метод интервью берётся из промта брифовщика внутренней базы знаний: разбор
конкретного случая, детектор выдумки, замок пересказа «где я ошибся», признак
тянет вопрос. Промт бота самостоятельный, а не копия: другой жанр и бюджет в
три раунда против часа разговора.

## 9. Логи

Добавляются к полям M1: `interview_round` (номер раунда, число вопросов, число
пробелов), `summary_ready`, `issue_created` (номер), `labels_created`. Ни один
лог не содержит текста вопросов, ответов и тела issue - правило M0 не меняется.

## 10. Критерий приёмки

1. `make ci-check` проходит локально и в CI.
2. Обращение с голосовым «бот не ставит задачу в CRM» без деталей получает
   раунд из 2-3 вопросов, каждый с предполагаемым ответом, а не тикет.
3. Кнопка «Всё так» принимает раунд целиком, следующий раунд не переспрашивает
   закрытое.
4. Ответ голосовым принимается наравне с текстом.
5. Саммари показывается по разделам контракта, кнопка «Поправить» возвращает в
   интервью, правка попадает в итоговый текст.
6. После «Публикую» в GitHub появляется issue: в шапке ФИО автора и ник, разделы
   по заголовкам контракта, метки `type`, `status:new`, `author:<slug>`.
7. Обращение, упёршееся в предел раундов, даёт issue с меткой `incomplete` и
   явным списком пробелов в теле, а не отказ.
8. Каталог обращения на диске пуст только после публикации, `tg_file_id` в базе
   остался.
9. Обрыв GitHub не теряет обращение: работа уходит в повторы, после
   восстановления issue создаётся ровно один, дубля нет. Отмена обращения в
   середине интервью останавливает вопросы, а не приводит к тикету.
10. Правка `rules/contract.yaml` меняет состав вопросов и разделов issue без
    миграции и без правки кода.

Пункты 2-9 требуют живого прогона в dev-контуре и `OPENROUTER_API_KEY` там же.

## 11. Тестовый сценарий

| Тест | Что подаём | Что ожидаем |
| --- | --- | --- |
| `TestLoadContract` | файл правил без обязательных пунктов у типа | ошибка загрузки, а не молчаливый пропуск |
| `TestInterviewValidate` | ход модели с четырьмя вопросами; с ключом вне контракта; с `ready` при непустых `gaps` | каждый отклонён |
| `TestAllTrueApplies` | раунд из трёх вопросов и нажатие «Всё так» | все три `suggested` записаны, `gaps` пуст |
| `TestRoundLimitPublishesIncomplete` | обращение с незакрытыми пунктами и исчерпанным пределом | переход в `summary`, `incomplete` истинно, пробелы перечислены |
| `TestPublishIsIdempotent` | работа `publish` дважды на одном обращении и она же на отменённом | оба лишних запуска выходят сразу, issue один |
| `TestAnswerReachesInterview` | текст автора при статусе `interview` | попадает в `ApplyAnswers`, а не получает «сбор закрыт» |
| `TestScrubContacts` | саммари с телефоном и email | в теле их нет, остальной текст цел |

Тесты с базой берут DSN из `TEST_DATABASE_URL` и пропускаются без неё - правило
M0. Запросов к OpenRouter и GitHub в тестах нет: клиенты проверяются живым
прогоном, мок проверял бы сам себя.

## 12. Долги, закрываемые здесь

- **Удаление медиа переезжает в `PublishIssue`.** В M1 файлы стираются после
  нормализации; инвариант требует, чтобы они жили до подтверждения автором.
- **Тест на побайтовое равенство префикса.** В M1 префикс это константа из
  `embed`, и проверять нечего. В M2 диалог многоходовый, и инвариант из таблицы
  архитектуры наконец получает тест.
- **`GITHUB_TOKEN` в Compose.** Переменная доводится до контейнера и
  проверяется при старте.

## 13. Что останется незакрытым

- Просмотр тикетов, статусы через метки, уведомления, комментарии, отмена после
  публикации - M4.
- Проверка дублей и лимиты - M5.
- Перечень работ обращения записан строкой в двух SQL (`FinishCollect` и
  `CancelCase`). M2 добавляет три вида работ; если перечень понадобится в
  третьем месте, он сводится в одну константу тем же коммитом.
- Golden-набор из реальных обращений: качество интервью проверяется руками до
  его сбора.
