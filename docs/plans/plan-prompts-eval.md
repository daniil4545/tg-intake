## 4. Данные и состояния

Сопоставимость базы (старый контракт, код до среза 2) и замера:
- M1, M2, M4 считаются по числу вопросов в `round_asked` и от контракта не зависят. Раунды
  обоих - `evalRounds = 2`, модель и reasoning сверяет `sameSetup`.
- M3 базы - `cases.incomplete` старого кода, то есть `Missing` по `case`, `expected`,
  `actual`. По Р-14 ядро `case`, `wrong` открыто, если `case` пуст или `expected`/`actual` в
  `gaps`. Старый `checkTurn` требовал каждый пустой обязательный ключ в `gaps`, а ключ из
  `gaps` снимался из `filled`: условия совпадают, карта Р-14 к базе применяется тождественно.
- Ломается знаменатель M3: в базе нет `mixed`, в замере часть бывших `bug` и `feature` станет
  `mixed` с ядром из четырёх пунктов. Порог по M3 - как в Р-9 (`bug`+`mixed`), без поправок:
  это строже к замеру, `pass` честный. Справка: M3 по `bug` и `mixed` отдельно и M3 на
  пересечении - ID с типом `bug` в базе и `bug`/`mixed` в замере (тип - большинство по
  прогонам), доля закрытого ядра по всем прогонам этих ID. Матрицы переходов типов нет.
- Попытки: шаг повторяется до `maxAttempts = 5` (`evalStep`). `Attempts` - сумма попыток шагов
  обращения; у базы без поля колонка `-`.

Цикл итераций (Р-9: не больше трёх):
- Итерация: правка `interview.md` - коммит в `feature/ticket-form`, затем
  `make eval-compare EVAL_RUNS=1 EVAL_OUT=iterN`. Разбор и откат - через git; вопросы
  последнего прогона - в локальной БД: `SELECT payload->'questions' FROM case_events
  WHERE kind='round_asked'`.
- Код выхода итерации всегда не 0 (прогонов 1 из 3); годность читается по строкам `ok`/`miss`.
  Итерация взяла порог, если все строки `ok` и запас M1 над порогом не меньше разброса M1
  базы (max-min по трём прогонам): иначе `ok` на одном прогоне - шум.
- Итерация взяла порог - финальный замер. После третьей - финальный замер лучшей: больше
  `ok`, при равенстве выше M1; она возвращается в `interview.md` коммитом. Финал один:
  `make eval-compare` (3 прогона, `EVAL_OUT=after`). Итого до 6 прогонов.
- Финал не взял порог - срез закрывается с таблицей в журнале, решение на гейте B (Р-9).
- Прогон, упавший не по промту (сеть, лимиты), повторяется не больше 2 раз на итерацию или
  финал, дальше - блокер в журнал. `EVAL_PARALLEL` - 6 по умолчанию: на 12 было 19
  таймаутов. Стоимость прогона снимается по базе и пишется в журнал среза.

## 5. Кодовая модель

```go
const evalBaseRuns = 3 // прогонов базы и финала (Р-9)

type caseRun struct {
    // ... поля среза 1
    Attempts int `json:"attempts,omitempty"` // сумма попыток шагов обращения
}

// compareRuns - таблица база/замер и вердикт по Р-9; reasons пуст - pass.
func compareRuns(base, after evalResult) (table string, reasons []string)
// sameSetup - модель, reasoning, раунды и ID обращений первого прогона совпадают.
func sameSetup(base evalResult, model, reasoning string, rounds int, ids []string) error
```

`compareRuns` получает уже годную базу: `runsValid` (прогонов `evalBaseRuns` и в каждом
`Failed <= evalFailLimit*(Cases+Failed)`) проверяется в `eval_test.go` до хода модели, причина
`base broken` - там же.
- Порог на `Mean.Metrics` (допуск 1e-9): M1 >= база + 0.10; M2 <= база + 0.10; M3 >= база -
  0.05; M4 < база; доля `failed` (`Failed/(Cases+Failed)`) не больше доли базы + 0.05, иначе
  причина `failed: X vs base Y` - обе стороны в `evalFailLimit` порознь ещё не значит близко
  друг к другу; у замера `evalBaseRuns` прогонов, иначе причина `runs N of 3`. `Bugs = 0`
  в базе или замере - причина `M3: no bug cases`.
- Таблица: строка на метрику и на долю `failed` - база (среднее и min-max), замер, разница,
  правило, `ok`/`miss`.
  Ниже справка без влияния на вердикт: по типам M1-M4 со знаменателями (тип без базы - `-`),
  M3 на пересечении, среднее `Attempts` на обращение, ID, где база спрашивала, а замер молчит,
  ID, упавшие только в одной стороне.
- Вывод - `t.Log`, последняя строка `verdict: pass` или `verdict: fail: <причины>`.

Правки `interview.md`, итерация 1 (дальше - по разбору):
- «Что добирается внутри вопроса» становится «Уточнение `detail`»: адрес объекта, дословный
  образец, неразличимые роли (Р-3); незнакомое название и ручные шаги - частные случаи адреса
  и ролей. Правило «дописывай к вопросу» снимается: оно для анкеты с шестью пунктами.
- `detail` - только когда без него работу не начать; ядро закрыто и объект назван - `ready`
  без вопросов. Это рычаг M1: `detail` при пустом `gaps` допустим (Р-3).
- «Признаки, которые тянут вопрос»: остаются «нет примера» (`case`), «следствие без
  действия» (`wrong`), «решение вместо задачи» (`why`), «пересланное сообщение»; уходят
  исключения, признак готовности и частота - вопросы бывших необязательных пунктов (Р-7).
- «Как спрашивать»: снимается «частота нужна тоже»; предел три вопроса остаётся (схема).

- Команда: `make -C src ci-check DATABASE_URL=<лок> TEST_DATABASE_URL=<лок>`, затем

  База - аргументом make: `src/.env` перекрывает окружение. Ключ OpenRouter - из `src/.env`.

  цифрами. Таблица и вердикт - в журнал среза.
- Не автоматизируется: гейт B читает саммари 5 обращений из списка «база спрашивала, замер
  молчит» в БД финального прогона и сверяет `case`/`wrong` с протоколом; R3 «сделки один
  раз» - саммари обращения со сделкой 59767187, если оно в наборе.
