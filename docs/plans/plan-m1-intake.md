# План M1: приём и нормализация

Срез второй. Источник требований - [prd.md](../prd.md), технические решения -
[architecture.md](../architecture.md), предыдущий срез -
[plan-m0-skeleton.md](plan-m0-skeleton.md). Спека не спорит с PRD: расхождение
означает возврат к гейту A, а не правку на месте.

## 1. Что делаем и зачем

Второй вертикальный срез: от первого сообщения до собранного протокола сырья.
Автор накидывает пачку (текст, голос, скриншоты, ссылки, пересылки), жмёт
«Готово»; сервис транскрибирует голос, разбирает скриншоты с протоколом в
контексте, склеивает всё в один текст, показывает автору и удаляет файлы.

Срез доказывает цепочку «медиа - OpenRouter - структурированный вывод -
протокол» и очередь `jobs` целиком, не таща за собой интервью и публикацию.
Показ протокола автору - единственный способ принять срез без GitHub: он делает
результат нормализации наблюдаемым.

Границы среза:

| Входит | Не входит |
| --- | --- |
| Меню проекта и сбор сырья в любом порядке | Интервью, добивание вопросами |
| Сбор пачки, кнопки «Готово» и «Отмена» | Саммари и подтверждение автором |
| Воркер очереди `jobs`, ретраи, отсрочка | Просмотр тикетов, статусы, уведомления |
| Клиент OpenRouter, транскрибация голоса | Клиент GitHub и публикация issue |
| Разбор скриншотов по схеме, склейка протокола | Напоминание о брошенном черновике |
| Удаление файлов, уборка черновиков | Обезличивание как отдельный шаг (см. 8) |
| Повтор старта бота (долг M0) | Живость поллера в healthcheck (см. 13) |

Напоминание о черновике (`remind`, кейс 2 PRD) уезжает в M2: без публикации
черновик всё равно некуда довести, а ticker срез заводит и так - место для
`remind` останется готовым.

## 2. Структура файлов

Прибавка к M0 - шесть файлов, все в `internal/app`.

```text
src/internal/app/
├── bot.go          # + меню действий, приём сырья, «Готово», «Отмена»
├── case.go         # жизненный цикл обращения: старт, элементы, переходы
├── worker.go       # захват jobs, ретраи, ticker уборки
├── normalize.go    # шаги normalize_voice и normalize_images, склейка протокола
├── openrouter.go   # клиент: chat/completions, json_schema, ретраи
├── media.go        # скачивание, временный каталог, удаление
└── prompts/        # transcribe.md, screenshot.md
src/migrations/0003_intake.sql
```

`case.go` отделён от `bot.go`: Telegram (кнопки, тексты, маршрутизация) против
состояния обращения в БД. Иначе в M2 переход состояния не прочитать без чтения
клавиатур. Отдельного `queue.go` нет: захват работ - одна функция рядом с
единственным своим потребителем.

## 3. Конфиг

Прибавка к таблице M0.

| Поле | Переменная | Обязательна | Назначение |
| --- | --- | --- | --- |
| `OpenRouterKey` | `OPENROUTER_API_KEY` | да | ключ OpenRouter |
| `ModelMedia` | `OPENROUTER_MODEL_MEDIA` | нет, `google/gemini-3.1-flash-lite` | голос и скриншоты |
| `MediaDir` | `MEDIA_DIR` | нет, `/tmp/intake` | временные файлы обращения |
| `MaxItems` | `MAX_ITEMS` | нет, `30` | предел элементов в одном обращении |
| `AudioConvert` | `AUDIO_CONVERT` | нет, `auto` | `auto` или `always`, см. 10 |

`OPENROUTER_MODEL_DIALOG` в срезе не появляется: диалоговых шагов нет, а
переменная без потребителя - ложное требование к деплою.

`MEDIA_DIR` создаётся и проверяется на запись при старте: образ
`distroless/static:nonroot` работает от непривилегированного пользователя, и
упереться в права на первом голосовом хуже, чем не подняться вовсе. В
dev-Compose под каталог монтируется `tmpfs` - файлы живут минуты.

`MAX_ITEMS` - защита от пересылки переписки целиком; лимит на элементы, а не на
байты. Элемент сверх лимита не принимается, автор получает «уже 30 сообщений,
нажмите Готово» один раз, а не на каждое следующее; признак «уже сказали» -
событие `limit_reached` в журнале, потому что счётчик элементов после отказа не
растёт и сам по себе повтор не отличает.

`AUDIO_CONVERT` валидируется на старте наравне с `LOG_LEVEL` (M0): значение вне
`auto|always` - ошибка конфига, а не молчаливый фолбэк.

## 4. Схема данных

Миграция `0003_intake.sql`, обе стороны.

```sql
-- Up
ALTER TABLE cases      ALTER COLUMN project_id DROP NOT NULL,
                       ADD CONSTRAINT cases_project_before_work
                       CHECK (status = 'collecting' OR project_id IS NOT NULL);
ALTER TABLE case_items ADD COLUMN forwarded boolean NOT NULL DEFAULT false,
                       ADD COLUMN mime      text;

-- Down
ALTER TABLE case_items DROP COLUMN mime, DROP COLUMN forwarded;
ALTER TABLE cases      DROP CONSTRAINT cases_project_before_work;
UPDATE cases SET status = 'cancelled' WHERE project_id IS NULL;  -- иначе SET NOT NULL упадёт
ALTER TABLE cases      ALTER COLUMN project_id SET NOT NULL;
```

`project_id` становится необязательным: обращение рождается раньше, чем автор
выбрал проект (раздел 5). Пустой проект допустим только в `collecting`, и это
держит `CHECK`, а не проверка в Go: набор статусов зафиксирован архитектурой
целиком, M2 добавляет переходы, а не значения. Обращение, уехавшее в
`normalizing` без проекта, - это issue в неизвестном репозитории.

`Down` отменяет обращения без проекта: вернуть им `NOT NULL` нельзя. Осознанная
потеря черновиков лучше падающего отката.

`forwarded` - сообщение переслано, то есть это не слова автора. В протоколе
такой кусок помечается, иначе модель принимает пересланную жалобу за постановку
задачи автором и тянет из неё требования, которых автор не выдвигал.

`mime` решает два вопроса: скриншот это или файл неизвестного типа, и какой
`format` уходит в `input_audio` OpenRouter.

**Автор обращения - тот, кто пишет боту, независимо от источника пересылки.**
Решение владельца: переслал чужие сообщения - значит взял их на себя. Имя и ID
исходного отправителя (`forward_origin`) не сохраняются нигде: авторству они не
нужны, а перепиской с клиентом стали бы персональными данными.

Прочая схема из M0 не меняется: `case_items.kind` остаётся
`text|voice|photo|link`, скриншот-документ пишется как `photo`.

## 5. Поток и состояния

Поток сбора один. Различается только момент выбора проекта: до сырья или после.

```
/start -> меню проекта -> «Создать тикет» ---+
                                             |
любое сообщение без активного обращения -----+--> [collecting] --«Отмена»--> [cancelled]
   (сырьё принято, проект спрошен следом)         |
                                              «Готово»
                                                 v
                                           [normalizing]
                                                 |
                                  normalize_voice (по одному на голосовое)
                                                 |
                                           normalize_images
                                                 v
                                      протокол готов, файлы удалены
                                                 v
                                            [interview]  <- граница среза
```

**Своё сообщение и пересланное равнозначны:** пересылка попадает в те же
`case_items` и тот же протокол, отдельного «входа пересылкой» в коде нет.
Порядок «сырьё раньше проекта» нужен потому, что человек начинает с материала, а
не с репозитория; требовать сначала выбрать проект значит потерять первое
сообщение.

Правила этого порядка:

1. Сообщение пришло, активного обращения нет - завести `collecting` без
   проекта, принять элемент.
2. Проект спрашивается ровно один раз: при первом элементе обращения, у
   которого `project_id` пуст. Признак - счётчик элементов, а не флаг в памяти:
   пачка из десяти сообщений не должна давать десять одинаковых вопросов, а
   рестарт между сообщениями не должен давать одиннадцатый.
3. Автор может выбрать проект в любой момент до «Готово». Нажал «Готово» без
   проекта - бот повторяет вопрос и ждёт выбора, сырьё при этом на месте.
   Вместе с вопросом приходит и клавиатура сбора: инлайн-меню проекта своей
   разметкой её не пускает, поэтому это два сообщения, а не одно.
4. Автор потыкал меню, но не нажал «Создать тикет», и сразу написал в бота:
   обращение заводится без проекта, вопрос задаётся заново. Единственный
   источник истины по проекту - `cases.project_id`, а не последний экран.

**Апдейты обрабатываются последовательно** (`telebot.Settings{Synchronous:
true}`). По умолчанию telebot запускает каждый хендлер в своей горутине
(`update.go:421-432`): пачка из десяти пересылок даёт десять параллельных
хендлеров над одним обращением, двойную вставку `cases` с падением на уникальном
индексе, случайный порядок элементов в протоколе и повторный вопрос о проекте.
Одна строка конфигурации снимает весь класс этих гонок. Цена - медленный хендлер
(скачивание до 20 МБ) задерживает следующие апдейты; при единицах обращений в
день это дешевле любой блокировки.

`interview` в M1 - конечная точка: бот показывает протокол и говорит, что
интервью появится в следующем срезе. Статус честный, новых значений в `CHECK` не
нужно, в M2 на этом месте появляется работа `interview`.

Активное обращение у автора одно (частичный уникальный индекс из M0). Автор,
нажавший «Создать тикет» при живом обращении, получает выбор: продолжить или
начать заново. «Начать заново» переводит старое в `cancelled` и заводит новое в
той же транзакции.

## 6. Приём сырья

Хендлеры: `OnText`, `OnVoice`, `OnPhoto`, `OnDocument`, `OnVideo` плюс
**`OnMedia` фолбэком**. Обращения в `collecting` нет - оно заводится тут же
(раздел 5), сырьё не теряется. Ответа на каждое сообщение нет: бот не
перебивает, кроме единственного вопроса о проекте.

`OnMedia` обязателен: не найдя ни специфичного хендлера, ни его, telebot молча
роняет апдейт (`update.go:387-419`), и аудиофайл, стикер, гифка или кружок
исчезают без единого слова - хуже отказа, потому что автор считает, что
отправил.

| Что пришло | Как записывается |
| --- | --- |
| текст | `kind=text`, `source_text` = текст |
| текст со ссылками | `kind=link`, если в тексте есть URL-сущность; сам текст сохраняется целиком |
| голосовое | `kind=voice`, `tg_file_id`, `mime` из `Voice.MIME`, файл скачивается |
| фото | `kind=photo`, берётся `Message.Photo` (Bot API отдаёт наибольший размер), подпись в `source_text` |
| документ с `mime_type` вида `image/*` | `kind=photo`: скриншот, отправленный файлом, - обычный случай, и терять его из-за способа отправки нельзя |
| документ другого типа, видео, кружок, аудиофайл, стикер, гифка | не принимается, бот отвечает «пришлите текстом, голосом или скриншотом» |
| пересланное сообщение | по типу содержимого, плюс `forwarded=true` |
| альбом скриншотов | каждое сообщение - свой элемент, `tg_group_id` = `Message.AlbumID` |

Пересылка определяется по `Message.Origin != nil`, а не по
`Message.IsForwarded()`: последний смотрит только на устаревшие
`forward_from` и `forward_from_chat` (`message.go:498-500`), которых нынешний
Bot API не заполняет, - флаг всегда оставался бы ложным. Сама библиотека в
диспетчере смотрит на `Origin` (`update.go:54`). Медиа внутри пересылки
скачивается как своё: `file_id` в апдейте наш. Сообщение из чата с запретом
пересылки до бота не дойдёт вовсе - ограничение Telegram, не сервиса.

Пометка `forwarded` не меняет ни авторства, ни хода интервью в M2: вопросы
задаются тому, кто прислал, а он отвечает сам либо переспрашивает источник и
возвращает ответ боту. Смысл пометки - модель должна знать, что деталь надо
уточнять, а не считать её сказанной автором лично.

Проверки при приёме: `file_size` из апдейта против 20 МБ (до запроса файла,
потолок Bot API), число элементов против `MAX_ITEMS`, скачивание в
`MEDIA_DIR/<case_id>/<item_id>`. Ошибка скачивания - элемент `failed` и «файл не
дошёл, пришлите иначе»; обращение не теряется.

Кнопка «Готово» - reply-клавиатура, появляется вместе с обращением: её видно
всегда, не надо искать инлайн-кнопку выше по переписке. Рядом «Отмена». Обе
дублируются командами `/done` и `/cancel`.

## 7. Функции

```
StartCase(ctx, tgUser, projectSlug) (*Case, bool, error)
  вход: профиль Telegram; slug проекта либо пусто (вход пересылкой)
  1. upsert users (M0)
  2. есть активное обращение - вернуть его с признаком «уже есть»
  3. insert cases (collecting, project_id из slug либо NULL),
     событие case_started
  выход: обращение, готовое принимать сырьё
```

```
SetProject(ctx, case, projectSlug) error
  1. статус не collecting - «проект уже не поменять», выйти
  2. неизвестный или неактивный slug - warn и просьба выбрать заново
  3. записать project_id, событие project_set
  назначение: вход пересылкой заводит обращение без проекта; выбор приходит
  вторым шагом и может опоздать относительно нескольких сообщений пачки
```

```
CollectItem(ctx, case, msg) error
  вход: обращение и сообщение Telegram
  1. статус не collecting - подсказать «сбор закрыт», выйти
  2. определить kind по содержимому; неподдерживаемое - ответ и выход
  3. элементов уже MAX_ITEMS - не принимать, ответить «нажмите Готово», выход
  4. для voice и photo: file_size против 20 МБ, FileByID + Download в
     MEDIA_DIR/<case_id>/, записать file_path, tg_file_id, mime
  5. insert case_items (status=pending, forwarded из msg.Origin != nil)
  6. проект пуст и это первый элемент обращения - задать вопрос о проекте
  выход: элемент в очереди на нормализацию, ответа автору нет
```

```
CancelCase(ctx, case, reason) error
  вход: обращение и причина (кнопка автора либо «начать заново»)
  1. статус терминальный - выйти, отменять нечего
  2. в одной транзакции: статус cancelled, событие case_cancelled,
     pending-работы этого обращения в failed с причиной
  3. DropFiles: файлы отменённого обращения не ждут часового сборщика
  выход: слот активного обращения свободен, медиа удалено
  назначение: «Отмена», /cancel и «начать заново» - один путь, а не три
```

```
FinishCollect(ctx, case) error
  1. статус не collecting - выйти: повторное «Готово» не должно ставить
     работы второй раз
  2. элементов нет - «пока нечего разбирать», статус не меняется
  3. проекта нет - повторить вопрос о проекте, статус не меняется
  4. в одной транзакции: статус normalizing, событие collect_finished,
     job normalize_voice на каждый pending-элемент kind=voice
  5. голосовых нет - сразу job normalize_images
  выход: цепочка запущена, автору «разбираю, это займёт полминуты»
```

Шаг 5 отличается от псевдокода в architecture.md, где при отсутствии фото
ставится сразу `interview`: протокол строит именно `normalize_images`, и без
этого шага текстовое обращение осталось бы с пустым `cases.protocol`.
Расхождение зафиксировано в architecture.md тем же коммитом.

Ключи работ детерминированы, иначе `jobs.key UNIQUE` либо не даст поставить
второе голосовое, либо пропустит дубль: `normalize_voice:<case_id>:<item_id>`,
`normalize_images:<case_id>`. Постановка - `ON CONFLICT (key) DO NOTHING`:
повторная постановка той же работы это не ошибка транзакции, а признак, что она
уже стоит.

```
RunNormalizeVoice(ctx, job) error
  1. прочитать файл; AUDIO_CONVERT=always - прогнать через ffmpeg в mp3
     (после конвертации format в запросе тоже mp3, а не исходный ogg)
  2. запрос к медиа-модели: input_audio (base64, format из mime) плюс
     промт transcribe.md - дословный транскрипт на русском, без пересказа
  3. пустой транскрипт - элемент failed с причиной «речь не распознана»:
     PRD требует сказать об этом прямо, а не отдать пустоту дальше
  4. записать normalized, статус элемента done
  5. если voice в статусе pending не осталось - job normalize_images
  выход: транскрипт в case_items.normalized
```

**Провал элемента не имеет права остановить цепочку.** Шаг 5 смотрит на
`case_items.status`, поэтому элемент, чья работа исчерпала повторы, переводится
в `failed` тем же кодом, который гасит работу (см. `RunWorker`). Иначе одно
битое голосовое держит обращение в `normalizing` навсегда, занимая единственный
слот, и автор не заведёт даже новое.

```
BuildProtocol(ctx, case) string
  вход: элементы обращения в порядке создания
  1. текст - как есть; голос - транскрипт; ссылка - URL строкой
  2. пересланное помечается «переслано (не слова автора)»
  3. элементы failed попадают строкой «не удалось разобрать: <причина>»:
     модель должна видеть пробел, а не достраивать его сама
  4. неразобранные скриншоты в первый протокол не попадают - их дописывает
     RunNormalizeImages, который этот протокол и строит
  выход: один текст, вход медиа-модели на скриншотах и диалоговой в M2
```

```
RunNormalizeImages(ctx, job) error
  1. записать cases.protocol = BuildProtocol
  2. по каждому photo-элементу: запрос к медиа-модели с изображением
     (data:<mime>;base64) и протоколом в контексте, схема ScreenshotExtract
  3. валидация Go: unreadable присутствует (пустой список допустим,
     отсутствие поля - нет); facts или unreadable непусты
  4. невалидный ответ - один повтор, второй раз - элемент failed
  5. дописать разбор в protocol, элементы done
  6. протокол пуст целиком (всё сырьё провалилось) - вернуть обращение в
     collecting, автору «ничего не удалось разобрать, пришлите иначе»;
     это переход из машины состояний architecture.md, а не новый исход
  7. иначе статус обращения interview, DropFiles, событие normalized,
     job notify с готовым протоколом
  выход: протокол с разбором скриншотов, файлов на диске нет
```

```
DropFiles(ctx, case) error
  удалить MEDIA_DIR/<case_id> целиком, обнулить file_path у элементов
  тем же запросом: путь в БД, указывающий на стёртый файл, - ловушка для
  следующего шага, который решит, что файл ещё есть
  вызывается: по завершении нормализации, при отмене, при уборке черновиков
  примечание: в M1 удаление стоит сразу после нормализации - дальше файл в этом
  срезе никому не нужен. В M2 вызов переезжает в PublishIssue: до подтверждения
  саммари файл обязан существовать (инвариант «медиа до подтверждения»)
```

```
SweepDrafts(ctx) error   -- раз в час из ticker
  обращения в collecting старше суток: DropFiles, лог files_dropped
  статус не трогаем: черновик остаётся, автор вернётся к тексту, но не к
  файлам - это цена инварианта «медиа не переживает обращение»
  берём только collecting: нормализуемое обращение держит файлы открытыми,
  и выдёргивать их из-под воркера нельзя
```

```
ClaimJobs(ctx, limit) ([]Job, error)  -- запрос из architecture.md, раздел 9
RunWorker(ctx)
  два обработчика (константа, не конфиг: столько же заложено в MaxConns пула
  в M0), каждый: захват, выполнение по kind, done либо retry
  retry: run_after = now() + 2^attempts секунд, attempts > 5 - работа failed
  исход провала, единой функцией на все шаги нормализации:
    1. элемент, к которому привязана работа, тоже failed с причиной
    2. цепочка двигается дальше: провал голосового не отменяет разбор
       скриншотов, провал скриншота не отменяет протокол
    3. проваленный normalize_images возвращает обращение в collecting -
       иначе слот активного обращения занят навсегда
    4. автору «не смог обработать, пришлите иначе», лог job_failed
  ticker: раз в минуту освобождает локи старше пяти минут
```

```
Complete(ctx, req) (json.RawMessage, error)   -- openrouter.go

  1. POST /api/v1/chat/completions, response_format json_schema,

  2. таймаут 60 секунд; 429 и 5xx - три повтора с экспонентой; 4xx - без
  3. вернуть content первого choice, распарсить в схему вызывающего
```

## 8. Промты и схема

`prompts/transcribe.md` - дословный транскрипт на русском, не пересказ, не
резюме; неразборчивое помечать `[неразборчиво]`, не достраивать. Единственное
исключение из дословности - персональные данные клиента: ФИО, телефон, адрес
заменяются на `[клиент]`, `[телефон]`, `[адрес]`. Дословность нужна для
разбора жалобы, а не для сохранения чужих контактов, и правило одно с
экстрактором скриншотов.

`prompts/screenshot.md` - разбор скриншота с протоколом сырья в контексте,
схема из раздела 7 [architecture.md](../architecture.md):

```json
{"screen": "...", "facts": [{"label": "...", "value": "..."}],
 "relevant": "...", "unreadable": ["..."]}
```

Оба промта - файлы, а не строки в коде: это блок «Изменяемое», их правка не
должна требовать чтения Go.

Персональные данные клиента в промте: экстрактор не выписывает ФИО, телефоны и
содержимое переписки, но выписывает идентификаторы карточек, статусы, даты и
суммы. Обезличивание отдельным шагом в срез не входит - последняя точка перед
публикацией это саммари, а его нет до M2; промт пишется так, чтобы тогда ничего
не переделывать.

## 9. Логи

Прибавка к событиям M0, имена буквально: `case_started`, `item_collected`
(kind, forwarded), `item_rejected` (причина), `limit_reached`,
`case_reopened`, `collect_finished` (items),
`job_claimed` (kind, attempt), `job_done` (kind, ms), `job_failed` (kind,
attempts, error), `llm_call` (step, model, ms, tokens_in, tokens_out),
`normalized` (case_id, items, chars), `files_dropped` (case_id, files),
`case_cancelled`.

Ни транскриптов, ни текстов сообщений, ни разбора скриншотов, ни имён: человек
в логе - `user_id`, содержимое - только длина в символах.

## 10. Проверка ogg/opus - первый шаг реализации

Открытый вопрос из PRD и архитектуры: принимает ли `gemini-3.1-flash-lite`
через OpenRouter голосовое Telegram (OGG/OPUS) без конвертации. Проверяется
живым запросом с реальным голосовым до написания `normalize.go`; результат
дописывается сюда фактом с датой.

- Принимает: `AUDIO_CONVERT=auto` остаётся дефолтом, ffmpeg в образ не идёт.
- Не принимает: статический ffmpeg отдельным слоем (плюс примерно 80 МБ к
  `distroless/static`), дефолт становится `always`.

Узнав ответ после написания шага, переделывать пришлось бы и шаг, и образ, и
деплой - поэтому проверка идёт первой.

## 11. Критерий приёмки

1. `make ci-check` проходит локально и в CI.
2. Автор выбирает проект, жмёт «Создать тикет», отправляет текст, голосовое и
   два скриншота, жмёт «Готово» - получает протокол, в котором есть смысл
   голосового и то, что вычитано со скриншотов.
3. Пересылка чужой пачки без выбора проекта заранее: сырьё принято целиком и в
   порядке отправки, проект спрошен ровно один раз, `forwarded` проставлен, в
   протоколе есть пометка. Полный живой прогон не дублируется: путь тот же, что
   в пункте 2, проверяются признак и порядок.
4. Скриншот, отправленный документом, разбирается наравне с фото.
5. После разбора каталог обращения на диске пуст, `file_path` обнулён,
   `tg_file_id` в базе остался.
6. Вложение тяжелее 20 МБ, видео и стикер получают понятный отказ, обращение
   живо; ни одно сообщение не остаётся без ответа бота.
7. Обрыв OpenRouter (неверный ключ в dev) не теряет обращение: работа уходит в
   повторы, после предела автор получает «не смог обработать», а обращение
   возвращается в сбор, а не виснет.
8. Рестарт сервиса в середине нормализации не теряет обращение: после подъёма
   цепочка доходит до протокола.
9. «Отмена» освобождает слот и стирает файлы: следующее «Создать тикет»
   заводит новое обращение, каталога прошлого нет.
10. В логе есть `llm_call`, `normalized`, `files_dropped`; нет ни одного
    транскрипта, имени и текста сообщения.

## 13. Долги M0, закрываемые здесь

- **Повтор старта бота.** Один неудачный `getMe` роняет процесс; егресс к
  Telegram с этого VPS нестабилен даже с закреплённым DC. `NewBot` получает
  пять попыток с отсрочкой 1-2-4-8-16 секунд, после чего падение остаётся
  падением.
- **Живость поллера в healthcheck закрыть не удаётся.** Мерить время последнего
  апдейта нельзя: у бота с единицами обращений в день молчание - норма. Сам цикл
  опроса ненаблюдаем: `LongPoller.Poll` отдаёт только непустые ответы, ошибку
  гасит внутри (`poller.go:69-88`), а `getUpdates` неэкспортирован, так что и
  свой поллер его не позовёт. Долг остаётся долгом; от зависшего поллера сейчас
  защищают `restart: unless-stopped` и повтор старта выше.
