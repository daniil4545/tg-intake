# Спека M4: подключение проектов

Дата: 2026-08-08. Вторая тема среза M4, вынесена отдельным документом: к
просмотру тикетов она не относится, а вместе они перерастают лимит спеки.
Основной документ среза - [plan-m4-lifecycle.md](plan-m4-lifecycle.md).

## 1. Что делаем и зачем

Мультипроектность работает с M0: проект - строка в `projects`, меню строится из
неё, добавление не требует выката кода. Но завести эту строку сегодня нечем, и
в базе живёт ровно один проект - сам бот. Сервис показывает сотрудникам самого
себя, а тикеты по реальным сервисам заводить некуда.

M4 даёт способ: список проектов задаётся переменной окружения контура, старт
приводит таблицу к нему.

## 2. Границы

**Входит.** Переменная `PROJECTS`, её разбор при старте, синхронизация таблицы,
пример в `.env.example`.

**Не входит.** Управление проектами из бота, роль владельца, удаление проектов.

## 3. Решение: почему переменная окружения

Три пути отпадают, и каждый по своей причине.

**Миграция с `INSERT`** - репозиторий публичный, а имена и адреса внутренних
сервисов туда попадать не должны. Это оговорено ещё в seed `0002`.

**Прямой `psql` на сервере** - `deploy/safe-ssh.sh` весь read-only, и заводить
ради вставки привычку ходить на сервер руками значит терять единственный
инструмент диагностики, которому можно доверять.

**Команда в боте** - потребовала бы роли владельца, которой в модели доступа
нет: все в белом списке равны, и вводить иерархию ради трёх строк дорого.

Остаётся переменная окружения: она уже приватна, уже правится владельцем в
Coolify и не стоит ничего, кроме разбора.

Инвариант «добавление проекта не требует деплоя» уточняется: не требует выката
кода. Правка переменной и рестарт контейнера - требует, и это честная цена за
то, что список внутренних сервисов не лежит в публичном git.

## 4. Конфиг: `PROJECTS`

Одна переменная, JSON-массив. Пустая или отсутствующая означает «таблицу не
трогать»: локальный запуск живёт на seed, и пустое значение не должно молча
опустошать меню.

```json
[
  {"slug": "tg-intake", "title": "Предложка (сам бот)",
   "owner": "daniil4545", "repo": "tg-intake",
   "context": "Telegram-бот приёма обращений: доводит сырой фидбек интервью до готового описания и заводит тикет."},
  {"slug": "…", "title": "…", "owner": "…", "repo": "…", "context": "…", "active": false}
]
```

| Поле | Обязательно | Назначение |
| --- | --- | --- |
| `slug` | да | ключ синхронизации и значение в `callback_data`, маска `^[a-z0-9-]{1,32}$` как в схеме |
| `title` | да | что видно в меню |
| `owner`, `repo` | да | куда публикуются тикеты |
| `context` | да | абзац «чем занят проект», уезжает в кэшируемый префикс промта и определяет, насколько осмысленные вопросы задаст интервью |
| `active` | нет, по умолчанию `true` | `false` убирает проект из меню, сохраняя историю тикетов |

Разбор идёт в `LoadConfig` вместе с остальными переменными и копит проблемы в
общий список: битый JSON, пустое обязательное поле, slug не по маске, дубль
slug. Битый список роняет старт - узнать об этом в логе выката лучше, чем
пустым меню в момент, когда автор нажал `/start`.

## 5. Функции

### `ParseProjects(raw string) ([]ProjectConfig, error)`

Живёт в `config.go` рядом с `parseIDs`: тот же жанр, тот же способ сообщать о
проблеме. Пустая строка даёт пустой список без ошибки. Проверяет маску `slug`,
непустые `title`, `owner`, `repo`, `context` и отсутствие дублей `slug`.

### `SyncProjects(ctx, pool, list []ProjectConfig) error`

Живёт в `db.go` рядом с `ListProjects` и `MarkLabelsReady`: владелец таблицы
проектов - этот файл. Пустой список - выход без единого запроса.

Каждая запись идёт `INSERT ... ON CONFLICT (slug) DO UPDATE` по полям `title`,
`github_owner`, `github_repo`, `context`, `active`, `updated_at`. Проекты, не
перечисленные в списке, не трогаются: убрать проект из меню значит поставить
ему `"active": false`, а не забыть строку. Молчаливая деактивация
неперечисленного превратила бы опечатку в исчезнувший проект.

`labels_ready` синхронизация не трогает: `PrepareProject` на старте отрабатывает
по всем активным проектам независимо от флага, и метки в новом репозитории
заведутся сами.

Логи: `projects_synced` с числом записей и `project_added` на каждый новый slug -
появление проекта в меню должно быть видно в логе выката.

## 6. Правки существующего кода

| Файл | Правка |
| --- | --- |
| `config.go` | `ProjectConfig`, `ParseProjects`, поле `Projects` в `Config` |
| `db.go` | `SyncProjects` |
| `main.go` | вызов `SyncProjects` строго до `checkGitHub`: тот заводит метки по активным проектам, и новый проект должен появиться в таблице раньше, иначе метки доедут только следующим стартом |
| `.env.example` | `PROJECTS` с примером и предупреждением, что реальные проекты в git не коммитятся |

Схема не меняется: в `projects` уже есть все нужные поля.

## 7. Критерий приёмки

1. В `PROJECTS` добавлен второй проект: после рестарта он виден в меню, метки
   заведены в его репозитории, тикет по нему уходит именно туда.
2. Проект с `"active": false` исчезает из меню, его тикеты остаются в базе.
3. Битый `PROJECTS` роняет старт с внятной ошибкой в логе.
4. Пустая переменная оставляет таблицу нетронутой: локальный запуск на seed
   работает как раньше.

## 8. Тестовый сценарий

| Тест | Что проверяет |
| --- | --- |
| `TestParseProjects` | пустая строка даёт пустой список; битый JSON, дубль slug и slug не по маске дают ошибку |
| `TestSyncProjects` | новый slug вставляется, существующий обновляется, неперечисленный не трогается, `active: false` убирает из `ListProjects` |

## 9. Отклонения при реализации

`SyncProjects` получил параметром логгер: появление проекта в меню должно быть
видно в логе выката, а у функций `db.go` своего логгера нет.

## 10. Что останется незакрытым

**Токен под новые репозитории - на владельце.** Fine-grained PAT выдаётся на
конкретные репозитории: право на второй проект не следует из права на первый.
Пока токен не расширен, старт по новому проекту пишет `github_write_denied`, и
тикет туда уйти не сможет. Код здесь бессилен, это разовое действие руками.
