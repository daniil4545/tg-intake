# Спека: сверка черновика с состоянием проекта (issue #34, поглощает #32)

## 1. Что делаем и зачем

Бот заводит тикеты на уже сделанное. Из десяти обращений в `qualifier` с 14.08
четыре потребовали не работы, а разбора: дубль активного тикета, функция уже
работала, требование закрыл вчерашний релиз. Разбор каждого стоит захода
триажа - сверка с кодом, продом и бэклогом, комментарий автору, метки. Автор
обращения тоже теряет: он ждёт новой функции, а через несколько дней получает
«оно уже работает».

Причина в коде: интервью идёт только по репликам автора. Весь контекст проекта у
модели - абзац `projects.context`, сочинённый из README при подключении проекта.
Ни списка тикетов, ни `CHANGELOG.md`, ни архитектуры в промт не попадает.
Единственное обращение к issues на пути публикации - `FindIssue` по маркеру
`intake:case:<uuid>`: это защита от двойного POST, а не поиск похожих.

Срез добавляет один шаг: перед показом саммари сервис сверяет собранный черновик
с состоянием проекта и показывает автору найденные пересечения. Тикет всё равно
создаётся по решению автора, но уже с разделом «Пересечения» в теле -
разработчику не приходится восстанавливать этот контекст с нуля.

## 2. Как это выглядит для человека

1. Автор описывает пожелание, отвечает на вопросы интервью, доходит до саммари.
2. В карточке саммари после разделов появляется: «Похоже, часть этого уже есть:»
   и список - тикет с номером и заголовком либо документ со ссылкой, у каждого
   пункта строка о том, что именно совпало. Ниже: «Если это оно - нажмите
   «Сброс», тикет не понадобится. Если нет - напишите, чего не хватает.»
3. Кнопки прежние: «Публикую» и «Поправить».
4. Автор пишет правку - интервью продолжается, следующее саммари сверяется
   заново. Автор публикует - тикет уходит с разделом «Пересечения» в теле.
5. Ничего не нашлось, репозиторий недоступен, модель ответила мусором - карточка
   выглядит ровно как сегодня, публикация идёт своим ходом.

## 3. Границы среза

Не входит:

- Ветка «дополнить существующий тикет комментарием»: решение владельца - исход
  один, новый тикет с разделом «Пересечения». Метод POST комментария не заводим.
- Блокировка публикации при находке в любом виде.
- Сверка в режиме «Спросить»: он и так отвечает по документации.
- Обновление `projects.context` по мере жизни проекта - отдельная задача.
- Пересечение с исходным кодом: только тикеты и документы.

## 4. Решения среза

- **Сверка стоит между саммари и его показом.** Точка подтверждения остаётся
  одна - «Где я ошибся?». Второй экран после «Публикую» дёргал бы автора после
  того, как он уже согласился, и добавил бы состояние в машину. Цена решения:
  шаг саммари удлиняется на запросы к GitHub и один вызов модели, и сверка
  тратится в том числе на обращения, которые автор потом отменит.
- **Источники - тикеты и документы состояния.** Одних тикетов мало: из четырёх
  разобранных случаев один не пересекался ни с одним тикетом, только с
  работающим кодом, другой - с вышедшим накануне релизом. Читаем
  `CHANGELOG.md`, `README.md`, `docs/backlog.md`, `docs/architecture.md` -
  список фиксированный, отбора файлов моделью нет: это второй вызов модели и
  второй источник выдумки ради гибкости, которая здесь не нужна. Файла нет в
  репозитории - пропускаем молча.
- **Сверка не имеет права остановить обращение.** GitHub недоступен, модель
  вернула мусор, бюджет вышел - в лог warning, блок пустой, саммари уходит
  автору. Обратное поведение отняло бы у бизнеса единственный вход в разработку
  ради необязательной подсказки.
- **Адреса строит Go.** Модель называет номер тикета и путь файла из выданных ей
  списков; всё, чего в этих списках не было, отбрасывается. Ссылку собирает код -
  тот же инвариант, что у режима «Спросить» и раздела «Ссылки».
- **Хранится готовый markdown-список.** Обрамление разное: в чате вводная фраза
  и подсказка про «Сброс», в issue - заголовок раздела и строка о том, что автор
  список видел. Оба места берут один и тот же список, чат прогоняет его через
  `plainText`.
- **Вопрос автору пишет Go, а не модель.** Формулировка «чего не хватает» - часть
  разговора бота, а не вывод шага; отдавать её модели значит получить в тикете
  случайную реплику.

## 5. Изменения

### Новое: `src/internal/app/overlap.go`

```go
type Overlap struct { gh *GitHub; llm *OpenRouter; log *slog.Logger; model DialogModel }
func NewOverlap(gh *GitHub, llm *OpenRouter, log *slog.Logger, model DialogModel) *Overlap
func (o *Overlap) Check(ctx context.Context, cs *Case, p Project, title, brief, body string) string
```

`Check` возвращает markdown-список пунктов или пустую строку. Ошибку наружу не
отдаёт: любой сбой - warning в лог и пустой результат.

Шаги:

1. `gh.GetRepo` - ветка по умолчанию.
2. `gh.TreeDocs` - дерево md-файлов; из него берутся пути `overlapDocs` в
   порядке приоритета, каждый читается `gh.File` и режется `cutDoc`. Бюджеты:
   `overlapDocChars = 20000` на файл, `overlapAllChars = 60000` на все. Один
   `docs/architecture.md` в `intake` весит 47 КБ - без обреза он съел бы контекст.
3. `gh.ListIssues(ctx, p, overlapIssues)` - последние 50 тикетов, pull request'ы
   уже отсеяны внутри.
4. Один вызов модели: префикс `prompts/overlap.md` с картой документов, дальше
   волатильное - список тикетов, содержимое файлов, черновик последним.
5. `keepFound` - проверка вывода: номер обязан быть среди выданных тикетов, путь -
   среди прочитанных файлов; остальное отбрасывается со счётчиком в лог.
6. `overlapList` - рендер пунктов со ссылками.

Структура ответа модели:

```go
type overlapItem struct {
	Issue int    `json:"issue"` // 0, если пункт про документ
	Path  string `json:"path"`  // пусто, если пункт про тикет
	Note  string `json:"note"`  // что именно совпало, одна строка
}
type overlapOut struct {
	Found bool          `json:"found"`
	Items []overlapItem `json:"items"`
}
```

`Found` без пунктов ничего не значит: список строится по пунктам, прошедшим
проверку. Новый шаг логирования - `stepOverlap = "overlap"`.

### Правки

- `github.go`, структура `Issue`: добавить `Title` и `State` - сверке нужны
  заголовок для строки списка и признак «закрыт» для смысла совпадения.
- `github.go`, `(*Publisher).body`: раздел `## Пересечения` между «Ссылки» и
  «Не разобрано».
- `interview.go`, `Summarize`: после проверки саммари и до транзакции - вызов
  `Check`; результат идёт в `UPDATE`, в снимок события `summary_ready` и в
  карточку.
- `interview.go`, `summaryMessage`: блок с пересечениями перед строкой «Где я
  ошибся?».
- `case.go`: поле `Case.Overlap`, колонка в `caseColumns` и `scanCase`.
- `src/migrations/0010_overlap.sql`: `ALTER TABLE cases ADD COLUMN overlap text
  NOT NULL DEFAULT ''`.
- `prompts/overlap.md`: новый промпт с подстановкой `{{DOCMAP}}`.
- `cmd/intake/main.go`: клиент GitHub собирается до интервью, `NewInterview`
  получает `*Overlap`.

## 6. Критерий приёмки

- Обращение, повторяющее уже выпущенную функцию, доходит до саммари, и в карточке
  виден список пересечений со ссылками на тикет или документ.
- Автор публикует - в теле issue есть раздел «Пересечения» с теми же пунктами.
- Обращение без пересечений выглядит и публикуется как до среза.
- Недоступный репозиторий или сбой модели не мешают саммари и публикации; в логе
  виден warning со шагом сверки.
- Ни один пункт списка не ссылается на тикет или файл, которых сервис не читал.

## 7. Тестовый сценарий

Юнит-тесты (`overlap_test.go`, без сети, на подставленном выводе модели):

1. Придуманный номер тикета отбрасывается, реальный остаётся.
2. Придуманный путь файла отбрасывается, прочитанный остаётся.
3. Ни одного прошедшего пункта - пустая строка.
4. Список рендерится со ссылками, собранными Go, и заголовком тикета.

`github_test.go`: тело issue с непустым `Overlap` содержит раздел «Пересечения»
в нужном порядке относительно «Ссылок» и «Не разобрано».

Живой прогон против `daniil4545/qualifier`: повторить обращение из тикета #68
(«автологирование причин отказов в AmoCRM»). Ожидается пункт про релиз 0.4.2 или
закрытый тикет #57. Затем контрольное обращение на заведомо новую тему - блока
быть не должно. Затем прогон с чужим `owner/repo` - саммари без блока, warning в
логе, публикация проходит.

## 8. Известные ограничения

- Сверка видит последние 50 тикетов: пересечение со старым тикетом активного
  репозитория останется незамеченным.
- Набор документов фиксирован. Проект с другой раскладкой доков сверяется только
  по тикетам и README.
- Длинные документы читаются с начала до обреза. Для `CHANGELOG.md` это верный
  конец - свежие версии сверху; для архитектуры конец файла может не попасть.
- Шаг саммари становится дороже и дольше: два запроса к GitHub на документы плюс
  вызов модели с волатильным блоком до 60000 символов, который не кэшируется.
