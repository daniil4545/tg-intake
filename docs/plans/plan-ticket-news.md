# Спека: новости по тикету доходят до автора (M8, половина M9)

## 1. Что делаем и зачем

Ни у одного менеджера нет аккаунта GitHub. Всё, что происходит с тикетом после
публикации, живёт в issue: смена метки, комментарий с разбором, причина
отклонения. Сегодня бот показывает статус только тому, кто сам открыл список, и
последний комментарий - только у закрытых тикетов. Фонового опроса GitHub нет
вовсе, поэтому отклонение может пролежать незамеченным неделю (долг из
[plan-m4-lifecycle.md](plan-m4-lifecycle.md), раздел 8).

Срез замыкает функцию «смотреть движение тикета»: сервис сам замечает новость,
коротко зовёт автора и показывает суть в карточке. Обратный канал не открывается:
ответить комментарием из бота будет можно следующим срезом.

## 2. Как это выглядит для человека

1. Разработчик вешает на issue `status:in-progress`. В течение пяти минут автору
   приходит: «Тикет #65 (Qualifier): статус «В работе». Открыть - кнопкой ниже
   или в «Мои тикеты».» Под сообщением одна кнопка - «Открыть тикет #65».
2. Разработчик оставляет комментарий. Автору: «По тикету #65 (Qualifier)
   появился комментарий разработчика.» Текста комментария в уведомлении нет.
3. В списке тикетов проекта такой тикет помечен: `#65 (новое) - В работе -
   Заголовок`, и свои тикеты стоят выше чужих.
4. Автор открывает карточку: статус, заголовок, автор, краткое содержание,
   последний комментарий, ссылка. Отметка «новое» снимается. Полное описание
   открывается кнопкой «Подробнее».
5. Выкат в dev автору не приходит вовсе: статус он увидит, когда откроет список.

## 3. Границы среза

Не входит:

- Ответ автора комментарием в issue (вторая половина M9). Решение владельца на
  гейте: сначала удобный просмотр, обратный канал следующим срезом. Принято
  заранее: отвечать можно будет текстом и голосовым, скриншоты - отдельный
  вопрос.
- Приёмка результата кнопками «работает» и «не то» при выходе в прод.
- Метка «жду ответа автора» и напоминание о повисшем вопросе.
- Дайджест, отчёты, сроки и оценки: PRD этого не обещает.
- Тикеты, заведённые в репозитории руками: список по-прежнему строится из своей
  базы.

## 4. Решения среза

- **Уведомление минимальное.** Решение владельца: сыпать содержанием в чат
  нельзя, сообщение несёт факт новости и кнопку перехода. Текст комментария
  читается в карточке, где виден вместе со статусом и сутью тикета.
- **Будят только значимые события.** Прежний отказ от уведомлений (2026-08-09)
  опирался на «три статуса на десяток тикетов дадут тридцать сообщений». Отбор
  снимает довод, не отменяя функцию: будят `status:in-progress`, `status:prod`,
  `status:rejected` и новый комментарий. Признак живёт в
  `rules/statuses.json` - состав меняется без миграции и без выката.
- **Опрос тикером, а не работой очереди.** Наружу опрос ничего не меняет: он
  читает GitHub и ставит работу `notify` в транзакции - то же, что делает
  `RemindDrafts` из часового sweeper. Новый вид работы потребовал бы миграции
  `jobs_kind_check` и ничего не дал бы взамен.
- **Два запроса на проект за тик.** Метки берутся одним списком issue с
  сортировкой по времени изменения, комментарии - одним списком по репозиторию с
  границей `since`. Поштучный обход тикетов дал бы десятки запросов на тик; при
  тике пять минут и трёх проектах выходит 72 запроса в час против лимита 5000.
- **Инвариант «источник истины - метка» остаётся буквальным.** Новые колонки
  хранят не статус тикета, а факт доставки: «о какой метке автору уже сказали» и
  «какой комментарий уже доставлен». Всё, что показывается человеку,
  по-прежнему читается из GitHub в момент показа.
- **Первое наблюдение молчит.** `told_status IS NULL` значит «тикет ещё не
  видели»: тик записывает текущий статус без уведомления. Иначе выкат разослал
  бы пачку сообщений по всем старым тикетам разом.
- **Краткое содержание пишет модель при публикации и оно идёт в issue.** Решение
  владельца: одна формулировка на две стороны. В карточке бота оно заменяет
  полное описание, в теле тикета встаёт первым разделом - разработчик видит суть
  не читая весь тикет. Генерировать на лету при открытии карточки нельзя:
  просмотр ходит наружу синхронно и обязан отвечать за секунды.
- **Свои тикеты сверху.** Правило PRD «все видят все» сохраняется, но отметка о
  новостях имеет смысл только у своих тикетов, и своё должно быть видно первым.

## 5. Изменения

### Схема данных (миграция `0009_ticket_news.sql`)

`cases`:

| колонка | назначение |
| --- | --- |
| `told_status text` | метка статуса, о которой автору уже сказали. NULL - тикет ещё не наблюдали, первый тик пишет статус молча |
| `told_comment_id bigint NOT NULL DEFAULT 0` | id последнего доставленного комментария; отсекает уже отправленное при перекрытии окна опроса |
| `has_news boolean NOT NULL DEFAULT false` | о новости сказали, а карточку автор ещё не открыл. Держит отметку в списке |
| `brief text` | краткое содержание тикета. У тикетов до выката пустое |

`projects`:

| колонка | назначение |
| --- | --- |
| `comments_since timestamptz NOT NULL DEFAULT now()` | граница окна опроса комментариев. Дефолт `now()` отсекает прошлую переписку: выкат не рассылает историю |

Down снимает все пять колонок.

### Слежение: `internal/app/watch.go`

```go
type Watch struct {
    pool     *pgxpool.Pool
    gh       *GitHub
    statuses Statuses
    log      *slog.Logger
}

func NewWatch(pool *pgxpool.Pool, gh *GitHub, statuses Statuses, log *slog.Logger) *Watch
func (w *Watch) Run(ctx context.Context) error
```

`Run` - один тик. Алгоритм:

1. `ListProjects` - активные проекты. Отказ проекта логируется `watch_failed` и
   не останавливает остальные: недоступный репозиторий не должен глушить чужие
   новости.
2. По проекту прочитать свои тикеты одним запросом: `id, issue_number,
   told_status, told_comment_id` из `cases` где `project_id = $1 AND
   issue_number IS NOT NULL`. Индекс `cases_project_issue` уже есть.
3. `gh.ListUpdated(ctx, project, issueScan)` - сто последних изменённых issue с
   метками. Наш тикет, изменённый за пять минут, из этого окна вытесниться не
   может, поэтому добора поштучно нет.
4. Для каждого совпадения по номеру: `statuses.Pick(labels)`.
   - метка не распознана или совпадает с `told_status` - ничего;
   - `told_status IS NULL` - `UPDATE cases SET told_status = $2`, лог
     `ticket_status_seen`, уведомления нет;
   - иначе одна транзакция: `told_status = $2`, при `status.Notify` ещё
     `has_news = true` и `putNotifyKey(caseID, "status:"+label, statusNews(...),
     keysTicket)`. Лог `ticket_status_told`.
5. `gh.ListComments(ctx, project, project.CommentsSince)`. Комментарии по issue,
   которых нет в `cases`, отбрасываются (тикет заведён руками).
6. Для каждого с `id > told_comment_id`: транзакция `told_comment_id = $2,
   has_news = true` плюс `putNotifyKey(caseID, "comment:"+id,
   commentNews(...), keysTicket)`. Лог `ticket_comment_told`.
7. Успешный разбор обоих списков двигает `projects.comments_since` на время
   самого свежего рассмотренного комментария - в том числе по чужим тикетам,
   иначе они остались бы в окне навсегда и перечитывались бы каждый тик. Отказ
   GitHub границу не двигает: окно перекроется следующим тиком, а дубли ловят
   `told_comment_id` и ключ работы.
8. Лог тика: `watch_tick` с проектом, числом issue, числом комментариев и числом
   новостей.

Тексты (`watch.go`, рядом с кодом, который их ставит):

```
Тикет #65 (Qualifier): статус «В работе».
Открыть - кнопкой ниже или в «Мои тикеты».

По тикету #65 (Qualifier) появился комментарий разработчика.
Открыть - кнопкой ниже или в «Мои тикеты».
```

### GitHub: `internal/app/github.go`

- Внутренний `listIssues` получает параметр сортировки. `ListIssues` и
  `FindIssue` остаются на `sort=created`, новый
  `ListUpdated(ctx, project, limit) ([]Issue, error)` ходит с
  `sort=updated&direction=desc`. Разбор ответа один.
- `ListComments(ctx context.Context, p Project, since time.Time) ([]Comment, error)`:
  `GET /repos/{o}/{r}/issues/comments?since=<RFC3339>&per_page=100&sort=created&direction=asc`,
  листание до `githubCommentPages` страниц с логом усечения - как у
  `LastComment`.
- `type Comment struct { ID int64; Body, IssueURL string; CreatedAt time.Time }`
  плюс `issueNumber(url string) int` - номер из хвоста `issue_url`; невалидный
  адрес даёт 0 и комментарий отбрасывается.
- Оба вызова идут рабочим клиентом (20 секунд, три повтора): это фон, а не
  обработчик апдейта.
- `Publisher.body` кладёт `## Кратко` первым разделом после строки авторства,
  когда `cs.Brief` не пуст.

### Краткое содержание: `internal/app/interview.go`

- `summaryOut` и `summarySchema` получают `brief` (string, в `required`).
- `checkSummary` отклоняет `brief` длиннее `briefLimit = 400` символов: пересказ
  на пять абзацев вытеснил бы статус и комментарий за край экрана.
- `Summarize` пишет `brief` через `scrubContacts` тем же `UPDATE`, что `title`
  и `summary`; снимок ложится в событие `summary_ready` рядом с `title` и `body`.
- `summaryMessage` показывает `brief` строкой после заголовка: инвариант «тикет
  не публикуется без подтверждения автора» требует, чтобы автор видел то, что
  уйдёт в issue.
- `prompts/summary.md`: правило про `brief` в разделах «Как писать» и «Ответ» -
  одно-два предложения о сути словами автора, без решения и вводных, до 400
  символов. Порядок блоков промта не меняется, кэшируемый префикс цел.

### Статусы: `rules/statuses.json` и `statuses.go`

- Каждому статусу поле `notify`. `true` у `status:in-progress`, `status:prod`,
  `status:rejected`; `false` у `status:new`, `status:dev`, `status:cancelled` -
  о публикации и о своей отмене автору уже сказали.
- `Status` получает поле `Notify`, `parseStatuses` его читает. Отдельной
  проверки нет: отсутствие поля значит «не будит».

### Просмотр: `internal/app/tickets.go`

- `Ticket` получает `Brief string` и `News bool`.
- `List(ctx, project, userID)`: в выборку добавлены `brief` и `has_news`,
  порядок - `ORDER BY (user_id = $2) DESC, issue_number DESC LIMIT 10`. `News`
  ставится только владельцу тикета.
- `Load` читает последний комментарий всегда, а не только у финального статуса.
  Цена - один запрос быстрым клиентом на открытие карточки.
- `MarkSeen(ctx, caseID string, userID int64) error`:
  `UPDATE cases SET has_news = false WHERE id = $1 AND user_id = $2 AND has_news`.
  Автор проверяется условием запроса: чужое открытие чужую отметку не гасит.

### Бот: `internal/app/bot.go`, `case.go`

- Набор кнопок `keysTicket` рядом с `keysCancel`. В `Bot.Notify` ветка: проект
  загружается по `cs.ProjectID`, кнопка строится как
  `cardBtn` с `cardData(slug, cs.IssueNumber)`. Новых полей в `notifyPayload`
  нет - номер и проект лежат в обращении.
- `onTickets` передаёт `senderID(c)` в `List`, печатает перед первым чужим
  тикетом строку «Другие тикеты проекта:» и помечает новость словом, не
  символом: `#65 (новое) - В работе - Заголовок`, подпись кнопки - `#65 новое -
  В работе`.
- `onCard` зовёт `MarkSeen` после успешной загрузки и добавляет кнопку
  «Подробнее» (`fullBtn`, та же `cardData`), когда есть и `Brief`, и `Body`.
- `cardText` печатает `Brief` вместо `Body`; при пустом `Brief` - `Body`, как
  сейчас, и кнопки «Подробнее» нет.
- `onFull` - экран полного описания с кнопкой возврата к карточке.

### Процесс: `cmd/intake/main.go`

- Собрать `Watch`, поднять четвёртую горутину `watchTickets` с
  `watchPeriod = 5 * time.Minute` и бюджетом тика `watchBudget = 2 * time.Minute`
  по образцу `sweepDrafts`. Часовой sweeper не годится: пять минут против часа -
  разная природа.

### Логи

`watch_tick`, `ticket_status_seen`, `ticket_status_told`, `ticket_comment_told`,
`watch_failed`. Уже существующие `tickets_listed` и `ticket_opened` не меняются.

## 6. Критерий приёмки

1. Смена метки на будящую доходит до автора одним коротким сообщением с кнопкой
   перехода не позже пяти минут.
2. Новый комментарий разработчика доходит тем же путём и виден в карточке
   независимо от того, закрыт тикет или нет.
3. Незначимая смена статуса сообщения не порождает, но список показывает новый
   статус.
4. Повторный тик без изменений не создаёт ни одной работы `notify`.
5. Список показывает свои тикеты первыми и помечает те, где есть новость;
   открытие карточки отметку снимает.
6. Тело нового issue начинается разделом «Кратко», и тот же текст автор видел в
   подтверждении саммари.
7. Отказ GitHub в тике не роняет процесс, не двигает границу окна и виден в
   логе.

## 7. Тестовый сценарий

Автотесты (`make test`, локальная база на порту 5433):

1. Метка сменилась на будящую - ровно одна работа `notify` и `has_news = true`.
2. Повторный тик без изменений - работ нет.
3. Смена на `status:dev` - `told_status` обновлён, `has_news` остался false,
   работ нет.
4. `told_status IS NULL` - статус записан, работ нет.
5. Новый комментарий - работа с ключом `notify:<case>:comment:<id>`; повторный
   тик тот же комментарий не дублирует.
6. Комментарий по issue, которого нет в `cases`, игнорируется.
7. `List` отдаёт свои тикеты первыми, `News` стоит только у своих.
8. `MarkSeen` автора гасит отметку, вызов от чужого id - нет.
9. `checkSummary` отклоняет ответ без `brief` и с `brief` длиннее предела.
10. Миграция 0009 вверх и вниз на базе с существующими тикетами.

`make ci-check` перед PR.

Живой прогон после выката `v0.1.11`:

1. Завести тикет ботом: в подтверждении саммари видно краткое содержание, в теле
   issue оно стоит первым разделом.
2. Повесить `status:in-progress`: уведомление с кнопкой, отметка в списке,

3. Оставить комментарий: уведомление про комментарий, текст виден в карточке

## 8. Отклонения при реализации

- **Пустое краткое содержание не отклоняется.** По спеке валидатор требовал
  непустой `brief`. Это противоречило принятому решению 2026-08-09 «саммари
  достраивается из контракта, молчание модели не останавливает тикет»: ответ без
  поля уводил бы работу в повторы, а автора - в тишину. Теперь пустой `brief`
  проходит с логом `brief_missing`, карточка в этом случае показывает описание
  целиком. Отклоняется только превышение предела - это ошибка формата, её лечит
  повтор запроса.
- **`inTx` вынесена из `Cases` в `db.go`.** Слежению нужна та же транзакция;
  вторая копия шаблона разошлась бы с первой на первой правке. `Cases.inTx`
  осталась обёрткой в одну строку.
- **Тесты с базой требуют `TEST_DATABASE_URL`.** Без переменной они молча
  скипаются - тот же класс дефекта, что «право `Contents: read` отсутствовало
  полторы недели». Факт записан в `AGENTS.md`, раздел «Команды».

## 9. Известные ограничения

- Обратного канала нет: ответить на комментарий из бота нельзя.
- Комментарии сервиса и разработчика неотличимы - оба уходят под одним токеном.
  Пока сервис комментариев не пишет, вопрос не стоит; с обратным каналом
  понадобится маркер в теле комментария.
- Тикеты, заведённые в репозитории руками, слежению не видны.
- У тикетов до выката краткого содержания нет: карточка показывает полное
  описание.
- Уведомление, исчерпавшее повторы, уходит алертом владельцу, а автору молчит -
  прежний долг из [backlog.md](../backlog.md).
- Окно опроса меток - сто последних изменённых issue на проект: репозиторий, где
  за пять минут меняется больше, потеряет часть новостей.
