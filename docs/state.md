## Решения

- **2026-08-08. Сервис определён как единая точка входа бизнеса в разработку.**
  Решение владельца. Прежнее определение - приёмник фидбека по работающим
  сервисам - описывало первую функцию, а не замысел. Четыре функции и их
  порядок в разделе 2 [prd.md](prd.md). Объём первой версии не меняется.
- **2026-08-08. После M2 идёт M4, брифинг - следом.** M4 замыкает контур первой
  функции: без статусов автор возвращается спрашивать в личку. Срочность
  брифинга снята тем, что промт брифовщика работает в чате Claude уже сейчас,
  без бота, и метрику «владелец продукта вне перевода требований» закрывает
  промт, а не канал доставки.
- **2026-08-08. Под второй режим впрок не закладываем ничего.** Список мест -
  раздел 13 [architecture.md](architecture.md). Три правки схемы дешёвые,
  четвёртая нет: одно активное обращение на автора держит маршрутизацию каждого
  входящего сообщения, и её переделка это решение продукта, а не миграция.
  Заложены только три дисциплины в коде, которые не стоят ни строчки:
  нормализация не знает об исходе, обработчики очереди по типу работы, контракт
  готовности данными. Первые две уже соблюдены в M1, проверено по коду.
- **2026-08-08. Сырьё принимается до выбора проекта, пересылка равна своему
  сообщению.** Решение владельца. Человек начинает с материала, а не с
  репозитория: требовать сначала выбрать проект значит терять первое сообщение.
  Автором обращения остаётся тот, кто пишет боту; имя исходного отправителя
  пересылки не сохраняется - авторству оно не нужно, а перепиской с клиентом
  стало бы персональными данными.
- **2026-08-08. Срок стал плавающим, объём первой версии жёстким.** Решение
  владельца после оценки: M1 плюс M2 это два полных среза, а за понедельником
  нет внешнего события. Сырой поток к дате вернул бы людей в личку.
- **2026-08-08. Апдейты Telegram обрабатываются последовательно.** telebot по
  умолчанию запускает хендлеры параллельно; на пачке пересланных сообщений это
  даёт случайный порядок сырья, двойное создание обращения и повторный вопрос о
  проекте. Одна строка настройки дешевле любой блокировки при таком потоке.
- **2026-08-08. Хранилище тикетов - GitHub Issues в репозитории проекта.**
  Альтернативы (отдельный репозиторий-агрегатор, своё хранилище в Postgres)
  отклонены: тикет должен лежать рядом с кодом, и это не требует писать
  просмотр и хранение самим.
- **2026-08-08. Статус тикета - метка на issue, единственный источник истины.**
  Убирает из проекта разбор коммитов и публичный вебхук-эндпоинт: сервис
  опрашивает GitHub и уведомляет об изменении метки.
- **2026-08-08. Медиа не хранится после обработки.** Решение владельца.
  Следствие: подтверждение саммари автором обязательно, а не желательно.
- **2026-08-08. Нормализация медиа отдельными шагами до диалога.** Экономия
  возникает не на первом проходе, а на том, что изображение не переотправляется
  в каждом ходе диалога, и на дешёвой модели для механического извлечения.
- **2026-08-08. Доступ по белому списку Telegram ID.** Отменяет прежнее решение
  об открытом доступе. Открытый бот означает запись в приватные репозитории для
  любого, кто нашёл его в поиске. Список в конфиге стоит два десятка строк кода
  и снимает из первой версии триаж, лимиты и защиту от мусора целиком.
- **2026-08-08. Авторство фиксируется телом issue и меткой `author:<slug>`.**
  GitHub не даёт создать тикет от чужого имени: автором становится владелец
  токена. Настоящее авторство требовало бы GitHub-аккаунта у каждого сотрудника
  и разовой OAuth-авторизации через публичный callback, то есть лишний день
  работы и порог входа там, где сейчас человек просто пишет в Telegram.
- **2026-08-08. Скриншоты разбираются после текста и голоса, с протоколом сырья
  в контексте.** Без контекста жалобы экстрактор не знает, что на карточке
  важно, и вычитывает всё подряд. Инвариант «изображение входит в контекст один
  раз» сохраняется: в диалог попадает только текст.
- **2026-08-08. Интервью раундами по 2-3 вопроса вместо одного за раз.** Пять
  последовательных вопросов - это пять кругов ожидания ответа; пачка из пяти
  теряет часть ответов. Каждый вопрос идёт с предполагаемым ответом, кнопка
  «Всё так» принимает раунд целиком.
- **2026-08-08. Тип «вопрос» не отдельный исход, а тикет с меткой `question`.**
  Ответ из документации требует источника доков и способа проверить ответ;
  это перспектива бота-консультанта, а не первая версия.
- **2026-08-08. Язык сервиса - Go.** Цепочка сборки и деплоя (GHCR image,
  distroless, goose в образе, Coolify Compose) отлажена на соседних сервисах
  платформы; своего ML-кода нет, только HTTP-вызовы, поэтому Python не даёт
  выигрыша и требует параллельной цепочки.
- **2026-08-08. Модели по шагам, обе runtime-настройкой.**
  `google/gemini-3.1-flash-lite` на голос и скриншоты (самая дешёвая с аудио на
  входе и структурированным выводом), `deepseek/deepseek-v4-flash-0731` на
  интервью и саммари. При единицах обращений в день разница между дешёвой и
  сильной моделью меньше доллара в день, поэтому выбор решает golden-набор.
- **2026-08-08. Очередь и outbox - одна таблица `jobs`.** Отклонение от
  `platform.md`: механизм захвата и повторов у них совпадает, отличие только в
  идемпотентности, которую даёт поле `key`. Вынесено на гейт A.
