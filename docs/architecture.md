# Архитектура intake

Источник истины по техническим решениям. Бизнес-требования - [prd.md](prd.md),
порядок работ - [backlog.md](backlog.md), внешние вызовы - [contracts.md](contracts.md),
схемы и промты модели - [llm.md](llm.md). Спека не спорит с PRD: расхождение
означает изменение требования и возврат к гейту A.

## 1. Стек и почему так

| Решение | Обоснование |
| --- | --- |
| Go 1.25 | Канон платформы. Вся цепочка деплоя (immutable GHCR image, distroless, goose в образе, Coolify Compose) уже отлажена на соседних сервисах платформы. Своего ML-кода нет, только HTTP-вызовы, поэтому экосистема Python ничего не даёт, а второй язык требует параллельной цепочки сборки. Python остаётся для evals и разовых скриптов |
| PostgreSQL 16 | БД, состояние и очередь через `FOR UPDATE SKIP LOCKED`. Redis и брокеры не нужны при единицах обращений в день |
| `gopkg.in/telebot.v4` | Bot API, инлайн-кнопки, long polling. Уже в проде в соседнем сервисе |
| `github.com/jackc/pgx/v5` | Драйвер и пул. Уже в соседних сервисах |
| `github.com/pressly/goose/v3` | Миграции, бинарь копируется в образ отдельным слоем |
| `log/slog` | JSON-логи, stdlib |
| `net/http` плюс `encoding/json` | Клиенты OpenRouter и GitHub. Десяток эндпоинтов GitHub и один OpenRouter не оправдывают `go-github` и SDK: чужая модель ошибок и ретраев дороже своих ста строк |

Прямых зависимостей три: telebot, pgx, goose. Всё остальное - стандартная
библиотека.

Модуль: `github.com/daniil4545/tg-intake`. Структура из
[AGENTS.md](../AGENTS.md), рабочий код плоско в `src/internal/app`.

## 2. Модели LLM

Выбор по шагам, а не одна модель на всё: у шагов разные требования к
модальностям и разная цена ошибки.

| Шаг | Модель по умолчанию | Цена (за миллион токенов) | Почему |
| --- | --- | --- | --- |
| Транскрибация голосового | `google/gemini-3.1-flash-lite` | вход 0.25, аудио 0.50, выход 1.50 | Самая дешёвая модель с аудио на входе, которая одновременно умеет структурированный вывод. Альтернатива `openai/gpt-audio-mini` дороже по аудио |
| Разбор скриншота | `google/gemini-3.1-flash-lite` | вход 0.25, изображение 0.25 | Та же модель, что и на голосе: один клиент, одно семейство промтов. Кандидат на замену при проверке на golden-наборе - `qwen/qwen3-vl-32b-instruct` (вход 0.10) |
| Интервью и саммари | `deepseek/deepseek-v4-flash-0731` | вход 0.09, выход 0.18, чтение кэша 0.018 | Текстовый шаг, аудио и картинки не нужны. Structured outputs и tool calling заявлены. Автоматическое кэширование префикса без явных breakpoints, что совпадает с нашим инвариантом порядка промта |

Цены сняты живым запросом к `/api/v1/models` 2026-08-08.

**Цена не ограничение.** Обращение это примерно 20 тысяч входных и 3 тысячи
выходных токенов, то есть от четверти цента на самой дешёвой модели до семи
центов на самой сильной: при десяти обращениях в день разница меньше доллара.
Поэтому модель шага выбирается качеством интервью на русском, а не прайсом, и
остаётся runtime-настройкой (`OPENROUTER_MODEL_MEDIA`,
`OPENROUTER_MODEL_DIALOG`). Качество текущей диалоговой модели не проверено;
арбитр - golden-набор из реальных обращений (задача в бэклоге).

Режим вопроса своих моделей не заводит: оба хода идут диалоговой.

## 3. Модель состояния

Ядро - обращение (`case`). Статус меняет только Go, только в транзакции вместе
с записью в журнал и постановкой следующей работы.

Машина одна на оба режима разговора: `cases.mode` (`ticket` по кнопке «Создать
тикет», `ask` по кнопке «Спросить») выбирает, чем кончится нормализация.

```
   «Создать тикет» либо «Спросить» после выбора проекта
   (свободное сообщение вне обращения не сохраняется:
              бот отвечает начальным экраном)
                    |
                    v
             [collecting] <--ответ показан--------------------+
                    |                                         |
                «Готово»                                      |
                    v                                         |
            [normalizing] --файл не читается--> [collecting]  |
             голос, скриншоты                                 |
                    |                                         |
      mode=ask +----+----+ mode=ticket                        |
               |         |                                    |
               v         |                                    |
        [answering] -----|------------------------------------+
               |         |
   «Создать тикет» либо  |
   просьба о правке      |
               +-------->+
                         v
                   [interview] <--«поправить»-----+
                         |                        |
         контракт закрыт или предел раундов       |
                         v                        |
                     [summary] ------------------ +
                         |
                   «Публикую»
                         v
                  [publishing] --issue создан--> [published]
```

`[cancelled]` достижим по «Сбросу» из любого статуса, кроме `publishing` (работа
publish уже в очереди и могла создать issue) и `published`. Отмена уже
созданного тикета из карточки - не переход машины: `cases.status` остаётся
`published`, работа `cancel_issue` закрывает issue и ставит метку
`status:cancelled` - после публикации жизнь тикета целиком в метках GitHub.

`[answered]` - разговор закрыт полученным ответом кнопкой «Закончить разговор»
под ответом, то есть из `collecting`. Статус терминальный и слот активного
обращения освобождает; от `cancelled` отличается только причиной, и разница
видна владельцу в диагностике. Переход в тикет односторонний: `mode` меняется
на `ticket`, и дальше разговор неотличим от начатого кнопкой «Создать тикет»;
обратного хода нет, выход - «Сброс».

Переход берёт разговор только из `collecting` и `answering`. Из `collecting` он
сначала смотрит, есть ли неразобранное сырьё: реплика, набранная после ответа и
не подтверждённая «Готово», - это и есть содержание будущего тикета, поэтому
разговор уходит в `normalizing` и попадает в интервью уже с ней. Нечего
разбирать - сразу `interview`. Из `normalizing` перехода нет вовсе: он оборвал
бы цепочку разбора, и сырьё осталось бы неразобранным навсегда. Тем же сравнением
с разобранным протоколом отсекается повторное «Готово» в режиме вопроса: сырьё
прошлого вопроса на месте, нового нет, и второй поход повторил бы тот же ответ.

Черновик «брошен» отдельным статусом не является: это `collecting` или
`interview`, к которому сутки не прикасались. Так машина остаётся на девяти
состояниях (`collecting`, `normalizing`, `interview`, `summary`, `publishing`,
`published`, `cancelled`, `answering`, `answered`), а напоминание становится
обычной работой в очереди - и только в режиме тикета: вопрос, на который уже
ответили, не черновик.

Свободное сообщение вне обращения ничего не заводит и не сохраняется, бот
отвечает меню: управление кнопками, открытый текст - только содержимое
обращения. Решение владельца 2026-08-09, отменило автозаведение от 2026-08-08:
случайная ссылка заводила обращение, и следующая реплика молча становилась его
сырьём. Ожидание правки саммари тоже не статус: «Поправить» ничего не меняет,
правкой становится следующее сообщение автора в `summary`.

## 4. Сущности

### `projects`

Мультипроектность с первого дня: добавление проекта это `INSERT`, деплой не
нужен.

| Поле | Назначение |
| --- | --- |
| `id`, `slug` | `slug` короткий (`crm-bot`), уезжает в `callback_data`, где всего 64 байта |
| `title` | что показываем в меню |
| `github_owner`, `github_repo` | куда публикуем. Токен один на сервис, в таблице его нет |
| `context` | один-два абзаца «чем занят проект», уходит в кэшируемый префикс промта |
| `labels_ready` | метки в репозитории заведены; ставится после успешного bootstrap |
| `active` | скрыть проект из меню, не удаляя историю |
| `comments_since` | граница окна, за которым слежение ищет новые комментарии. Двигается только после успешного разбора тика, назад не ходит |

### `users`

| Поле | Назначение |
| --- | --- |
| `telegram_id` | первичный ключ, он же признак узнавания |
| `first_name`, `last_name`, `username` | ФИО для шапки issue. `last_name` и `username` в Telegram опциональны, фолбэк на `first_name` плюс ID |
| `slug` | нормализованное имя для метки `author:<slug>` |
| `updated_at` | ФИО перечитывается при каждом обращении: люди меняют его в профиле |

Белый список Telegram ID живёт в конфиге, а не в таблице: список из пяти строк
не заслуживает таблицы и правится без доступа к БД.

### `cases`

| Поле | Назначение |
| --- | --- |
| `id` | uuid, он же ключ идемпотентности публикации и маркер в теле issue |
| `user_id`, `project_id` | автор и репозиторий; проект пуст только у `collecting`, `cancelled` и `answered`, дальше его требует CHECK |
| `status` | девять состояний из раздела 3 |
| `mode` | `ticket` или `ask`; выбирает следующий шаг после нормализации. Меняется один раз и только в сторону тикета, дефолт `ticket` |
| `kind` | `bug`, `feature`, `question`; пусто до шага интервью |
| `protocol` | склеенный протокол сырья, вход диалоговой модели. Подпись под медиа идёт отдельной строкой «слова автора»: пометка «переслано» относится к содержимому элемента, а подпись автор набирает сам |
| `contract` | jsonb: заполненные пункты контракта готовности по ключам |
| `gaps` | jsonb: незакрытые ключи. Список пробелов в issue берётся отсюда |
| `round` | сколько раундов вопросов прошло, против предела из конфига |
| `title`, `summary` | заголовок и тело будущего issue после подтверждения |
| `brief` | краткое содержание: первый раздел тела issue и единственное описание в карточке бота - полного тела карточка не показывает. Пусто у тикетов до появления поля и когда модель его не отдала (лог `brief_missing`) |
| `incomplete` | отправлено с пробелами, ставит метку `incomplete` |
| `issue_number`, `issue_url` | результат публикации; непустое значение запрещает повторную публикацию |
| `reminded_at` | напоминание отправляется один раз |
| `told_status`, `told_comment_id` | что слежение уже доставило автору: метка, о которой сказали, и последний отправленный комментарий. NULL в `told_status` - тикет заведён до появления слежения, и первое наблюдение молчит; публикация проставляет `status:new` сразу |
| `has_news` | о новости сказали, карточку автор не открыл; держит отметку в списке и гаснет при открытии |

Частичный уникальный индекс по `user_id` там, где статус не терминальный
(`published`, `cancelled`, `answered`): активное обращение у автора ровно одно,
любого режима, - это убирает класс вопросов «в какой из трёх черновиков попало
голосовое». Второй частичный уникальный индекс по `(project_id, issue_number)`
не даёт двум обращениям указывать на один тикет.

`told_status` статусом тикета не является: это ответ на вопрос «о чём автору уже
сказали». Колонки статуса тикета по-прежнему нет, и всё, что показывается
человеку, читается из GitHub в момент показа.

`protocol`, `contract`, `gaps` и `round` описывают структурированное интервью
вообще, а не тикет. Тикет-специфичны `kind`, `issue_number`, `issue_url` и часть
значений `status`.

### `case_items`

Сырьё обращения по одному сообщению.

| Поле | Назначение |
| --- | --- |
| `kind` | `text`, `voice`, `photo`, `link` |
| `tg_message_id`, `tg_file_id` | `file_id` персистентен и остаётся после удаления файла: единственный способ перечитать вложение потом |
| `tg_group_id` | `media_group_id` альбома. Bot API отдаёт четыре скриншота четырьмя апдейтами, поле нужно, чтобы не считать их четырьмя обращениями |
| `source_text` | текст сообщения или подпись к фото |
| `forwarded` | сообщение переслано: содержимое не слова автора, и протокол это помечает |
| `mime` | тип файла Telegram, отсюда `format` запроса к модели |
| `normalized` | транскрипт или разбор скриншота |
| `file_path` | локальный путь; обнуляется вместе с удалением файла после публикации |
| `status`, `error` | `pending`, `done`, `failed` и причина |

### `case_events`

Журнал решений: кто, когда, что. Проекция состояния лежит в `cases`, история в
журнале. Payload без персональных данных клиентов и без содержимого файлов.

Реплики разговора живут здесь же снимками текста: `summary_ready` в интервью,
`question_asked` и `answer_ready` в режиме вопроса. Колонка держала бы только
последнюю версию, а модели нужна вся переписка.

### `jobs`

Очередь и она же outbox.

| Поле | Назначение |
| --- | --- |
| `kind` | `normalize_voice`, `normalize_image`, `finish_normalize`, `interview`, `summarize`, `lookup`, `publish`, `notify`, `cancel_issue` |
| `key` | уникальный ключ идемпотентности, например `publish:<case_id>` или `interview:<case_id>`. Напоминание о брошенном черновике - обычная работа `notify` с суффиксом ключа `remind` |
| `status`, `attempts`, `run_after`, `locked_at`, `last_error` | захват через `FOR UPDATE SKIP LOCKED`, экспоненциальная отсрочка |
| `payload` | параметры шага. У `notify` непустой `chat_id` означает уведомление владельцу: адресат назван явно, кнопок и экранов у него нет |

Отработавшие работы убираются через неделю (`SweepJobs` тем же часовым тиком,
что и файлы черновиков): аудит живёт в `case_events`, а идемпотентность по ключу
нужна ровно пока обращение способно поставить работу заново. Провалы остаются -
по ним разбирают инциденты.

Нормализация идёт по элементу: запись и скриншот получают свою работу, а
закрывает разбор `finish_normalize`. Так бюджет работы принадлежит одному вызову
модели, и деградация провайдера на первом экране не оставляет следующие без
времени. Выбор следующего шага в одном месте (`advanceNormalize`): есть
неразобранные записи - работы на них, есть скриншоты - на них, не осталось
ничего - закрытие; `RecoverStuck` идёт тем же выбором, а не догадкой о том, где
всё встало. Чем кончится разговор, `advanceNormalize` не знает вовсе:
единственная развилка по режиму стоит в закрывающем шаге (`Normalizer.finish`),
`ticket` ставит `interview`, `ask` - `lookup`.

Шаги обращения - `finish_normalize`, `interview`, `summarize`, `lookup`,
`publish`, `cancel_issue` - существуют в единственном экземпляре и ставятся
заменой прежней работы (`replaceJob`); разбор элемента живёт по `item_id`, а
`notify` - по суффиксу ключа, их много. Отсюда второе «Готово» перезапускает
нормализацию, дописанный ответ отменяет ещё не начатый ход (модель отвечает
один раз на всё), а повторное «Публикую» после исчерпанных повторов снова
уходит в очередь, не упираясь в ключ погашенной работы. От дубля во внешнем
мире защищает не ключ, а состояние: `issue_number` и маркер в теле тикета.

**Два отклонения от `platform.md`, согласованы на гейте A.** Первое: очередь и
outbox - одна таблица, механизм захвата, повторов и аудита у них совпадает
полностью, а идемпотентность даёт поле `key`; две таблицы с одинаковым кодом
захвата были бы дублированием, а не защитой. Второе: ответы бота внутри диалога
уходят синхронно из обработчика апдейта - автор ждёт на экране, и лишний цикл
воркера превращает разговор в переписку с задержкой. Через очередь идут только
сообщения фоновой работы (протокол, ответ по документации, номер issue,
напоминание) - там доставка обязана пережить рестарт.

## 5. Процессы

Один процесс, четыре горутины, общий `context` для остановки.

1. **bot** - long polling с таймаутом 10 секунд. Принимает апдейты, пишет в БД,
   отвечает синхронно, ставит работы. Апдейты идут последовательно
   (`Synchronous`): параллельные хендлеры над одним обращением давали бы
   двойную вставку `cases`, случайный порядок сырья в протоколе и повторный
   вопрос о проекте. Поллер свой, а не `telebot.LongPoller`: тот прячет ошибку
   опроса в `debug`, а `Verbose` дампит сырые payload с текстами обращений, и
   `409 Conflict` от второго поллера не был виден нигде. Свой пишет отказ в лог
   и отмечает успешный опрос файлом в `MEDIA_DIR`; `healthcheck` считает
   контейнер здоровым только при отметке свежее трёх минут - живая база при
   молчащем опросе больше не выглядит здоровьем.
2. **worker** - два параллельных обработчика, тянут `jobs` через
   `FOR UPDATE SKIP LOCKED`; свой минутный цикл освобождает локи старше пяти
   минут.
3. **sweeper** - раз в час прогоняет восстановление (`RecoverStuck`, он же на
   старте), напоминание о черновиках старше суток (работой `notify`), уборку
   файлов (`SweepDrafts`) и уборку отработавшей очереди (`SweepJobs`).
4. **watch** - раз в пять минут спрашивает GitHub о новостях по тикетам:
   изменённые метки одним списком issue (`sort=updated`) и новые комментарии
   одним списком по репозиторию (`since`). Два запроса на проект за тик, сколько
   бы тикетов ни было. Значимая новость становится работой `notify`, отказ по
   проекту - предупреждением: недоступный репозиторий не глушит чужие новости.
   Своя горутина, а не часть sweeper: новость, пролежавшая час, для автора почти
   то же, что не пришедшая. Потолок у каждого проекта свой (45 секунд при бюджете
   тика в четыре минуты): повторы GitHub не знают об остатке бюджета, и медленный
   проект иначе забирал бы время следующих за ним.

Цепочка шагов живёт в БД, а не в памяти: воркер, закончив элемент, смотрит,
остались ли `pending` элементы того же типа, и ставит следующую работу сам.
Рестарт в середине обращения ничего не теряет.

Политика при переполнении: `attempts > 5` переводит работу в `failed`, и исход
провала (`HandleFailedJob`) отвечает автору по виду работы - «не смог
обработать, пришлите иначе» на разборе, «не смог посмотреть документацию» на
походе в документацию. Гашение работы и исход - одна транзакция: порознь падение
процесса между коммитами оставило бы элемент `pending`, а обращение в
`normalizing` навсегда. Провал элемента не останавливает цепочку: элемент
помечается `failed` (иначе проверка «pending не осталось» не сработала бы
никогда), а проваленные закрытие нормализации и поход в документацию возвращают
обращение в сбор, освобождая слот. Исчерпанное сообщение автору (`notify`)
уходит алертом владельцу с текстом потери; провал самого алерта нового алерта
не порождает - недоступный Telegram кормил бы очередь своими провалами. Тихо
потерянных обращений нет.

Восстановление (`RecoverStuck`, на старте и раз в час): `normalizing`,
`publishing` и `answering` двигаются только работой, и обращение, оставшееся
без неё (повторы исчерпаны, процесс умер между сменой статуса и постановкой,
старая версия оставила погашенный ключ), висит молча. Недостающая работа
ставится заново по состоянию в БД, причина не разбирается: `normalizing` через
`advanceNormalize`, `answering` через `lookup`, остальное через `publish`.
`collecting`, `interview` и `summary` не трогаются: там обращение ждёт
человека. Именно поэтому у похода в документацию свой статус, а не сбор: иначе
потерянную работу подобрать было бы не по чему.

Уборка файлов (`SweepDrafts`, раз в час): файлы обращений, к которым сутки не
прикасались (срок от `updated_at`: разговор идёт часами), и файлы закрытых
обращений (`published`, `cancelled`, `answered`) без отсрочки - сбой уборки при
публикации иначе оставил бы их навсегда. `normalizing` и `publishing` не
входят: там файлы держит работа. Статус уборка не меняет: автор вернётся к
тексту, но не к файлам - цена инварианта «медиа не переживает обращение».

## 6. Внешние контракты

Вынесены в [contracts.md](contracts.md): вызовы и ограничения Telegram,
OpenRouter и GitHub, проверенные документацией или живым запросом. Здесь
остаётся правило, которое держит всю модель потока: бот обрабатывает апдейты
последовательно, поэтому из хендлеров наружу ходят только быстрый
GitHub-клиент и единственный синхронный вызов модели в `/project`; всё
остальное, включая поход в документацию, - через очередь.

Прав у токена два, и проверяются оба: писать - созданием меток
(`PrepareProject`), читать содержимое - листингом корня (`CheckRead`). Одно
другого не доказывает: fine-grained PAT без `Contents: read` получает 403 и на
публичном репозитории, и режим «Спросить» так молча не работал целый релиз.
PAT выдаётся на конкретные репозитории, поэтому проверяется
каждый - на старте по всем активным и при заведении нового. Отказ по одному
проекту - предупреждение, а не падение старта; успех снимает bootstrap с
горячего пути.

## 7. Контракты LLM

## 9. Псевдокод ключевых функций

Только те шаги, где логика не читается из кода построчно. Остальное - сбор
сырья, нормализация, подстановка ответов, захват работ - описано кодом и его
комментариями.

```
RunInterview(ctx, job) error
  1. собрать запрос: префикс (метод, контракт, контекст проекта), протокол,
     переписка с автором (вопросы, показанные саммари, ответы)
  2. запрос к диалоговой модели по схеме InterviewTurn
  3. валидировать по правилам llm.md, при отказе - один повтор. Ход без
     единой догадки в вопросах тратит тот же повтор: кнопке нечего
     подтверждать. Второй такой ответ принимается как есть
  4. снять вопросы про пункты, о которых уже спрашивали дважды (счёт по
     журналу раундов): третий заход автор читает как поломку, пробел честнее.
     Правка саммари этого предела не знает, как и предела раундов
  5. слить contract хода с накопленным (память модели не гарантия: пункт, не
     повторённый раундом, иначе молча выпал бы), записать kind, contract,
     gaps, инкремент round
  6. если ready, вопросов не осталось или round достиг предела - job summarize
     иначе отправить автору один вопросный раунд; кнопка «Всё так» идёт с ним
     только при непустых догадках - обещание обязано совпадать с текстом
  выход: либо вопрос автору, либо переход к саммари
```

```
PublishIssue(ctx, job) error
  1. если case.issue_number не пуст или статус не publishing - выйти: работа
     уже сделана либо обращение отменено
  2. EnsureLabels для проекта, если labels_ready ложно
  3. собрать тело: шапка с автором, разделы контракта, список пробелов, раздел
     «Ссылки» (адреса из сырья, собирает Go: модель переписала бы адрес),
     маркер intake:case:<uuid>
  4. POST issues с метками type, status, author, при необходимости incomplete
  5. при неизвестном результате (таймаут, 5xx) перед повтором - поиск маркера
     сканом последних issue репозитория (не search API: его индекс отстаёт)
  6. записать issue_number и issue_url, статус published, событие published
  7. поставить job notify с номером и ссылкой, при заданном ALERT_CHAT_ID -
     второй job notify шапкой в чат владельца
  8. удалить файлы обращения, обнулить file_path
  выход: issue в GitHub, автор уведомлён, медиа на диске нет
```

```
Lookup.Run(ctx, job) error
  1. загрузить обращение; выйти молча, если mode не ask или статус не
     answering - работа устарела: отмена, кнопка «Создать тикет», уже отвечено
  2. снять версию разговора (число событий question_asked), контекст проекта и
     историю из журнала (question_asked и answer_ready)
  3. GetRepo - default_branch, TreeDocs - пути md-файлов с размерами
  4. ход отбора: пути вне дерева отбросить, дубли схлопнуть, оставить до трёх
  5. скачать отобранное, обрезая по потолкам и помечая обрез; нечитаемый файл
     пропустить - молчание хуже ответа по двум файлам из трёх
  6. ход ответа по скачанному, проверить по правилам llm.md
  7. одной транзакцией, взяв строку FOR UPDATE и сверив неизменность версии
     разговора (иначе ответ на прошлый вопрос лёг бы поверх свежей реплики):
     wants_ticket - mode=ticket, статус interview, работа interview;
     иначе - статус collecting, событие answer_ready снимком текста, работа
     notify автору с кнопками и, при заданном ALERT_CHAT_ID, вторая notify
     строкой владельцу: кто, проект, найден ли ответ, из каких файлов
  выход: ответ со ссылками, «в документации этого нет» либо переход в тикет
```

Потолки константами `lookup.go`: до 3 файлов, 80 000 символов на файл, 200 000
суммарно, 300 путей в списке дерева (обрез помечается - иначе «не нашёл»
читается как «в репозитории этого нет»). Бюджет - общий `jobTimeout` 4 минуты,
модель и размышления - диалоговые: жанр тот же, вторая пара настроек не нужна.

## 10. Логирование

JSON через `slog`, у каждой записи `service=intake` и `env`; `case_id`,
`user_id` и `step` добавляет то событие, к которому они относятся. Логируем
начало обращения, каждую работу (тип, попытка, длительность), каждый вызов
модели (модель, токены, время попытки), решение модели (тип обращения, число
пробелов и их ключи, не текст; у похода в документацию - сколько файлов
выбрано, сколько путей отброшено, найден ли ответ и просит ли автор правку),
публикацию (номер issue) и все ошибки с причиной.

Не логируем: тексты сообщений, транскрипты, разбор скриншотов, содержимое
файлов документации, тексты вопросов и ответов, ФИО. В логах человек это
`user_id`, а не имя.

## 11. Инварианты и чем они держатся

| Инвариант | Где обеспечен | Чем проверяется |
| --- | --- | --- |
| Медиа не переживает обращение | шаг 8 `PublishIssue`: `DropFiles` идёт после коммита публикации, его провал только логируется и подчищается почасовым сборщиком | тест: после публикации файлов на диске нет, `file_id` остался |
| Тикет не публикуется без подтверждения | `publishing` достижим только из `summary` по кнопке автора | тест: отменённое обращение не публикуется |
| Единственный источник истины по статусу - метка | сервис не хранит статус тикета: `told_status` отвечает «о чём автору сказали», а показ читает метки из GitHub | ревью схемы: колонки статуса тикета нет; тест: первое наблюдение метки автора не будит |
| Экстрактор признаётся в непрочитанном | обязательное `unreadable` в схеме, валидация Go | тест на ответе модели без поля |
| Порядок промта фиксирован | сборка запроса одной функцией: префикс из `embed` первым сообщением, история всегда сзади | тест сборки запроса |
| Ни одна идея не выбрасывается | недобор даёт issue с меткой `incomplete`, отказ невозможен | тест сценария предела раундов |
| Мультипроектность | проект это строка таблицы | добавление проекта в тесте без правки кода |
| Внешние вызовы идемпотентны | `jobs.key` плюс маркер в теле issue | тестами не покрыто: проверяется живым прогоном |
| Мутации GitHub идут очередью | публикация и отмена - работы `publish` и `cancel_issue` | ревью: из хендлера пишет только заведение проекта, и это одна метка-проверка |
| Ответ без источника не отдаётся | `checkAnswer`: `found` держится только на скачанных файлах и непустом тексте, иначе автор получает «в документации этого нет» | тесты: `found` при пустых `sources`, источник вне скачанного, путь вне дерева |
| Переход в тикет односторонний и сырья не теряет | UPDATE перехода берёт только `mode = 'ask'` в `collecting` или `answering`; несобранная реплика уводится в нормализацию, а не в интервью | тесты: перевод в разборе цепочку не рвёт, дописанная реплика доходит до протокола и до интервью |

## 12. Открытые вопросы

- Качество диалоговой модели на русскоязычном интервью. Решается golden-набором.
- Где живёт PRD, собранный брифингом. Сейчас он уходит документом в чат автору,
  а режим вопроса читает документацию из репозитория: отданный только в чат
  документ для него не существует. Решается до спеки M6 - файл в репозитории
  проекта или запись в БД.
- Отбор по трём файлам промахнётся, если ответ размазан по многим документам.
  Первый кандидат на правку после живого прогона режима вопроса.
- Нужен ли повторный проход по скриншоту, если вопрос всплыл уже в интервью.
  Пока не делаем: усложняет шаг ради неподтверждённой пользы.

## 13. Места, заточенные под один режим

Список вёлся с M1, чтобы цена второго режима не всплыла неожиданно. Режим
вопроса его проверил: дешёвые правки оказались дешёвыми и закрыты миграцией
`0008` вместе с `cases.mode`, `answering`, `answered` и работой `lookup`. Дороже
всего оказалась не схема, а маршрутизация, и она осталась нетронутой.

| Место | Состояние |
| --- | --- |
| `CHECK` на `cases.status` и `jobs.kind` | закрыто: `DROP CONSTRAINT` плюс `ADD CONSTRAINT`, как и оценивалось |
| Колонка режима в `cases` | закрыто: `ADD COLUMN ... DEFAULT 'ticket'`, данные целы |
| `CHECK cases_project_before_work` | пересобран под `answered`; у брифинга проекта нет вовсе, там он снимается целиком |
| Одно активное обращение на автора | открыто: **дорого, см. ниже** |

**Единственное дорогое место - не индекс, а маршрутизация.** Индекс лишь
охраняет инвариант; опирается на него `Cases.Active`, а через него - разбор
каждого входящего сообщения. Как только у автора может быть два активных
разговора, `Active` возвращает произвольный, и голосовое уезжает в случайный.
Цена: DDL плюс переделка `Active` и способ автора адресовать сообщение нужному
разговору - решение продукта, а не миграция. Режим вопроса этого не потребовал:
разговор по-прежнему один, у него лишь два жанра. Принимается на спеке M6.

Дешевизну остального держат три дисциплины: нормализация не знает об исходе
разговора (развилка стоит в закрывающем шаге, не в цепочке разбора), обработчики
очереди регистрируются по типу работы, правила живут данными. Исходы провалов
ветвятся центральным `switch` по виду работы - место, о котором обязан помнить
каждый новый вид. Тикет-специфика живёт дальше по потоку: тип обращения, метки
и отмена в `tickets.go`. Остался один адрес на будущее: `FinishCollect` требует
проект - вопросу это не помеха, а брифинг проект создаёт сам.
