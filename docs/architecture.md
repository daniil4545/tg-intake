# Архитектура intake

Источник истины по техническим решениям. Бизнес-требования - [prd.md](prd.md),
порядок работ - [backlog.md](backlog.md). Спека не спорит с PRD: расхождение
означает изменение требования и возврат к гейту A.

## 1. Стек и почему так

| Решение | Обоснование |
| --- | --- |
| Go 1.25 | Канон платформы. Вся цепочка деплоя (immutable GHCR image, distroless, goose в образе, Coolify Compose) уже отлажена на соседних сервисах платформы. Своего ML-кода нет, только HTTP-вызовы, поэтому экосистема Python ничего не даёт, а второй язык требует параллельной цепочки сборки. Python остаётся для evals и разовых скриптов |
| PostgreSQL 16 | БД, состояние и очередь через `FOR UPDATE SKIP LOCKED`. Redis и брокеры не нужны при единицах обращений в день |
| `gopkg.in/telebot.v4` | Bot API, инлайн-кнопки, long polling. Уже в проде в соседнем сервисе |
| `github.com/jackc/pgx/v5` | Драйвер и пул. Уже в соседних сервисах |
| `github.com/pressly/goose/v3` | Миграции, бинарь копируется в образ отдельным слоем |
| `log/slog` | JSON-логи, stdlib |
| `net/http` плюс `encoding/json` | Клиенты OpenRouter и GitHub. Три эндпоинта GitHub и один OpenRouter не оправдывают `go-github` и SDK: чужая модель ошибок и ретраев дороже своих ста строк |

Зависимостей ровно четыре. Всё остальное - стандартная библиотека.

Модуль: `github.com/daniil4545/tg-intake`. Структура из
[AGENTS.md](../AGENTS.md), рабочий код плоско в `src/internal/app`.

## 2. Модели LLM

Выбор по шагам, а не одна модель на всё: у шагов разные требования к
модальностям и разная цена ошибки.

| Шаг | Модель по умолчанию | Цена (за миллион токенов) | Почему |
| --- | --- | --- | --- |
| Транскрибация голосового | `google/gemini-3.1-flash-lite` | вход 0.25, аудио 0.50, выход 1.50 | Самая дешёвая модель с аудио на входе, которая одновременно умеет структурированный вывод. Альтернатива `openai/gpt-audio-mini` дороже по аудио |
| Разбор скриншота | `google/gemini-3.1-flash-lite` | вход 0.25, изображение 0.25 | Та же модель, что и на голосе: один клиент, одно семейство промтов. Кандидат на замену при проверке на golden-наборе - `qwen/qwen3-vl-32b-instruct` (вход 0.10) |
| Интервью и саммари | `deepseek/deepseek-v4-flash-0731` | вход 0.09, выход 0.18, чтение кэша 0.018 | Текстовый шаг, аудио и картинки не нужны. Structured outputs и tool calling заявлены. Автоматическое кэширование префикса без явных breakpoints, что совпадает с нашим инвариантом порядка промта |

Цены сняты живым запросом к `/api/v1/models` 2026-08-08.

**Цена не является ограничением, и это надо сказать прямо.** Одно обращение это
примерно 20 тысяч входных и 3 тысячи выходных токенов. На `deepseek-v4-flash`
это 0.24 цента, на `moonshotai/kimi-k2.6` около 2 центов, на
`anthropic/claude-sonnet-5` около 7 центов. При десяти обращениях в день разница
между самой дешёвой и самой сильной моделью меньше доллара в день. Поэтому
модель шага выбирается качеством интервью на русском, а не прайсом, и остаётся
runtime-настройкой: `OPENROUTER_MODEL_MEDIA`, `OPENROUTER_MODEL_DIALOG`.

Качество `deepseek-v4-flash` на русскоязычном интервью я не проверял и утверждать
не могу. Арбитр - golden-набор из реальных обращений сотрудников (задача в бэклоге):
прогон одного набора на трёх моделях стоит центы и даёт ответ за один вечер.

## 3. Модель состояния

Ядро - обращение (`case`). Статус меняет только Go, только в транзакции вместе
с записью в журнал и постановкой следующей работы.

```
   выбор проекта и «Создать тикет» либо первое сообщение автора
      (во втором случае проект спрашивается до «Готово»)
                     |
                     v
              [collecting] ---«Отмена»---> [cancelled]
                     |
                 «Готово»
                     v
             [normalizing]  --файл не читается--> сообщение автору,
                     |                            возврат в [collecting]
            голос, затем скриншоты
                     v
              [interview] <--«поправить»-------------+
                     |                               |
        контракт закрыт или предел раундов           |
                     v                               |
                [summary] ------------------------- +
                     |
              «Публикую»
                     v
             [publishing] --issue создан--> [published]
```

Черновик «брошен» отдельным статусом не является: это `collecting` или
`interview`, к которому сутки не прикасались. Так машина остаётся на семи
состояниях (`collecting`, `normalizing`, `interview`, `summary`, `publishing`,
`published`, `cancelled`), а напоминание становится обычной работой в очереди.

## 4. Сущности

### `projects`

Мультипроектность с первого дня: добавление проекта это `INSERT`, деплой не
нужен.

| Поле | Назначение |
| --- | --- |
| `id`, `slug` | `slug` короткий (`crm-bot`), уезжает в `callback_data`, где всего 64 байта |
| `title` | что показываем в меню |
| `github_owner`, `github_repo` | куда публикуем. Токен один на сервис, в таблице его нет |
| `context` | один-два абзаца «чем занят проект», уходит в кэшируемый префикс промта |
| `labels_ready` | метки в репозитории заведены; ставится после успешного bootstrap |
| `active` | скрыть проект из меню, не удаляя историю |

### `users`

| Поле | Назначение |
| --- | --- |
| `telegram_id` | первичный ключ, он же признак узнавания |
| `first_name`, `last_name`, `username` | ФИО для шапки issue. `last_name` и `username` в Telegram опциональны, фолбэк на `first_name` плюс ID |
| `slug` | нормализованное имя для метки `author:<slug>` |
| `updated_at` | ФИО перечитывается при каждом обращении: люди меняют его в профиле |

Белый список Telegram ID живёт в конфиге, а не в таблице: список из пяти строк
не заслуживает таблицы и правится без доступа к БД.

### `cases`

| Поле | Назначение |
| --- | --- |
| `id` | uuid, он же ключ идемпотентности публикации и маркер в теле issue |
| `user_id`, `project_id` | автор и репозиторий |
| `status` | семь состояний из раздела 3 |
| `kind` | `bug`, `feature`, `question`; пусто до шага интервью |
| `protocol` | склеенный протокол сырья, вход диалоговой модели |
| `contract` | jsonb: заполненные пункты контракта готовности по ключам |
| `gaps` | jsonb: незакрытые ключи. Список пробелов в issue берётся отсюда |
| `round` | сколько раундов вопросов прошло, против предела из конфига |
| `title`, `summary` | заголовок и тело будущего issue после подтверждения |
| `incomplete` | отправлено с пробелами, ставит метку `incomplete` |
| `issue_number`, `issue_url` | результат публикации; непустое значение запрещает повторную публикацию |
| `reminded_at` | напоминание отправляется один раз |

Частичный уникальный индекс по `user_id` там, где статус не терминальный:
активное обращение у автора ровно одно. Это убирает целый класс вопросов «в
какой из трёх черновиков попало голосовое».

### `case_items`

Сырьё обращения по одному сообщению.

| Поле | Назначение |
| --- | --- |
| `kind` | `text`, `voice`, `photo`, `link` |
| `tg_message_id`, `tg_file_id` | `file_id` персистентен и остаётся после удаления файла: единственный способ перечитать вложение потом |
| `tg_group_id` | `media_group_id` альбома. Bot API отдаёт четыре скриншота четырьмя апдейтами, поле нужно, чтобы не считать их четырьмя обращениями |
| `source_text` | текст сообщения или подпись к фото |
| `normalized` | транскрипт или разбор скриншота |
| `file_path` | локальный путь; обнуляется вместе с удалением файла после публикации |
| `status`, `error` | `pending`, `done`, `failed` и причина |

### `case_events`

Журнал решений: кто, когда, что. Проекция состояния лежит в `cases`, история в
журнале. Payload без персональных данных клиентов и без содержимого файлов.

### `jobs`

Очередь и она же outbox.

| Поле | Назначение |
| --- | --- |
| `kind` | `normalize_voice`, `normalize_images`, `interview`, `summarize`, `publish`, `notify`, `remind` |
| `key` | уникальный ключ идемпотентности, например `publish:<case_id>` или `interview:<case_id>:<round>`. Повторная постановка той же работы это конфликт вставки, а не второй вызов модели |
| `status`, `attempts`, `run_after`, `locked_at`, `last_error` | захват через `FOR UPDATE SKIP LOCKED`, экспоненциальная отсрочка |
| `payload` | параметры шага |

**Отклонение от `platform.md`, требует согласия на гейте A.** Канон говорит
«side effects только через outbox-таблицы» и подразумевает отдельную таблицу.
Здесь очередь и outbox это одна таблица: механизм захвата, повторов и аудита у
них совпадает полностью, отличие только в требовании идемпотентности, которое
обеспечивается полем `key`. Две таблицы с одинаковым кодом захвата были бы
дублированием, а не защитой.

**Второе отклонение.** Ответы бота внутри диалога отправляются синхронно из
обработчика апдейта, а не через очередь: автор ждёт ответа на экране, и лишний
цикл воркера превращает разговор в переписку с задержкой. Через очередь идут
только сообщения, порождённые фоновой работой (результат нормализации,
номер issue, напоминание) - там доставка обязана пережить рестарт.

## 5. Процессы

Один процесс, три горутины, общий `context` для остановки.

1. **bot** - `telebot.LongPoller` с таймаутом 10 секунд. Принимает апдейты,
   пишет в БД, отвечает синхронно, ставит работы.
2. **worker** - два параллельных обработчика, тянут `jobs` через
   `FOR UPDATE SKIP LOCKED`.
3. **ticker** - раз в час ставит `remind` для черновиков старше суток, раз в
   минуту освобождает локи старше пяти минут.

Цепочка шагов живёт в БД, а не в памяти: воркер, закончив элемент, смотрит,
остались ли `pending` элементы того же типа, и ставит следующую работу сам.
Рестарт в середине обращения ничего не теряет.

Политика при переполнении: `attempts > 5` переводит работу в `failed`, пишет
лог и отправляет автору «не смог обработать, пришлите иначе». Тихо потерянных
обращений нет.

## 6. Внешние контракты

### Telegram

- Скачивание: `bot.FileByID` и `bot.Download`. Потолок Bot API - 20 МБ, но
  `file_size` приходит в самом апдейте, поэтому отсекаем до запроса файла.
- Кнопки: `callback_data` 1-64 байта, поэтому в кнопке короткие идентификаторы
  (`project`, `a:new`, `r:<case8>:ok`), а не тексты. Маршрутизация - штатная для
  telebot: `InlineButton{Unique, Data}`, библиотека кодирует это как
  `\f<unique>|<data>` и разбирает сама. Свой формат `callback_data` мимо
  `Unique` не заводим: он не поймается хендлером по кнопке.
- Кнопка «Готово» на время сбора - reply-клавиатура: её видно всегда и не надо
  искать сообщение с инлайн-кнопкой выше по переписке.
- Раунд из двух-трёх вопросов уходит одним сообщением: в один чат допустимо
  примерно одно сообщение в секунду.

### OpenRouter

- `POST /api/v1/chat/completions`, `response_format` с `json_schema`,
  `provider.require_parameters: true`, чтобы запрос не уехал к провайдеру без
  поддержки схемы.
- Аудио: только base64 в `input_audio` с полем `format`, URL не принимается.
  Голосовое Telegram это OGG с кодеком OPUS; поддержка контейнера заявлена как
  зависящая от провайдера, поэтому в конфиге есть `AUDIO_CONVERT=auto|always`.
  План А - отдать ogg как есть. План Б - статический ffmpeg в образ, и это не
  бесплатно: база `distroless/static` не содержит ни ffmpeg, ни libc, бинарь
  придётся класть отдельным слоем и образ вырастет примерно на 80 МБ.
- Изображение: `image_url` с `data:image/jpeg;base64,...`.
- Таймаут 60 секунд, три повтора с экспонентой на 429 и 5xx, на 4xx повторов
  нет.
- Кэш: стабильный префикс отдельным первым сообщением. Ни одной изменяющейся
  строки перед ним, иначе кэш молча перестаёт работать. TTL у провайдеров
  порядка пяти минут, поэтому кэш экономит внутри одного разговора, а не между
  обращениями.

### GitHub

- `POST /repos/{owner}/{repo}/issues` с заголовком, телом и метками.
- Метки: по таблице разрешений GitHub права `Issues: write` у fine-grained PAT
  хватает и на `POST /repos/{owner}/{repo}/labels`, и на простановку меток при
  создании issue. Автосоздание несуществующей метки документацией не обещано,
  поэтому метки заводятся bootstrap-шагом при первой публикации в проект
  (`labels_ready`), а право проверяется при старте сервиса, а не в момент,
  когда первый тикет уедет без меток.
- Идемпотентность: своего ключа у GitHub нет. В тело issue уходит маркер
  `<!-- intake:case:<uuid> -->`; перед повторной попыткой сервис ищет его
  поиском по репозиторию. Это защита от дубля при потерянном ответе на успешный
  запрос.
- Лимиты: 5000 запросов в час, вторично не больше 80 создающих контент запросов
  в минуту. Наш объём на три порядка ниже, но очередь всё равно однопоточная по
  публикации.
- Заголовки `Accept: application/vnd.github+json` и
  `X-GitHub-Api-Version: 2022-11-28`.

## 7. Контракты LLM

Вывод модели - недоверенный структурированный ввод. Go валидирует его до записи
в БД и до любого внешнего вызова.

**Разбор скриншота.**

```json
{"screen": "что это за экран",
 "facts": [{"label": "поле", "value": "значение"}],
 "relevant": "как это связано с жалобой из протокола",
 "unreadable": ["что не удалось прочитать"]}
```

Поле `unreadable` обязательно и может быть пустым списком, но не может
отсутствовать: правдоподобная выдумка хуже явного пробела.

**Ход интервью.**

```json
{"kind": "bug|feature|question",
 "contract": {"<ключ>": "значение"},
 "gaps": ["<ключ>"],
 "questions": [{"key": "<ключ>", "text": "вопрос", "suggested": "предполагаемый ответ"}],
 "ready": false}
```

Проверки Go: вопросов не больше трёх; каждый `key` есть в `gaps`; все ключи
принадлежат контракту из файла правил; `ready` истинно только при пустом
`gaps`. Нарушение - повтор запроса, второе нарушение - падение шага в `failed`.

**Саммари.**

```json
{"title": "до 80 символов",
 "sections": {"<ключ>": "текст"},
 "gaps": ["<ключ>"]}
```

## 8. Промты и правила

`internal/app/rules/contract.yaml` - контракт готовности: ключ, заголовок
раздела в issue, обязательность, по каждому типу обращения.
`internal/app/prompts/` - `screenshot.md`, `interview.md`, `summary.md`.

Порядок сообщений в запросе интервью фиксирован:

1. system: метод интервью, контракт готовности, контекст проекта. Кэшируемый
   префикс, ни одной изменяющейся строки.
2. user: протокол сырья.
3. история раундов.

Правка правил не требует миграции: контракт хранится в `cases.contract` как
jsonb по ключам, а не колонками.

Метод интервью берётся из промта брифовщика (внутренняя база знаний): разбор
конкретного случая, детектор выдумки, замок пересказа «где я ошибся», признак
тянет вопрос. Промт бота самостоятельный, не копия: другой жанр и другой бюджет
вопросов.

## 9. Псевдокод ключевых функций

```
StartCase(ctx, tgUser, projectSlug) (*Case, error)
  вход: пользователь Telegram, slug проекта из callback_data
  1. если telegram_id не в белом списке - вернуть ошибку доступа
  2. upsert users: ФИО и username перезаписываются текущими
  3. если есть активный case - вернуть его и предложить продолжить или начать заново
  4. insert cases со статусом collecting, событие case_started
  выход: обращение в статусе collecting
```

```
CollectItem(ctx, case, msg) error
  вход: активное обращение и сообщение Telegram
  1. если case.status не collecting - подсказать «сбор закрыт», выйти
  2. определить kind по содержимому сообщения
  3. для voice и photo: проверить file_size против 20 МБ, скачать во временный
     каталог, записать file_path и tg_file_id
  4. insert case_items со статусом pending
  выход: элемент в очереди на нормализацию, ответа автору нет (бот не перебивает)
```

```
FinishCollect(ctx, case) error
  1. в одной транзакции: статус normalizing, событие collect_finished,
     jobs для каждого pending voice-элемента
  2. если голосовых нет - сразу job normalize_images
  выход: цепочка запущена, автору отправлено «разбираю»
  примечание: normalize_images ставится всегда, даже без единого фото - именно
  этот шаг строит cases.protocol, и без него текстовое обращение ушло бы в
  интервью с пустым протоколом
```

```
RunNormalizeVoice(ctx, job) error
  1. прочитать файл, при AUDIO_CONVERT=always прогнать через ffmpeg в mp3
  2. запрос к медиа-модели: input_audio плюс инструкция «дай дословный
     транскрипт на русском, не пересказывай»
  3. записать normalized, статус done
  4. если pending voice в этом обращении не осталось - поставить job
     normalize_images
  выход: транскрипт в case_items.normalized
```

```
RunNormalizeImages(ctx, job) error
  1. собрать протокол сырья из текстов и транскриптов, записать cases.protocol
  2. для каждого photo-элемента: запрос к медиа-модели с изображением и
     протоколом в контексте, схема ScreenshotExtract
  3. валидировать: unreadable присутствует, facts не пуст либо unreadable не пуст
  4. дописать разбор в protocol, статус элементов done
  5. поставить job interview
  выход: протокол сырья, включающий разбор скриншотов с учётом жалобы
```

```
RunInterview(ctx, job) error
  1. собрать запрос: префикс (метод, контракт, контекст проекта), протокол,
     история раундов
  2. запрос к диалоговой модели по схеме InterviewTurn
  3. валидировать по правилам раздела 7, при отказе - один повтор
  4. записать kind, contract, gaps, инкремент round
  5. если ready или round достиг предела - job summarize
     иначе отправить автору один вопросный раунд с кнопкой «Всё так»
  выход: либо вопрос автору, либо переход к саммари
```

```
ApplyAnswers(ctx, case, answer) error
  вход: текстовый, голосовой ответ или нажатие «Всё так»
  1. «Всё так» подставляет suggested по всем вопросам раунда
  2. голосовой ответ проходит транскрибацию тем же шагом, что и сырьё
  3. записать ответ в историю, поставить job interview следующего раунда
  примечание: разбор «на какой вопрос это ответ» делает модель на следующем
  ходу, Go не парсит свободный текст. Незакрытые ключи остаются в gaps и
  переспрашиваются, закрытые не трогаются
```

```
PublishIssue(ctx, job) error
  1. если case.issue_number не пуст - выйти, работа уже сделана
  2. EnsureLabels для проекта, если labels_ready ложно
  3. собрать тело: шапка с автором, разделы контракта, список пробелов,
     маркер intake:case:<uuid>
  4. POST issues с метками type, status, author, при необходимости incomplete
  5. при неизвестном результате (таймаут, 5xx) перед повтором - поиск маркера
     в репозитории
  6. записать issue_number и issue_url, статус published, событие published
  7. поставить job notify с номером и ссылкой
  8. удалить файлы обращения, обнулить file_path
  выход: issue в GitHub, автор уведомлён, медиа на диске нет
```

```
ClaimJobs(ctx, limit) ([]Job, error)
  UPDATE jobs SET status='running', locked_at=now(), attempts=attempts+1
  WHERE id IN (SELECT id FROM jobs
               WHERE status='pending' AND run_after <= now()
               ORDER BY run_after LIMIT $1 FOR UPDATE SKIP LOCKED)
  RETURNING *
```

## 10. Логирование

JSON через `slog`, обязательные поля: `service=intake`, `env`, `case_id`,
`user_id`, `step`. Логируем начало обращения, каждую работу (тип, попытка,
длительность, модель, токены), решение модели (тип обращения и число пробелов,
не текст), публикацию (номер issue), все ошибки с причиной.

Не логируем: тексты сообщений, транскрипты, разбор скриншотов, ФИО, содержимое
файлов. В логах человек это `user_id`, а не имя.

## 11. Инварианты и чем они держатся

| Инвариант | Где обеспечен | Чем проверяется |
| --- | --- | --- |
| Медиа не переживает обращение | шаг 8 `PublishIssue`, `file_path` обнуляется в той же транзакции | тест: после публикации файлов на диске нет, `file_id` остался |
| Тикет не публикуется без подтверждения | `publishing` достижим только из `summary` по кнопке автора | тест перехода состояний |
| Единственный источник истины по статусу - метка | сервис не хранит статус тикета, только читает метки | ревью схемы: колонки статуса тикета нет |
| Экстрактор признаётся в непрочитанном | обязательное `unreadable` в схеме, валидация Go | тест на ответе модели без поля |
| Порядок промта фиксирован | сборка запроса одной функцией, префикс первым сообщением | тест: префикс побайтово равен между двумя вызовами |
| Ни одна идея не выбрасывается | недобор даёт issue с меткой `incomplete`, отказ невозможен | тест сценария предела раундов |
| Мультипроектность | проект это строка таблицы | добавление проекта в тесте без правки кода |
| Внешние вызовы идемпотентны | `jobs.key` плюс маркер в теле issue | тест двойного запуска publish |

## 12. Открытые вопросы

- Принимает ли выбранная модель OGG с OPUS напрямую. Проверяется живьём, от
  ответа зависит, попадёт ли ffmpeg в образ.
- Качество `deepseek-v4-flash` на русскоязычном интервью против более дорогих
  моделей. Решается golden-набором.
- Нужен ли повторный проход по скриншоту, если вопрос всплыл уже в интервью.
  Пока не делаем: усложняет шаг ради неподтверждённой пользы. Учесть, что в M1
  файлы удаляются сразу после нормализации (интервью в срезе нет), и такой
  проход станет возможен только когда удаление переедет в `PublishIssue`.
