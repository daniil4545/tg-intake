# Внешние контракты intake

Вынесено из раздела 6 [architecture.md](architecture.md): перечень вызовов и
ограничений внешних API, проверенных документацией или живым запросом. Правила
здесь меняются вместе с кодом клиентов (`bot.go`, `openrouter.go`, `github.go`).

## Telegram

- Скачивание: `bot.Download`, он сам зовёт `getFile`; отдельный `FileByID` дал
  бы второй запрос ради того же ответа. Потолок Bot API - 20 МБ, но
  `file_size` приходит в самом апдейте, поэтому отсекаем до запроса файла.
- Кнопки: `callback_data` 1-64 байта, поэтому в кнопке короткие идентификаторы,
  а не тексты. Маршрутизация - штатная для telebot: `InlineButton{Unique, Data}`,
  библиотека кодирует это как `\f<unique>|<data>` и разбирает сама. Свой формат
  `callback_data` мимо `Unique` не заводим: он не поймается хендлером по кнопке.
  Реальные `Unique` живут в `bot.go` (`project`, `create`, `publish`, `card` и
  прочие), payload - slug проекта, номер раунда или `slug:number` карточки.
- Постоянная reply-панель: вне сбора «Меню | Сброс», в сборе «Готово | Сброс».
  Её видно всегда и не надо искать инлайн-кнопку выше по переписке. Цена:
  reply-кнопка маршрутизируется по точному тексту раньше `OnText`, тексты
  панели - зарезервированные слова, и хендлеры разводят их по состоянию:
  «Готово» в разговоре - ответ автора, «Меню» в сборе - сырьё, «Сброс» -
  всегда управление (от случайного слова-ответа спасает подтверждение).
- Раунд из двух-трёх вопросов уходит одним сообщением: в один чат допустимо
  примерно одно сообщение в секунду.
- Отклик на действие обязателен, и он идёт правкой существующего сообщения, а
  не новой репликой. Нажатие инлайн-кнопки: сначала `answerCallbackQuery` с
  текстом (всплывающая подсказка гасит спиннер до похода в базу или GitHub),
  затем `editMessageText` - экран меняется на месте, отработавшие кнопки
  исчезают. Приём материала в сборе и ответ в интервью правят своё сообщение:
  счётчик «Принято сообщений: N» и пометка «Ответ принят» под вопросами.
  Правка может отказать (сообщение старше 48 часов, текст не изменился) -
  тогда шлём новым сообщением, молчания быть не должно.
- Уведомления владельцу шлёт второй экземпляр бота со своим токеном
  (`ALERT_BOT_TOKEN`) и `Offline: true`: чужой канал не имеет права уронить приём
  обращений, цена - неверный токен виден первой отправкой, а не на старте.
  Пустой токен означает отправку ботом intake (уместно, когда он сам добавлен в
  чат), пустой `ALERT_CHAT_ID` выключает уведомления целиком.
- Правка требует помнить `message_id`, а у сообщений из очереди его знает
  только отправитель: счётчик сбора и последнее сообщение раунда живут в
  памяти процесса. Потеря при рестарте безвредна - появится новый счётчик, а
  пометка раунда просто не проставится.

## OpenRouter

- `POST /api/v1/chat/completions`, `response_format` с `json_schema`,
  `provider.require_parameters: true`, чтобы запрос не уехал к провайдеру без
  поддержки схемы.
- Аудио: только base64 в `input_audio` с полем `format`, URL не принимается.
  Голосовое Telegram это OGG с кодеком OPUS, и провайдер принимает его напрямую:
  проверено живым прогоном. Перекодировки в сервисе нет - режим `AUDIO_CONVERT`
  и вызов ffmpeg убраны в 0.1.5, образ `distroless/static` его и не содержал.
- Изображение: `image_url` с `data:image/jpeg;base64,...`.
- Бюджет одной попытки - минута, три повтора с экспонентой на 429 и 5xx, на 4xx
  повторов нет. Повтор генерирует ответ заново и стоит как первая попытка,
  поэтому не начинается при остатке дедлайна меньше 30 секунд. Прежние две
  минуты держались за шаг, который думал без предела: одна такая попытка
  съедала бюджет работы целиком, и вторая не начиналась никогда (0.1.6).
  Единственный синхронный вызов модели - сборка карточки в `/project` - идёт с
  собственным бюджетом 20 секунд и фолбэком на поля репозитория; повторов там
  нет, за 20 секунд модель не отвечает.
- Размышления диалоговой модели ограничены: уровень задаёт
  `OPENROUTER_REASONING_DIALOG` (`off` - не передавать параметр вовсе), в
  запросе есть потолок `max_tokens`. Размышления считаются выходными токенами,
  и без предела шаг интервью уходил на 110-120 секунд при 4476 токенах ответа.
- Кэш: инвариант порядка промта - канон в [architecture.md](architecture.md).
  TTL у провайдеров порядка пяти минут, поэтому кэш экономит внутри одного
  разговора, а не между обращениями.

## GitHub

- `POST /repos/{owner}/{repo}/issues` с заголовком, телом и метками.
- Метки: по таблице разрешений GitHub права `Issues: write` у fine-grained PAT
  хватает и на `POST /repos/{owner}/{repo}/labels`, и на простановку меток при
  создании issue. Автосоздание несуществующей метки документацией не обещано,
  поэтому старт сервиса заводит метки каждому активному проекту и этим же
  проверяет право - а не в момент, когда первый тикет уедет без меток. Проект,
  добавленный после старта, получает метки bootstrap-шагом первой публикации
  (`labels_ready`).
- Идемпотентность: своего ключа у GitHub нет. В тело issue уходит маркер
  `<!-- intake:case:<uuid> -->`; проверка выполняется только со второй попытки
  публикации - на первой дубля быть не может. Ищем не через search API (его
  индекс отстаёт), а сканом последних 30 issue списком
  `GET /issues?state=all&per_page=30&sort=created&direction=desc`: дубль ищется
  сразу после потерянного ответа, нужный тикет лежит в начале списка. Это
  защита от дубля при потерянном ответе на успешный запрос.
- Лимиты GitHub (5000 запросов в час и вторичные) на наших объёмах не
  достигаются; публикация всё равно однопоточная.
- Заголовки `Accept: application/vnd.github+json` и
  `X-GitHub-Api-Version: 2022-11-28`.
- Просмотр и жизненный цикл тикета: `GET /issues` со `state=all` для списка и
  его меток, `GET /issues/{n}` для карточки и для добора тикетов, вытесненных
  из окна списка, `GET /issues/{n}/comments` для последнего комментария
  (постраничный обход до 5 страниц по 100, `githubCommentPages`),
  `POST` и `DELETE /issues/{n}/labels/...` для точечной правки статуса,
  `PATCH /issues/{n}` со `state: closed` и `state_reason: not_planned` для
  отмены. `PUT /labels` не используем: он затёр бы метки, проставленные
  владельцем вручную.
- Заведение проекта из бота: `GET /repos/{owner}/{repo}` и
  `GET /repos/{owner}/{repo}/readme` (содержимое приходит в base64), плюс одна
  метка записью как проверка права. `owner/repo` GitHub принимает в любом
  регистре - ключ проекта сравнивается без учёта регистра, в базу пишется
  каноническое написание из ответа API.
- Списки issue возвращают и pull request'ы: документация просит отличать их по
  ключу `pull_request`, иначе чужой PR отдаст свои метки нашему номеру.
- Два HTTP-клиента с разными бюджетами. Рабочий обслуживает очередь: таймаут 20
  секунд, три повтора с экспонентой. Быстрый обслуживает то, что зовут из
  обработчика сообщения: пять секунд, без повторов. Причина - `Synchronous` у
  телебота: апдейты всех авторов идут одной очередью, и один медленный ответ
  останавливает бота для всех.
